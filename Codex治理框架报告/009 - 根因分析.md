# 根因分析

## 根因一：把"账本"当"状态"常驻（层归属错误）

STATE.json 的三重身份——指针（active/current_core/latest，应当常驻）、账本
（322 条记录，应当 query-first）、档案（174 条历史 session，应当归档）——被压进
一个 `always_full_boot` 文件。框架明明已发明了正确的机制（query_first 层、
`historical_session_auto_load=false`、lifecycle 闸门），却把最大的数据放错了层。
**这是最大单项（22.4 万 tokens，54%）的直接原因。**

## 根因二：全文重付策略（FULL_SET_EVERY_SESSION_AND_COMPACTION）

"每次会话+每次压缩都全额重读"把一次性成本变成了乘法成本。该策略的动机是
防止"摘要冒充闭包"——但 hash 收据 + 抽查复认同样能建立"我确实持有过全文"的
证据链，成本却是常数级。策略把**防幻觉的手段**（重读）当成了**防幻觉的证明**，
而 runtime 自己都声明 `NOT_CERTIFIED_BY_TOOL`——重付并没有买到它想要的认证。

## 根因三：append-only 的证据永久性没有被"退休"机制配平

证据永久性要求只增不改（对），但没有任何记录生命周期结束时迁出常驻层的通道。
结果是所有历史以线性速度堆进必读文件：STATE 5 天 113 倍、MEMORY/003 无界、
checkpoint 无轮换。**永久性应该在归档层实现，而不是在常驻层实现。**

## 根因四：写作义务按"全分母"而非"触及集"计量

逐 KC 回评的分母是全部 46 条 KC；扩展认知 8 片每轮逐段；航向+偏航双反思每轮必写。
安全动机明确（防局部叙事），但产生了与任务规模无关的固定税：一轮只碰 2 条 KC
也要为 44 条写 NOT_TOUCHED。旧式审计（13 万/份）到分片式（1.4–3.4 万）的演变
证明分母可以瘦身而证据性不塌——但合同没跟上实践。

## 根因五：叙述性五重复制

同一事件（判词、收据、边界）在 STATE 记录、SESSION.md、MEMORY/003、投影行、
审计集五处各叙述一遍。每处都在"当前必读或必写"集合里，信息重叠度高、措辞各异，
一致性靠人工维护（已出现 P5.1 的索引不符）。缺少"一处权威 + 他处指针"的引用纪律。

## 根因六：分片解决了结构，未解决体积；且没有预算线

v2 分片的判定标准是导航/边界（正确），但没有任何机制回答"这个逻辑文档还该不该
全额常驻"。于是 41,857 tokens 的全景视野、27,551 tokens 的 MEMORY 日志心安理得地
留在 always_full 层。**缺的是层的准入预算，不是更多的分片。**

## 根因七：全局宪法不分层

`~/.codex/AGENTS.md` 66KB/29 节全量常驻，宪法、路由表、SOP、产品事实混装。
项目层好歹有 LOAD_SET 分层，全局层连这个都没有——每个会话为 29 节里与自己无关
的 20+ 节付费。

## 复利回路（各根因如何互相加强）

```
每轮必读全部历史（根因一/二）
  → 每轮也必须为全部历史写回评/日志/记录（根因四/五）
    → 历史进一步增大（根因三）
      → 下轮读得更久、写得更久
        → 重事务成本超过承受阈值 → 被绕过（P2）
          → 绕过后真值源漂移（P1/P3）→ 信任下降 → 更依赖"全文重读"自证 → 回到起点
```

框架目前正处在这个回路的"被绕过"节点上。**治理的目标是让 AI 软件工程成功；
当遵循成本使遵循本身不可行时，最大的风险不再是漏读，而是整个合同失去约束力。**

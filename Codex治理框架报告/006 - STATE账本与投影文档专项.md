# STATE 账本与投影文档专项

## 一、STATE.json 的体量与内部构成

| 指标 | 值 |
|---|---|
| 字节 / 行 | 840,123 / 11,905 |
| **est tokens** | **223,524** |
| 层 | `always_full_boot`（每会话全文）+ `dynamic_state` |
| JSON 总字符（含结构） | 771,838 |
| `records` 键字符 | 752,653（**97.5%**） |
| 记录总数 | 322 |
| 其中 `kind=session` | **174（占 STATE 字符 33.8%，261,200 字符）** |
| 其余 148 条（result/formal/t3_pulse/audit…） | ≈49 万字符 |
| session 记录大小 | 中位 1,107 字符，最大 8,751 |

**两个结论**：

1. STATE 名义上是"当前动态状态"，实际是**账本+档案的合体**：97.5% 是 records。
   尽管 `historical_session_auto_load=false`、`evidence_status_grants_load_eligibility=false`
   设计了防复活闸门，但**记录本体嵌在必读全文里**，闸门只挡住"任务资格"，挡不住
   "字节过境"。每会话为获得 5 条 active 记录与若干当前指针，支付 322 条记录的全文。
2. 只删 session 记录不够：反事实测算——去掉全部 174 条后 STATE 仍 ≈510,638 字符
   ≈ **152,429 est tokens**。其余 148 条记录的平均冗长（≈3,300 字符/条）同样需要
   治理（结果类记录把判词、收据、边界全嵌在 STATE 里，而收据本有 RUNS.json/runs/ 目录承载）。

## 三、投影文档（四件套之二）的增长形态

| 文档 | est tokens | 结构 |
|---|---:|---|
| 全景视野.md | 41,857 | 索引 1,083 + 8 行分片（大表按家族拆行，每片自带表头两行） |
| 扩展认知.md | 32,812 | 索引 1,445 + 8 片（AI 阐释层长文） |
| 方向追踪.md | 13,786 | 索引 927 + 5 片 |
| 核心认知.md | 12,191 | 单文件，curation+manifest 管理（纪律最好的一份） |

投影的价值在"当前指针"，但行分片承载的是**累积结果表**（OUT-* 行随每个结果追加）。
分片让单文件回到可编辑规模，却让"全文加载义务"膨胀为索引+8 片的 41,857——
结构与体积是两个问题，分片只解决了前者。

| 片 | est tokens | 内容 |

003 是典型的顺序追加型日志：每轮把整段会话总结（含判词、收据、纪律、下一动作）
追加进来，单条已达 1,500+ tokens（S175/S176 条目）。它同时被 always_full_boot
全文加载——**日志越勤勉，启动越贵**，与"勤于记录"的治理初衷形成直接对抗。

## 五、checkpoint 乘法（磁盘侧，详见 007）

139 个 checkpoint、187M、6,068 个文件。抽实测 S-169：单个 checkpoint 2.9M =
`before/`+`after/` 两份全量副本，内容为 MEMORY、全景视野、扩展认知、方向追踪四个
分片目录 + STATE.json + 各索引。即**每次 checkpoint 把当时全部可变治理文档复制两份**。
这是 STATE/投影膨胀在磁盘上的二次放大（139 × ≈1.3M 均值）。

## 六、本专项结论

STATE 是整个框架成本结构的心脏问题：它把**指针（应该常驻）**、**账本（应该 query-first）**、
**档案（应该归档）**三重身份压进一个 always_full_boot 文件，且只增不减。
任何优化若不动 STATE 的层归属，只在文档间腾挪，节省都是零头。

# 四项消融与合法恢复的结果

声明六成员全部执行。两个接受、四个指定项类型拒绝，remainder=0只覆盖该成员表；没有把诊断当作数学上的普遍不可能性。

| 成员 | 唯一修改/控制 | 实际结果与首个相关诊断 |
|---|---|---|
| SC00 | 原链、原类型及上游对应/实际消费者 | exit0；初次31.513047秒，修复证据分类后的正式02为31.673237秒 |
| SC01 | helix(loop i)从sucPathℤ i改为ℤ | exit42；54行的unglue输入y不再具有所需primGlue类型 |
| SC02 | decodeSquare正整数分支j=i1面由loop k改为base | exit42；43行的decodeSquare端面不一致，诊断明确比较intLoop(pos n)∙loop与修改后的hfill |
| SC03 | decode的i=i0面删掉predSuc y k纠正项、直接用y | exit42；59行hcomp边界出现`predℤ (sucℤ y) != y` |
| SC04 | 保持decodeEncode类型，将J证明项改成refl | exit42；62行通用decode/encode复合不能在此直接作为p的定义性相等 |
| SC05 | 独立模块位置恢复原片段与全部消费者/对应证明 | exit0，31.459519秒；除模块名外与SC00相同 |

四个拒绝均为原生`UnequalTerms`，没有缺库、超时、语法解析失败或未解决hole被计入。每个文件与SC00只有共同模块名调整及预声明的一处替换；SC05只有模块名变化。生成diff和逐项对账见`CONTROL-VERIFICATION.json`。

SC03不证明pred(suc y)在数学上不等于y：原链已经使用该路径等式。它说明删掉沿该路径的纠正项后，该指定立方面组合无法直接满足端面约束。SC04也不否定decodeEncode命题，原J证明与恢复版本已经给出它。

SC01改变了类型族，它是因果对照，不能冒充同任务保真转换失败。SC02/03检验指定实现的边界；没有证明这些写法是所有可能正确实现中唯一的条件提供方式。

在这个实际链中，未见必要局部数据被丢弃后仍以原结论通过的情况。原数据恢复后的接受，是本域正常正控制。该结果支持关闭当前六成员候选，不支持“全HoTT无问题”，也不能把四次正确拒绝称为四次理论缺陷命中。

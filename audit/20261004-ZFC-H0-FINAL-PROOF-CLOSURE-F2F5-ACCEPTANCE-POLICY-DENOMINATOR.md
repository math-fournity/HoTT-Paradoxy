# ZFC-H0 总证明闭环：M2–M5 的实际政策与同一任务来源分母

> **身份：** `RESEARCH_COGNITION_CLOSURE / M2_M3_M4_M5_SOURCE_DENOMINATOR / SOURCE_AND_MACHINE_BOUNDARY / NOT_A_BARE_ZFC_INCONSISTENCY`。
>
> **冻结分母：** 用户圆环原案、IEP *Zeno’s Paradoxes*、Norton *Zeno’s Paradoxes of Motion*、SEP *Set Theory*，以及 fixed Cubical Agda H0 的 C-359–C-366 控制。

## 1. 先分清四条待支付的桥

M2–M5 不能靠同一个 Lean fixture 支付。它们各自要求不同种类的实际证据：

| 义务 | 必须由什么支付 | 不能用什么替代 |
|---|---|---|
| M2：实际 `P` | source/policy 确实把 `FormalDone` 直接提升为同一原过程的 `OriginDone`。 | “级数收敛”“模型有端点”或项目自定义 policy。 |
| M3：bare-ZFC-facing `Q` | 被来源固定的 bare interface，明确其可见输入、完成判词、bridge reject/payment。 | ZFC 可以编码序列，或一个 source-contract fixture。 |
| M4：`SameFullQ` | A 与 H0 的对象、输入、操作、观察、Done、consumer 一一对应。 | 只共享“完成”“永不停机”或 completion-gap 形状。 |
| M5：归因 | 一份实际基础验收/使用来源，把上述 M2–M4 放入同一 `T_meta/C_accept/AdequacyLift`。 | “ZFC 是基础”这句泛称，或 source 沉默。 |

## 2. M2：固定标准解法来源没有支付 strict P

Norton 的直接文本区分 strict completion 与 revised completion；后者删除不存在的 first/last action 条件而解除困难。IEP 把 ZF with Choice、实分析和 Standard Solution 放进应用语境，但也不要求最后一步。C-362 将这张来源合同的逻辑后果机器化：

```text
RevisedAllActionsCompletion
∧ ¬ StrictLastActionCompletion
∧ ¬ (RevisedDone → OriginalDone).
```

故此来源分母得到的不是 M2 所需的实际 `P`，而是：

```text
M2_STRICT_PROMOTION_POLICY_REJECTED_WITH_SCOPE
SOURCE_TASK_CONTRACT_DIVERGENCE_ESTABLISHED_WITH_SCOPE
```

这不说全部数学家都拒绝 P；它只说被冻结的 Standard Solution owner 不能被用作 P 的来源支付。

## 3. M3：过程可表示与完成验收是两层

SEP 固定 ZFC 的一阶语言和集合表示的基础位置；C-366 在外部 Foundation Lean 的 Zermelo-model interface
实际检查 sequence graph、ordinal domain 和唯一 stage value。它排除：

```text
没有时间 primitive ⇒ 集合论不能表示过程。
```

但当前来源没有定义 `bare ZFC` 自己会消费哪个 `FormalDone`、何时要求 `OriginDone`，或如何支付
`FormalDone → OriginDone`。F-049/C-364 已完成当前 application-level 的有界接口控制，判词为：

```text
M3_LANGUAGE_ABSENCE_ROUTE_REJECTED_WITH_SCOPE
BARE_SEMANTIC_COMPLETION_INTERFACE_UNDERDETERMINED_WITH_SCOPE
```

因此 M3 在此分母不能被正实例化，也不能被“ZFC 无法表示时间”伪造为负实例化。

## 4. M4：共同形状已经机器化，共同任务没有

fixed H0 的 C-363 是 `revisedDone ∧ ¬ originalDone ∧ ¬ bridge` 的 exact Cubical Agda completion gap；
C-362 是来源认证的 Zeno-side revised/strict gap。二者共同支持：

```text
COMPLETION_GAP_SCHEMA_MATCH_ESTABLISHED
```

它们不能支持 `SameFullQ`。原因不是缺少一个类比词，而是字段被直接逐项核对为不同：

- A1 的圆环 `State/Op/OriginDone` 仍有多种模型合同；
- Zeno 标准解法是 indexed action/continuum policy；
- H0 是 Cubical Agda universe h-level questioning process；
- 当前来源没有一个 consumer 同时判定二者。

F-048 A5 因而已经给出该明确分母的：

```text
ACTUAL_Q_UNIFICATION_REJECTED_WITH_SCOPE.
```

这不是“两个案例永远不可能同任务”的全称结论；新来源若逐字段把它们接到同一 policy 才能重开。

## 5. M5：归因的必要输入没有出现

若 M2 没有 strict P source payment、M3 没有 bare completion interface、M4 没有 SameFullQ，那么 M5
所需的 `C_accept/AdequacyLift` 无从由当前分母产生。现有 source 只有：

- Zeno-side application owner；
- model/relative-consistency或基础语言 statements；
- fixed H0 的 internal kernel result；
- 项目定义的 C-359 policy consequence。

没有一个来源把它们合成同一基础验收政策。因此唯一准确的 M5 verdict 是：

```text
M5_BARE_ZFC_ATTRIBUTION_UNDERDETERMINED_WITH_SCOPE.
```

它不是 bare ZFC 被证明无责；它说明当前分母不允许将归因推到 bare ZFC。

## 6. 机器核与来源核的组合边界

| 实物 | 真正机器检查的内容 | 不能替它支付的来源义务 |
|---|---|---|
| C-359 | 显式 `ZFCOneUse + SameFullQ + P + B` 的条件 consequence。 | 哪个实际 community policy 具有这些前提。 |
| C-360/C-363 | fixed H0 coarse completion 不能反射为 original finite halt。 | H0 与 Zeno 是同一实际任务。 |
| C-361/C-362 | 几何级数/来源合同的 completion distinction。 | Standard Solution 无支付地宣布 strict original completion。 |
| C-364 | fixed source-contract application view 的 observation-gap control。 | bare ZFC semantic interface。 |
| C-366 | Zermelo model process representation positive control。 | acceptance policy、bridge 或 H0 semantic transport。 |

所以本分母的总有效结果是：已有 kernel 结论保留；实际 M2–M5 连接被逐字段**拒绝或未定义**。没有一条“source 没提到”的事实被升格为数学反例。

## 7. 对总闭环的作用

本卡给出 M2–M5 的来源分母终点：

```text
M2_SOURCE_PROMOTION_REJECTED_WITH_SCOPE
M3_BARE_INTERFACE_UNDERDETERMINED_WITH_SCOPE
M4_ACTUAL_Q_UNIFICATION_REJECTED_WITH_SCOPE
M5_ATTRIBUTION_UNDERDETERMINED_WITH_SCOPE
```

它与 F1-F 的 M1 source denominator 合在一起，允许下一步进行**总完成条件审计**：不是宣布 ZFC 无问题，
而是检查是否已经满足 SOP §5 的“实际有界拒绝”或“formal target 未定义”条件。

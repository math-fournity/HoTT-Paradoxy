## 2. `AS_RUN`：proof context witness 不是 construction lifecycle

公开来源给出的 `AC`、`AC_Pi_Pow`／`AC_func`里的 `exE` 和 `AC_func_Pow`里的 `bexE`，只支持形式证明上下文中局部使用一个存在见证。它没有说明该 `f` 在公理或定理前处于草稿、等待构造、等待评估、已交付或被实际运算者使用的状态。

```text
Target-Q (as run)    = existential axiom/proof use 是否建立 P3 B-direction construction/admission tension
Candidate-Q (as run) = NONE; no source-supported P3 state graph
Control-Q (as run)   = axiom assumption + proof-context local witness versus construction lifecycle
Q-state delta        = Q_SAFETY_REPAIR / P3_NOT_APPLICABLE_ON_THIS_SOURCE
```

因此 `formal axiom / theorem / existential elimination` 不能被简化为 `object-level f constructed` 或 `real/computational task completed`。但反过来，source没有 runtime lifecycle也只是此冻结 proof-system card 的来源缺口，不是对 B 向的一般反驳。

当前 P3要求每个 state/edge有来源事实、前提与效果，且 construction bridge须保持 TheorySide、ProcessSide和 Done 同一。H032在现行合同下仍会被分类：

```text
CURRENT_CONTRACT = ALIGNED_P3_NEGATIVE_CONTROL
P3              = FORMATION_AS_ATOMIC / PROOF_CONTEXT_WITNESS_ONLY /
                  CONSTRUCTION_SEMANTICS_NOT_SUPPLIED

```

P1的 formal payment不会替P3支付构造状态，P3的来源缺口也不会把 P1已支付的 proof theorem重新变成未付 Q。三把刀在此卡没有共同 Q。

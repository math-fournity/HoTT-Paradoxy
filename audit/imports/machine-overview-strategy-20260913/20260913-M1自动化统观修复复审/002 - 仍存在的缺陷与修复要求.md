# 仍存在的缺陷与修复要求

优先级仍按研究工具可信度解释：P1 应在信任自动判定或主线集成前关闭；P2 是 M1 合同的具体缺口，但不否定正常校准结果。以下都不是 HoTT 理论的数学 BUG。

## P1-1 · 执行 profile 与协调器身份没有形成可重建闭包

精确源码哈希已经纳入总资格判定，这是有效修复。但 profile 仍只记录 toolchain 文件的**当前**哈希，没有在 profile/case 中保存它的期望哈希；library registry 也只检查“文件存在、路径与 toolchain 字段相同”。相关实现见
[profile.py:90](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/profile.py:90) 和
[profile.py:136](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/profile.py:136)。

隔离复现同时做了两项变化：把 `TOOLCHAIN.json.runtime_cache.tmpdir` 改到另一路径，并把 `AGDA_LIBRARIES` 改成只有注释、没有可用 library entry 的文件。完整 `inspect-profile` 仍返回 exit 0、`PROFILE_QUALIFIED`；同一副本的 `validate` 也返回 `VALID`。这说明 profile 锁住了 toolchain **所自述的**二进制与 Cubical 哈希，却没有锁住决定执行方式的 toolchain 配置和 registry 内容。

协调器本身也没有被 run 精确固定。三份 post-fix verify 收据都写：

```text
coordinator_version = 0.1.0
git.head = e4ab45b…
git.tracked_dirty = true
tracked_dirty_entries = 13
```

修复实现后来提交为 `56c4306`，但收据没有保存当时 dirty diff 或协调器模块 manifest；`0.1.0` 在修复前后也未变化。[util.py:136](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/util.py:136) 还使用 `--untracked-files=no`。在本次独立 native fixture 中，全部协调器代码是 untracked，run 却把空 Git commit 报成 `tracked_dirty=false`。因此“version + HEAD + dirty 计数”不能恢复实际执行的协调器字节。

影响：正常 proof 的目标与内核结果仍可直接核查，但“这份搜索／收据由哪一版协调器、哪一份执行配置生成”没有可重建身份。缓存、registry 或 runner 变化可能不使旧 case/run stale。

最小修复：

- 在 profile/case 中固定 `TOOLCHAIN.json` 与 `AGDA_LIBRARIES` 的期望 SHA-256，并检查 registry 实际解析到的 library file；
- run 保存 Python 可执行文件身份、registry/toolchain 实际哈希和协调器源 manifest；
- final acceptance run 要么在已提交 clean tree 上生成，要么保存精确 dirty patch/全部参与模块哈希；untracked 输入不得从身份计算中消失；
- `validate` 重算这些身份，不能只显示当前值。

证据：[unpinned execution config 命令](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/commands/unpinned-execution-config-profile/>)、[补充结果](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/results-supplement.json>)。

## P1-2 · validator 对必需证据集合及 artifact 哈希仍 fail open

F3 的 stdout 触发修好了，但 validator 没有定义和强制一份完整 schema。直接证据如下：

| 受控变化 | `validate` 实测 |
|---|---|
| 删除 `target-freeze-3.json` | `VALID`、0 errors |
| 从成功 run 删除整个 `import_closure` | `VALID`、0 errors |
| 从 `generated_sources` 删除 `Proof.agda` 条目，再把实际 `generated/Proof.agda` 也删除 | `VALID`、0 errors |
| 把 `kernel/verify/command.json` 的 argv 和 exit 改成另一内容 | `VALID`、0 errors |
| 将成功 run 的 `ATTEMPT.json` 删除或改坏并不影响本检查路径 | 终态 RUN 存在时不核对应 attempt（另见 P2-1） |

代码原因很具体：

- [case.py:293](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:293) 只遍历收据**自报**的 `generated_sources`，没有要求五个固定模块恰好齐全；
- [case.py:303](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:303) 只在 target ledger 已存在时核对，缺失时没有 error；
- `import_closure` 完全没有进入 validator；
- [case.py:203](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:203) 对 command/environment 只检查文件存在，不核收据内 artifact hash 或内容字段。

而且当前未改原件本身已经暴露了一个真实不一致：三份 post-fix verify × 四个 kernel，共 12 个 `environment.txt` 都是实际 302 bytes、SHA-256 `c50851c…`，收据却记录 301 bytes、SHA-256 `eb9c761…`。原因是 [verify.py:468](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/verify.py:468) 对无末尾换行的字符串计算 hash，而 [verify.py:496](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/verify.py:496) 写文件时增加换行。当前 `validate` 仍返回 `VALID`，正因为它不检查这项。

影响：`VALID` 不能支持交接中“证据完整、可恢复、完整 import closure 已核”的主张。旧 stdout 完整不代表其它证据不能失踪。

最小修复：为 search、verify、attempt、legacy、review 分别定义必需字段与固定 artifact roster；验证恰好存在的五个 generated modules、必需 target-freeze entry、import closure、command/environment/stdout/stderr 的路径、bytes、hash 和交叉字段；所有 hash 必须针对实际写入字节计算。缺项不能通过从 JSON 清单删行来消失。

证据：[主结果](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/results.json>)、[Proof 文件同时缺失的结果](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/results-extra.json>)。

## P1-3 · validator 仍信任语义标签、总状态与无认证 legacy marker

即使所有文件都存在，validator 仍没有从原始内容重新导出关键结论：

| 受控变化 | `validate` 实测 |
|---|---|
| 把成功 verify 的 kernel `exit_code` 改成 99，同时保留 `status=KERNEL_ACCEPTED`、`expectation_met=true` | `VALID` |
| 复制一份 search run，写成 `pair_context_checks=0`、`checks_planned=4788`、`complete=true`，并把 witness 观察／种类写错 | `VALID` |
| 把 post-fix verify 的 search binding 改为不存在的 run/revision，再放入一个无有效 schema、无 attester、无 reason 的 `LEGACY.json` | `VALID`；该 run 被列为 legacy，attested_by/reason 均为 null |

[case.py:217](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:217) 没有重算 search 的观察结果、separation kind、数量和 complete 依据；[case.py:313](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:313) 只检查 status/expectation 的少量组合，没有从 exit 与诊断重算状态；[case.py:379](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:379) 只凭 `LEGACY.json` 存在就切到弱校验分支。

影响：某份 JSON 可以在不对应实际搜索或内核结果时获得 `VALID`。这正是自动化统观最需要阻止的“把记录中的成功字符串当作证据”。

最小修复：

- 从 pair/ops 重新执行可信模型，重算 observation、separation kind、AST、各计数、控制和 complete；
- 从 kernel exit、timeout、stdout/stderr 诊断重算每个 kernel status 与总 status，并和 command artifact 交叉；
- legacy 只能来自固定 allowlist/manifest，marker 必须有 schema、原 run hash、适用弱项与签发依据；任意新 marker 不得降低校验强度；
- duplicate run id、目录名与 run_id、ATTEMPT/run 身份都需一致。

## P1-4 · 对应审查仍可把错误元数据写成“任务保持”，报告仍跨 search 聚合

当前三份保存 review 的自然语言已经修正，这是正面事实；但通用算法仍未实现它所声称的“由结构导出”：

1. 在副本中篡改模型源，使 profile 明确为 `PROFILE_NOT_QUALIFIED`。`review-correspondence` 仍 exit 0，并为 WV-0002 写 `task_preservation=PRESERVED_AT_MODEL_LEVEL`。CLI 在 [cli.py:195](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/cli.py:195) 取得 fast profile report 后没有检查其 status；五项 preservation checks 也没有 profile qualification。
2. 把 WV-0002 的 `separation_kind` 从 `value_mismatch` 改成 `completion_divergence`，并把观察写成一侧 omega；pair 与 ops 不动，所以现有 AST hash 不变。审查仍 exit 0，写出“一侧发散、一侧返回”，五项全 PASS，并判 preserved。原因是 [correspondence.py:34](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/correspondence.py:34) 直接信任 `witness["separation_kind"]`，没有从 ops 重算。
3. 在含两个 rev-3 search 的真实复审副本中，指定 `explain --search-run AUDIT2-NATIVE-SEARCH`。生成报告仍收进原 `20260913-SEARCH-L1-003` 绑定的三份 verify 和三份 review，再加当前 search 的 verify；输出直接列出四个 verify ID。原因是 [cli.py:237](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/cli.py:237) 只按 case/revision 聚合，不按 source search run/hash。

影响：具体保存的 WV-0002 已修正，却仍可由邻近的输入失真重新生成错误解释；报告又能把多个搜索的证据放进同一结果页。这会直接误导下一轮 AI 对“找到了什么”的理解。

最小修复：对应入口先执行与 verify 相同的完整 binding 和 profile qualification；从可信模型重算观察与 separation kind；逐项核 TaskSpec 的实际 consumer/完成要求；preserved 只能来自这些重算结果。`explain` 必须只连接选定 search hash 的 verify/review，跨 search 内容另列为明确的其它尝试。

证据：[profile 失败仍 preserved](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/commands/review-with-failed-profile/>)、[伪造标签 review](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/commands/semantic-label-review/>)、[跨 search 报告结果](</Volumes/D/HoTT独立答复/20260913-M1自动化统观复审-2705847/results-report-mix.json>)。

## P1-5 · search 的 run-id 没有执行已有安全标识符检查

`verify_witness` 会调用 `validate_identifier(run_id)`，但 search 在 [cli.py:100](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/cli.py:100) 先把原始 `args.run_id` 拼成路径，并直接 `begin_attempt`；`run_search` 自身也不校验。

隔离复现使用 `--run-id ../escaped-run --max-checks 0`。命令 exit 0，并在规定的 `machine-overview/runs/` 外创建：

```text
machine-overview/escaped-run/ATTEMPT.json
machine-overview/escaped-run/RUN.json
```

收据还原样保存 `run_id=../escaped-run`。使用更多 `..` 或绝对路径可以扩大写入位置；本次只在一次性 fixture 内做了单层、安全复现。

影响：由人或 LLM 提供的 run ID 可以突破独占 run 目录，破坏路径所有权和隔离假设；escaped run 又不进入正常 index/validate 扫描。

最小修复：所有命令在任何路径构造之前统一执行 `validate_identifier`；run/search/review/case 的外部 ID 禁止分隔符和绝对路径；所有最终路径 `resolve()` 后必须证明位于指定 owner root。为 search、review、explain、get/query 的标识符分别加 CLI 负向回归。

## P2-1 · 终态 RUN 与 ATTEMPT 没有双向一致性

把一个成功 verify 的 `ATTEMPT.json` 改成 `RUNNING` 并删除结束时间，`validate` 仍返回 `VALID`。[case.py:359](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/case.py:359) 只在 `RUN.json` 不存在时读取 ATTEMPT；只要终态文件存在，attempt 被完全跳过。

本次也确认了正面路径：真实 FileExistsError 会留下 INTERRUPTED，环境修复后同 ID rollover 和 timeout 均工作。修复重点因此不是重写恢复器，而是让 validator 核对每个终态 RUN 必须对应 `COMPLETED` attempt，run/case/witness/AST/attempt number/rollover 链一致。异常若尚未生成 RUN，应保留 INTERRUPTED；不能让 RUN 与 RUNNING 同时成为有效终态。

## P2-2 · sparse grammar 的 witness 已守界，但“声明的负控制”仍越界

在 `deadline_horizons=[2]` 的新 case 中，720 个捕获分离缩减成的所有 witness 都只使用 k=2，F5 主问题已修复；搜索也诚实报告 4,332/4,332 和 complete=true。

同一收据的 negative control 却由 [search.py:465](/Volumes/D/HoTT-machine-overview/machine-overview/machine_overview/search.py:465) 根据输入对最大 round 直接构造 k=1。k=1 不在声明集合 `[2]` 中，但字段名称仍是 `declared_deadline_does_not_separate_this_pair`，报告器也把它当当前负控制。

最小修复：从声明 horizons 中选择满足控制条件的 horizon；没有合适参数时明确 `CONTROL_NOT_AVAILABLE_IN_GRAMMAR`，不能在 grammar-complete 收据中偷偷引入 grammar 外操作。

## P2-3 · 交接文档与版本口径发生漂移

canonical handoff 在 [HANDOFF-20260913.md:37](/Volumes/D/HoTT-machine-overview/machine-overview/HANDOFF-20260913.md:37)、[第 109 行](/Volumes/D/HoTT-machine-overview/machine-overview/HANDOFF-20260913.md:109) 和[第 553 行](/Volumes/D/HoTT-machine-overview/machine-overview/HANDOFF-20260913.md:553) 都把 `56c4306` 写成当前 HEAD；实际当前 HEAD 是 `2705847`，中间已有 `e964ff8` 和 `2705847` 两个 handoff 文档提交。代码身份确实仍是 `56c4306`，所以正确写法应是“implementation commit=56c4306；handoff/current HEAD=2705847”。

`AUDIT-RESPONSE` 又把总状态写成 `F1-F7 FIXED`。如果这个短句仅指七个精确触发，成立；交接正文把它扩写为“证据完整、失败可见、任务保持可靠”时，则被本次邻近反例否定。协调器版本仍是 `0.1.0`，也无法单靠版本号区分修复前后行为。

最小修复：更新 handoff 的实现／文档双身份；将总状态改为“original trigger regressions pass; audit acceptance pending”；提升协调器版本或直接以 immutable source manifest 为运行身份。文档修正不替代前七项代码修复。

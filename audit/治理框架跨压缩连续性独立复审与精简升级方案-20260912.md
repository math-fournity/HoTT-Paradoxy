版本：`COMPACTION-CONTINUITY-REVIEW-20260912-v3`

状态：`INDEPENDENT_AUDIT_COMPLETE / REVISED_AFTER_USER_CORE-REBUILD_RULING / IMPLEMENTED_AND_MECHANICALLY_VERIFIED_REVISION_18 / VERSION_CLOSED_AT_GOVERNANCE_V3.0.0`

适用范围：本报告独立复审 WebGPT 历史治理框架、当前顶层综合 repo 治理框架、Luna Max 的自反馈报告，以及这些机制是否真正服务于“连续跨越上下文压缩后，仍像没有压缩一样继续研究”的用户目标。v2 根据用户进一步说明，冻结三件套完整加载的不可替代性并撤回任何以“现行核心摘要”替代 `核心认知.md` 全文的备选。本报告提出精简升级方案，但**不修改**当前 `.codex` 规则、STATE、三件套、runtime 或数学研究状态。

## 0. 结论先行

我的结论比上一份 Luna Max 报告更进一步：

1. **当前治理框架确实复杂化了，但复杂化主要发生在“每轮认知装配”与“重复审计”，不是历史保全、证据分层或原子 checkpoint 本身。**
2. WebGPT 的原框架和当前顶层框架都把一个正确目标——跨 Session/压缩保持研究连续性——错误扩大成了“除三件套外，还把越来越大的历史证据、机器索引和旧收据全文重新放进模型上下文”。WebGPT 已经用自己的 `Q-CONTEXT`、`L16–L18`、R036–R039 记录证明，这会形成“加载触发压缩，压缩又要求从头加载”的自激循环。这里被否定的是**三件套之外的无边界扩张**，不是用户指定的三件套全文输入。
3. 当前顶层框架继承了这个核心错误，并进一步放大：v2 需求 owner 写入后的当前 runtime 计划要求加载 **105 份文档、9,424,036 bytes、110,356 行**；WebGPT 历史快照的当前计划是 **498 份文档、3,672,791 bytes、64,812 行**。两者的工具都明确写着 `model_context=NOT_CERTIFIED_BY_TOOL`。
4. 当前 9.42 MB 中，用户明确要求的三件套占 **1,168,976 bytes / 12.40%**；两个 machine-managed manifest 占 **3,537,190 bytes / 37.53%**；8 份历史逐-KC审计占 **3,477,316 bytes / 36.90%**。三类合计占 **86.84%**。因此，最严重的浪费不是三件套本身，而是把机器索引和历史收据误当成每轮必须常驻的认知。
5. Luna 报告关于跨 owner preflight、generation migration、provenance、派生物自依赖和 writer 顺序的建议大体有价值；但它没有识别首要架构问题。如果先实现这些建议，而不先修复加载模型，框架只会在错误的主链上继续增加检查器、状态和收据。
6. “理论上的无限穿越压缩”包含两个缺一不可的合同。第一是**输入保真**：每个压缩边界后，必须重新完整加载 `核心认知.md`、`方向追踪.md`、`全景视野.md` 的当前逻辑全文；核心用于注入训练数据中没有的用户原创认知，另外两份用于恢复全历史/全方向/全成果视野。第二是**行为连续**：未来 AI 必须实际利用这三个输入作出与当前研究状态相称的判断。行为验收是追加证据，绝不能替代全文输入。
7. 推荐的第一阶段因而不是“保守临时保留”三件套，而是**永久冻结 `核心认知.md → 方向追踪.md → 全景视野.md` 的全文启动不变量**，把 manifest、validator 源码、旧 Session、旧逐-KC审计、raw ledger 和历史收据移到查询/按需/归档层。仅按当前实物选取三件套和必要当前入口，候选启动集约为 **18 份、1,328,309 bytes**，比当前计划少约 **85.91%**；这证明无需削弱用户上下文工程，也能先消除大部分浪费。
8. v1 中“若核心全文挤压研究空间，可考虑拆成完整原文账本与现行核心原则”的备选现已明确撤回。`核心认知.md` 不是可以由摘要、manifest、主题索引、KC 子集或另一份“现行核心”替代的冷档案。若完整三件套在某宿主上无法容纳，框架必须先削减非三件套载荷；仍无法容纳时应 fail closed 或使用足够容量的宿主，不能自动摘要核心。

所以，正确升级方向不是“再增加一层治理”，而是：

```text
完整保存一切 ≠ 每轮加载一切
可发现一切   ≠ 当前常驻一切
工具读出全文 ≠ 模型保有全文
历史可审计   ≠ 历史收据拥有当前任务资格

真正目标：
少量、当前、完整的启动核
        +
按当前任务精确恢复的证据切片
        +
永不丢失但默认不常驻的历史原件
```

## 3. 本 repo 真正要做什么

这个 repo 的目的不是保存一套漂亮的治理框架，也不是证明“历史文件一个都没有丢”之后停止。它是一个长期 AI 数学研究工作区，必须同时完成五个结果：

1. 忠实保存用户关于 HoTT、时间、ASK、现实相对悖论和 Z 哲学的研究问题与工作意识；
2. 让 LocalGPT、WebGPT、Gemini 的历史工作和两个 Git 谱系可发现、可回源、可区分；
3. 让所有候选方向、正反结果、失败、未知、证据等级和下一动作维持当前可见性；
4. 让未来 AI 能继续做新的数学构造、反例、形式化和现实桥梁审查，而不是每次重新整理历史；
5. 在 Session/压缩边界后恢复足够认知，使研究决策和证据纪律与压缩前等价。

因此，治理的成功指标应是：

```text
恢复后是否能正确回答“用户要什么”
恢复后是否看得见全部当前方向和结果
恢复后是否知道哪些结论仍未证明
恢复后是否能选出有判别力的下一动作
作具体主张前是否能定位并读取直接证据
新成果是否被原子、可恢复地写回当前 owner
```

文件数、账本行数、validator 数量和每轮输出字节数都不是独立成功指标。

## 4. WebGPT 原框架：真正的威力与根本缺口

### 4.1 值得保留的部分

WebGPT 原框架最强的地方不是“全文加载”，而是建立了一条真实的研究状态链：

- 根 AGENTS 路由治理 Skill `hott-session-governance` 与业务 Skill `hott-paradox-research`；
- STATE 用稳定 ID 保存 requirement/candidate/result/session/source gap，记录 `depends_on`、`full_sources`、`source_hashes` 和状态；
- FRONTIER 保存最值得推进的下一判别动作；
- LESSONS 保存失败、反解释和重开条件；
- RESUME 给新 Session 一个可执行入口；
- 每个研究轮保存 PROOF_NOTE/CLAIMS/SOURCES/代码/测试/原始运行和证据范围；
- checkpoint 有 snapshot、lock、transaction、before/after、stale writer 拒绝和 finish/rollback；
- portable handoff 与 exchange 明确区分发送、接收、审计、接受和合并。

R039 是这套机制的良好实例：它不仅留下“31/31”，还留下 `PAPER_ONLY`、`native_kernel=NOT_RUN`、`HoTT_core_error=false`、`novelty=KNOWN_CORE_NOT_CLAIMED` 和下一候选 race/timeout。这样的结果包能被未来研究者继续使用而不夸大。

### 4.2 它已经实证暴露的缺口

WebGPT 自己记录了全文加载模型的失败：

- `Q-CONTEXT.progress_note` 记录 92 份、1,177,239 bytes 的动态集合未完整通过，聚合正文截断并发生真实压缩；
- LESSONS `L16–L18` 明确指出固定集合加载触发压缩，压缩后又要求重读，可能永远无法进入业务；
- R036、R038、R039 的 cognition status 分别出现 `NOT_CERTIFIED_FULL_DYNAMIC_LOAD`、`DYNAMIC_INCOMPLETE`、`BLOCKED_FULL_COGNITION_DYNAMIC_INCOMPLETE`；
- WebGPT 当前快照的 runtime plan 已膨胀到 498 份、3,672,791 bytes、64,812 行；
- 91 个 record 中 88 个属于 loader 视角的开放状态，39 个历史 Session 仍是 `review_required`。

这说明 WebGPT 框架做到了“历史不静默消失”，却没有解决“什么必须在当前上下文中常驻”。它把数学结果需要复核与 Session 生命周期混成一个 `review_required` 状态，导致历史 Session 和大量依赖永久获得当前加载资格。

## 5. 当前顶层框架：新增优势与放大的问题

### 5.1 当前顶层真正增强了什么

当前框架相对 WebGPT 有不可替代的增强：

- 以 `核心认知.md` 统一三平台用户原文和本轮治理原文；
- 以 `方向追踪.md` 形成跨 LocalGPT/WebGPT 的 24 方向 portfolio；
- 以 `全景视野.md` 形成跨来源的结果、失败、未知和证据边界；
- 以 source manifest、四类 ledger、22,226 行 reconciliation register 和理解章节 merge manifest 建立跨 repo provenance；
- 保留 LocalGPT dirty、WebGPT revision41、Gemini 仅对话、aistudio-docs 已移走等互不相同的边界；
- 仍然保留 checkpoint、hash、stale/recovery 和 `NOT_CERTIFIED_BY_TOOL`。

这些能力应该保留。它们解决的是 WebGPT 单一工作区无法解决的“跨 AI、跨 repo、跨历史来源”的问题。

### 5.2 当前顶层怎样放大了加载问题

当前实现把 `REQUIRED` 写成一个 55 文件的硬集合，并在 `graph()` 中把所有 `open/active/pending/blocked/in_progress/review_required` 记录、手工 active/review_due/unresolved、latest session 及递归依赖全部加入。当前 STATE 的 22 个 record 中有 15 个被视为开放，其中 8 个是历史治理 Session。

这些历史 Session 每个都引用自己的 `CORE_COGNITION_AUDIT.md`。8 份表合计 3,477,316 bytes；内容都是对同一 903/913 KC 集合的重复行，且多数关系为 `NOT_TOUCHED`。它们作为历史证据可以有价值，但不应该在未来每轮重新进入上下文。

当前 fixed set 还全文装入：

- `sources/SOURCE_MANIFEST.json`：2,442,132 bytes；
- `核心认知.manifest.json`：1,095,058 bytes；
- 多个 schema、validator 源码、audit summary/receipt；
- 理解章节工作史和旧方案；
- 再由 active direction/result records 重复引入 WebGPT STATE、HoTT owner、source prompts 和旧 Session。

这违反了全局治理对 machine-managed 资产的规则：这类资产应先通过 manager 的 `query/list/get` 建立最小认知，不应默认全文读取 raw JSON。

### 5.3 当前 fresh receipt 证明了什么，没有证明什么

`verify_fresh_three_way.py` 在新 Python 进程中读取全部计划、拼接字节、检查 hash/EOF，并拒绝 wrong snapshot、缺 chunk 和篡改 chunk。它证明 runtime 的文件协议有效。

它没有启动一个 fresh AI，没有把正文装入模型，没有要求模型回答研究状态问题，也没有测量压缩后的行为。receipt 自己明确写着：

```text
model_context = NOT_CERTIFIED_BY_TOOL
mathematics   = NOT_CERTIFIED
```

因此，“105 份都被 Python 读过”不能作为“未来 AI 像没压缩一样”的验收。

此外，当前 `MEMORY.md` 和此前比较报告仍写 load graph=96，而当前 runtime 与 fresh receipt 都给出 105。这个 96/105 漂移再次说明：越多 current/receipt/summary 载体，越容易产生叙事不一致。

## 6. 两套框架的发证式比较

| 维度 | WebGPT 原框架 | 当前顶层框架 | 独立判定 |

## 7. 对 Luna Max 报告的独立评价

| Luna 建议 | 本次判断 | 原因与处理 |
|---|---|---|

| current-owner consistency preflight | 保留为第二优先级 | 能防 96/105、revision/status 漂移，但不能解决上下文爆炸 |

| 派生物 dependency graph | 缩小为直接自循环/陈旧检查 | runtime 已有 record cycle 检查，不需要再建通用图系统 |

Luna 报告最大的遗漏是：它把“反复纠错”作为主问题，却没有把“研究根本无法开始或每次都要重放 9.42 MB”提升为 P0。它甚至把“上下文成本”主要表述成避免 raw ledger，而没有审计当前 plan 的实际组成和 `review_required` Session 的递归放大。

本次重新排序为：

```text
P0  修复加载模型与生命周期选择
P1  证明 fresh AI 能恢复研究等价状态
P2  再做最小 current-owner/generation/provenance preflight
P3  只有新证据支持时再扩展 writer/supersession/narrative lint
```

## 8. 根因：五种不同命题被混成了“全文加载”

### 8.1 完整保存

历史原文、代码、失败、Git、manifest 和 Session 不应丢失。当前框架在这方面做得好。

### 8.2 完整可发现

未来 AI 应能知道某一方向/结果/证据存在，并能沿 ID 和 locator 找到。STATE、三件套、README 和 register 应承担这一层。

### 8.3 当前工作意识

未来 AI 开工时必须知道用户航向、当前方向组合、成果边界、开放未知和下一动作。这不是一份可以由通用训练先验补足的摘要层，而由三件套当前逻辑全文共同构成 always-on 研究认知层：核心注入用户原创问题意识，方向与全景提供全局统筹视野。

### 8.4 当前任务所需全文

三件套是任务无关的全文输入例外，任何研究任务都要完整加载。当 AI 要推进 `DIR-W-RACE-TIMEOUT` 时，在已经完整持有三件套之后，还应加载与它相关的 R039 proof/result、操作语义和必要 HoTT 规则；不需要同时加载 aistudio coverage、全部旧 Gemini 往来和 8 份治理回评。精确 `core_refs` 用于定位和聚焦，不能反向把完整 core 缩成一个 KC 子集。

### 8.5 模型理解

文本被工具读出、hash 正确、进入 prompt，仍不自动证明模型理解。理解只能通过实际任务行为、反例和回源能力作有限验收。

当前框架没有把“三件套必须全文进入上下文”与“其他资产按任务回源”分开，结果是历史保全越成功，三件套越难真正稳定进入上下文并留出研究空间。

## 9. “像没有压缩一样”的可实现定义

### 9.1 不承诺隐藏心理状态相同，但必须保证三件套输入相同

无法保证未来模型拥有与压缩前完全相同的隐藏激活和逐 token 心理状态；这不削弱用户对三件套全文重新输入的要求。三件套就是为了在模型内部状态无法永久保存时，从 repo 外部重新提供不可由训练数据替代的用户认知和研究全局。因此不得把目标错误写成：

```text
INFINITE_COMPACTION = EXACT_INTERNAL_MEMORY_IDENTITY
```

### 9.2 双重合同：输入保真 + 研究行为连续

第一项是不可替代的输入合同：

```text
AfterEveryCompactionBoundary:
  load_exact_logical_document(核心认知.md)
  then load_exact_logical_document(方向追踪.md)
  then load_exact_logical_document(全景视野.md)

OnEveryFreshSession:
  execute_the_same_three_way_full_load

WithinSameUncompactedContext:
  do_not_reload_merely_because_a_new_user_turn_or_internal_step_started
  reload_only_if_three_way_source_changed_or_context_retention_became_uncertain

ForbiddenSubstitutes:
  summary | manifest | embedding hit | KC subset | old receipt | model memory
```

“logical document”允许未来按自然边界物理分片，但所有分片仍须按索引顺序完整加载；分片只解决传输/导航，不减少语义内容。

第二项才是研究状态的可观察等价。令 `S_n` 是第 n 个已 checkpoint 的 repo 状态，`Recover(S_n, task)` 是新 Session 在完整三件套基础上按任务回源后的认知。目标应是：

```text
Recover(S_n, task)
  ≃
压缩前研究者对 task 作出可靠下一决策所需的最小充分认知
```

这里的 `≃` 不是逐 token 相等，而是对一组可观察命题保持一致：

1. 用户当前目标和禁止漂移点一致；
2. 所有当前方向及其状态、依赖、优先级可列举；
3. 所有当前结果、反例、失败、未知和证据等级可列举；
4. 最新已完成动作和下一最小判别动作一致；
5. closed/historical/superseded 不会错误复活；
6. 完整核心已经在场，并能对选定方向聚焦正确 KC、加载直接证据；
7. 对超出证据的强主张会拒绝或降级；
8. 新结果能原子写回，下一 Session 能观察到。

只要每一轮都满足 `三件套全文恢复 → 任务证据回源 → 工作 → checkpoint → fresh 双轨验收`，连续性可以通过 checkpoint 归纳维持任意多轮。三件套之外的历史证据不需要全部同时常驻；三件套本身不适用这一按需规则。

## 10. 目标架构：四层认知，而不是一个无限 LOAD_SET

```text
L3 历史原件/审计/代码/Git（完整保存，默认冷）
                    │ locator / query
                    ▼
L2 当前任务证据切片（按 direction/result/claim 精确水合；不替代完整 core）
                    │ 结果与未知回写
                    ▼
L1 不可替代的全文研究视野（核心、方向、全景）
                    │ 每次完整恢复
                    ▼
L0 启动核（AGENTS、治理 Skill、协议、repo/权限/恢复规则）
```

### 10.1 L0：启动核

每次新 Session/压缩后全文读：

- 根 `AGENTS.md`；
- 根 `README.md`、`MEMORY.md`、`feature-list.md`、`rulings.md`；
- `.codex/AGENTS.md`、本地治理 Skill、`PROTOCOL.md`、load policy；
- 业务研究时再加载业务 Skill，不让纯治理审计自动进入全部数学方法正文。

### 10.2 L1：当前研究视野

每次新 Session 和每个压缩边界后永久全文读，且顺序固定：

- `核心认知.md`；
- `方向追踪.md`；
- `全景视野.md`；

随后加载当前 STATE 的 active/open issue 视图；研究模式下再加载 FRONTIER、LESSONS、RESUME 和三问。

关键变化不是暂时保留三件套，而是把三件套永久定义为不可缩减输入，同时禁止历史收据、机器 manifest 和 validator 源码跟随它们自动常驻。

### 10.3 L2：任务证据切片

选定任务后，由 stable ID 展开：

```text
direction_id
  → core_refs（在已全文加载的 core 中聚焦精确 KC，不是选择性加载）
  → result_ids
  → open issues / failed_at / reopen_if
  → exact owner / proof / code / run / source
```

L2 必须读决定本轮主张的证据全文；这里不能用摘要替代原证据。不同任务得到不同的**附加证据切片**，但得到相同的三件套全文底座。这才是“固定用户认知与全局视野 + 任务相对最小充分证据”的闭包。

### 10.4 L3：历史与机器层

默认不进入模型全文上下文：

- `核心认知.manifest.json`、`sources/SOURCE_MANIFEST.json`；
- raw ledger、22,226 行 register；
- 历史 Session、checkpoint before/after、旧 full KC audit；
- validator/runtime 源码和旧验证报告；
- source snapshots、Git objects、原始 trajectory。

它们仍完整保留、可查询、可验证；当任务审计其实现或某条来源时才进入 L2。

## 11. 精确的最小变更设计

### 11.1 `LOAD_SET` 从文件清单升级为职责分层

建议下一版使用一个 owner，不新增平行数据库。现有 `LOAD_SET.json` 可升级为 v3，至少区分：

```json
{
  "always_full_three_way": [
    "核心认知.md",
    "方向追踪.md",
    "全景视野.md"
  ],
  "always_full_boot": [],
  "research_full": [],
  "query_first": [],
  "task_expand": [],
  "archive_verify_only": []
}
```

runtime 必须拒绝删除、重排或降级 `always_full_three_way`；每个其他文档在 plan 中必须带 `reason` 和 `selected_by`，未来 AI 能看到它为什么进入本轮，而不是只看到路径。

### 11.2 STATE 将生命周期和证据复核分开

当前一个 `status=review_required` 同时承担“这个结果还需复核”和“这个 Session 必须每轮加载”，是主要放大器。建议分为：

```text
lifecycle_status = ACTIVE_WORK | CURRENT | OPEN_ISSUE | CLOSED | HISTORICAL | SUPERSEDED
evidence_status  = UNREVIEWED | REVIEW_REQUIRED | VERIFIED_WITH_SCOPE | NOT_RUN | UNKNOWN
```

loader 依据 `lifecycle_status` 选择当前对象，不依据 `evidence_status` 让历史 Session 自动复活。历史 Session 一旦完成应为 `HISTORICAL`；其尚未复核的数学主张由独立 candidate/result/issue record 保持 `REVIEW_REQUIRED`。

### 11.3 动态选择规则

默认启动只加入：

1. 先完整加入固定顺序的三件套；
2. latest Session 的短 `SESSION.md`；
3. active/current direction/result；
4. open issue；
5. 当前任务显式选择的附加证据依赖闭包。

不得默认加入：

- 所有历史 Session；
- Session 的所有 `full_sources`；
- resolution evidence；
- source hash 所列每个文件；
- 旧 full KC audit。

hash 路径可以在机械 verifier 中检查，而不必把每个被 hash 的正文注入模型。

### 11.4 逐-KC回评与三件套全文加载是两个独立不变量

用户此前明确要求每轮逐编号回评，本轮又明确要求每个压缩边界后完整加载核心；二者不能互相替代，也不能因存储成本被静默删除。

当前方案固定为：

1. 每个实质工作单元仍生成本轮完整 `CORE_COGNITION_AUDIT.md`；
2. 它证明的是公开逐项评估记录，不证明模型隐藏理解；
3. 所有旧审计归入 L3，不进入下一轮默认 load graph；
4. 当前启动可以读取上一轮短 alignment summary 和所有 `TENSION/DEVIATED/CORRECTED` 项，但这只补充当前完整 core，不替代 core；
5. 本升级方案不再包含用 sparse delta 取代逐-KC回评的设计。未来若要讨论，必须作为新的用户需求修订，而不能混入本次容量优化。

这样先解决 3.48 MB 旧审计被反复加载的问题，同时完整保留用户要求的输入和结束审视语义。

### 11.5 Fresh 验证必须从“字节行为”升级为“双轨验收”

保留机械轨：

- 三件套当前 generation/version、固定顺序、逐字节 hash、连续 ranges、真实 EOF；
- 其他路径的 hash、snapshot、stale、lock、transaction、rollback；
- archive 完整性、manager query、引用存在和 deterministic output。

新增模型行为轨：在全新 Session 或真实压缩恢复后，让 AI 在不知道预设答案的情况下完成：

1. 说明为什么核心认知是训练数据外的用户上下文工程，并说出用户最高研究目标和两条现实相对方向；
2. 枚举当前 24 个方向及其状态，或通过受控查询无遗漏取得；
3. 枚举当前结果、主要反例、开放未知和 native/数学边界；
4. 解释为什么 race/timeout 是数学恢复后的候选，而历史交接仍是当前阻塞；
5. 为一个随机 direction 找到精确 KC、result、proof/code/run source；
6. 面对旧 Session 的过时结论，指出 current replacement；
7. 对一个超出证据的强结论 fail closed；
8. 完成一项小任务并 checkpoint，再由第二个 fresh Session正确恢复。

行为轨只能支持指定样本/模型/版本的 `OBSERVED_WITH_SCOPE`，不能升级成永久“模型理解认证”；但行为轨失败或缺失也绝不能反向放宽三件套全文输入合同。

### 11.6 容量合同

不设任意通用行数上限。每次 plan 必须报告：

- bytes/lines；
- 使用目标模型 tokenizer 得到的 token 估计；
- 当前 host context 和 auto-compaction threshold；
- 为实际研究保留的工作空间；
- 若超预算，哪个非三件套层导致、如何移出常驻集合。

若一次加载本身触发压缩，不允许对同一 snapshot 无穷重启。应输出稳定错误：

```text
FULL_TRIO_EXCEEDS_HOST_CONTEXT
RECOVERY_LOOP_DETECTED
TASK_SLICE_TOO_LARGE
MODEL_CONTEXT_NOT_BEHAVIORALLY_QUALIFIED
```

若问题来自非三件套载荷，先按本设计移出常驻集合；若完整三件套本身仍无法容纳，则停止数学研究、保留证据，并使用足够容量的 host 或等待用户另行裁定。不得自动摘要、裁剪、选择 KC 或用旧 receipt 放行。

## 16. 迁移风险、兼容与回滚

### 16.1 最大风险：精简导致静默遗漏

### 16.3 STATE migration 风险

对策：保留 stable record IDs；旧 `status` 有兼容 reader；迁移前后记录集合、依赖和 source hashes 一致；只改变加载资格，不改变数学证据等级。

### 16.4 rollback

- exact HEAD/tag；
- v2 LOAD_SET、runtime、STATE、HEAD；

- current tests/receipts。

若 fresh behavior 退化，回滚到该 tag；历史原件和现有 checkpoint 不删除。

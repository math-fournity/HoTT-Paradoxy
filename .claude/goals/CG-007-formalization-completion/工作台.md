## 4. 教训

- W1：开工前漏了翻查，写结论前补上了。以后开工的第一个动作就是翻查，与写文件分开。
- `run_cmd` 依赖检查可以把“没有用到某类论证”这种范围声明变成机器核对，并附正控制。以后凡是声明“没有用到 X”，都这样核对。
- zsh 不对未加引号的变量分词：多参数命令用 bash 数组，或用 Python 调用。
- W3：给一个已有翻译解释的类型再加 `ORingStructure`，会引出 Foundation 的 `standardModel` 与翻译解释两个 `Structure` 实例相争。用类型同义词加恒等双射（S4 的 `eval_equiv_iff`）隔开。
- W3：`naturalNumber_induction` 是 elab_as_elim，情形参数直接写项会把数字字面量的实例弄乱；一律留 `?_` 再逐个证明。
- W7：命题对照文件要导入它引用的每个模块。漏导 `GodelQ.IdeaT` 时，`Sound`、`Complete` 解析到别处的同名声明，报的是“Function expected”，不是“未知名字”。
- W7：先写抽象层，再写实例。P 的两侧分属“跳跃”与“统一”，是在写抽象层 `P1Rule`、`OriginSound`、`FormalSound` 时才看出来的；原设计把它们串成一条链。
- W5：Foundation 在 ℒₒᵣ 结构上的 `≤` 是作用域内的实例（`x = y ∨ x < y`），在 ℕ 上与 `Nat.le` 不是定义相等；用 `rw [le_def]; omega` 搭桥，写成一条引理（`nat_le_iff`）。
- W5：Foundation 的 `“…”` 公式，求值的 simp 引理在任何带 `ORingStructure` 的 𝗣𝗔⁻ 模型里都直接可用；先写一个 `example` 试出化简形状，再写正式引理。
- W5：校验器 `--rerun` 要求证据索引里已有行；先写索引行，再校验（这次先校验了一次，失败后补上）。
- W4b：要证一个语法函数可计算，在 𝗜𝚺₁ 里用 Foundation 的内部递归（`Language.TermRec`、`UformulaRec1`、`PR.Blueprint`）把它写成 Σ1 函数，再用 `computable_iff_sigma1`，比在 Mathlib 里逐层证原始递归省力（约 600 行，对比估计的上千行）。
- W4b：内核陷阱：把一个 Def 包成“恒等代换”的新公式（同一组变量原样传入）会让内核卡死；直接用原 Def（`rel := iTRDef`、`rel_defined := iTR_defined`）。
- W4b：只给 `Defined` 实例时，`definability` 会去展开函数本身而超时；要同时给 `instance … : 𝚺ᴬ₁-Function₂ f := f_defined.to_definable`。
- W4b：`φ/[t]` 是 `φ ⇜ ![t]` 的记号，不是 `Rewriting.app (Rew.subst …)` 的字面形状；改写时直接用关于 `⇜` 的引理。
- W4b：简化目标时，若会把构造本身在结果向量里展开，先 `generalize … = W` 把结果向量换成变量；需要符号编码的值时，用 `have h : encode … = 0 := rfl` 显式给出。
- W4b：读 Foundation 源码核对实现事实（`codeOfREPred` 是选择出的公式、`of_provability` 是语义证明）改变了 W8 的路线；写结论前先读实现，不凭定理名推断。

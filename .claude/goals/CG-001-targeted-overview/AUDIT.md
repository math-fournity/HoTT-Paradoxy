# CG-001 独立审计闭包

> 给另一个会话使用（Claude 或其他 AI，由用户另开）。审计者按以下顺序工作：先独立恢复原意和验收标准，再读执行者的总判词，最后回到源文件、证明源码和运行记录。审计者不替执行者补成果，也不改执行者的产物。

## 1. 固定输入

- **执行者交付的精确版本**：执行者交付时给出的 commit，以及本目录下的 `最终报告.md`、`工作台.md`、`结论账本.md`、`证据索引.md`、`relay.md`。
- **原意与验收标准的来源**：`核心认知.md` 中的 KC-000010、KC-000022、KC-000044 至 KC-000048；本目录 `GOAL.md` §1 的六个完成门和合格命中判据；《最高指示-Claude版》。
- **证据**：`HoTT/formal/claude-cg001/`，以及 `HoTT/verification/runs/` 下名字含 `-CG001-` 的 run。

## 2. 审什么

1. **原意**：路线是否仍在回答用户的问题——理论为经济性或普适性做的取舍，以及让它在同一任务下显露的过程。有没有收窄成 HoTT 内部矛盾、“信息丢了不能恢复”、一般停机问题或覆盖率。
2. **便利地图**：是否来自原典；添入与省去两面是否都看了；“暂无种子”的理由是否站得住。
3. **种子与排名**：每个种子的 T 是否真的被 P 碰到；邻近对照是否选对；查重是否回到了全景原文。
4. **判词**：每个 QUALIFIED_HIT 或 STRONG_CANDIDATE 都逐条核五条判据（a 至 e）。原生证明用 `scripts/audit/verify_formal_proof_run.py --rerun` 复跑。检查有没有拿代理模型冒充靶前提（`MODEL_TARGET_LINK_OPEN`），有没有偷换任务。
5. **结论诚实**：身份标注；精化是否冒充原问；解释是否加码。
6. **遗漏**：G-OMISSION 那一遍是否真的用了另一种组织方式。

## 3. 写入与权限

- 只写本审计自己的记录，例如本目录下的 `审计/`，或用户指定的位置。
- 不改执行者的产物，不推进任何 STATE，不 commit，除非用户另行授权。

## 4. 结论状态

用 `AUDIT_PASS`、`AUDIT_PASS_WITH_ISSUES`、`AUDIT_FAIL` 或 `AUDIT_INCOMPLETE`，每项附证据位置。执行完成、命中状态、审计状态三者分开报告。

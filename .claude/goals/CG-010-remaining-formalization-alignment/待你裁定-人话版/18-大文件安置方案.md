## 一、它到底是什么（调查结论）

- 它是 **9 月 12 日机器统观线建仓时对 324 份历史原始输入做的无损封存**：`objects.pack` 装原字节有序块（ZIP 按原始压缩段保留不重压，其余按 64KB 分段），`STORE.json` 是逐件 SHA-256 索引（30.4MB）。README 自述"**这是历史保全，不是另一套当前工作树**"。
- **不是 git packfile**（文件头已验证）。是自定义格式，需 `workspace/scripts/handoff/archive_store.py` 恢复。
- 当前在 git 里的形态是**健康的**：`dev`／`feat/machine-overview-m1`／`codex/semantic-overview` 的树里都只是一个 **134 字节的 LFS pointer**（oid `3cdaeaf8…`，size 217002151），本体在远端 LFS（HTTP 200 已验证）。**git 层面没有 207MB。**

## 二、决定性发现（推翻"pack 是唯一副本"的前提）

**那 324 份原始输入的原始载体，本来就在 repo 工作树里**：

- `sources/local-gpt/ALL-Markdown-root/Archive.zip`——**143.9MB，SHA-256 逐字匹配 `b6b128ad…`**（与 STORE.json 中 `Archive.zip` 条目的哈希一致）。它是 9 月 12 日打包时的原始总包。
- 另一份在 `/Volumes/D/ALL-Markdown/Archive.zip`（你已移走、按 AGENTS 纪律不恢复的目录）。
- **它未被 git track**（143.9MB 超 GitHub 100MB 限制，当年被排除或忽略），仅存在于磁盘。

即：**pack 与 Archive.zip 是同一批原始输入的两种形态——zip 是原始载体，pack 是解构存储。pack 不是唯一副本。**

## 四、推荐方案（按你的意图：正常分支形态，不留在主工作树）

**步骤 A　建一个独立的历史原件分支并推送（核心动作）**

1. 用 `archive_store.py` 从 pack 恢复全部 324 份原件到临时目录（或直接从两份已存在的 `Archive.zip` 解压——更快且已有原件）；
2. 在主 repo 建孤儿分支（无历史、仅此内容）如 `archive/original-inputs-20260912`，把 323 份（排除 143.9MB 的 `Archive.zip`）按原目录结构提交；
3. 推送到 `ZFC-Failure`。**结果：历史原件以正常文件树＋正常分支的形态在 GitHub 上，任何人 clone 分支即得，不依赖 LFS。**

**步骤 B　那个 143.9MB 的 `Archive.zip` 单独处置（三选一，请你定）**

- **B1（推荐）不入库**，理由：它本身就是这批原件的打包形态，内容已由步骤 A 逐份展开入库——保留逐份展开比保留总包更有用；原件另在 `/Volumes/D/ALL-Markdown/` 与你移走的目录里有副本。**若选 B1，建议在工作树里把它移到 repo 外的冷存区（见第 5 节），并在 `sources/` 留一个 README 说明"原始总包在 repo 外冷存、内容已展开入库"。**
- **B2 用 LFS 入库**（当前 pack 的做法）；
- **B3 拆分后入库**（zip 内分卷，工程量大，不推荐）。

**步骤 C　从各工作树移除 207MB 的 pack 实体副本**

7 份 × 207MB ≈ 1.5GB（主检出、012-opus-w8、cg007-w8-d3×2、9276、machine-overview、semantic-overview、opencode-repo）。步骤 A 完成后，工作树里的实体副本可以全部移除——**git 里本是 pointer，移除实体不影响任何分支内容**，省约 1.3GB。

**步骤 D（修复）　恢复两处 `.gitattributes` 的 LFS filter 行**

machine-overview 与 semantic-overview 的 `.gitattributes` 里 `archive/objects.pack filter=lfs` 被改动/删除，导致昨天 late-snapshot 时实体被当普通 blob 加入而撞 100MB 限制。恢复该行即可根除此类事故。

# 认知水合关系与检查点事务合同

状态：`CURRENT_PROJECT_CONTRACT`

版本：`cognition-hydration-checkpoint/v1`

需求：F-005、F-008、F-012；用户来源：`rulings.md` §5、§8–§16。

实现：`.codex/tools/cognition_runtime.py` 3.2.0。

## 1. 目的与不变量

本合同解决两个会破坏跨 Session 认知连续性的具体故障：

1. 把历史先后或叙事关系写成递归验证依赖，导致一个 stable record 水合数十 MB query-first 原件；
2. Session 自写 `POST-CHECKPOINT.json` 声称 checkpoint 已应用，但没有 canonical transaction/result。

不变量如下：

- 三件套仍按 `核心认知.md` → `方向追踪.md` → `全景视野.md` 全文加载，不能通过本合同缩减；
- record 的验证依赖、研究谱系和叙事邻接是三种不同关系；
- checkpoint 的成功由运行器事务实物证明，不由 AI 的总结文件证明；
- 历史缺件保留为缺口，不以当前时间补造过去不存在的语义回评或事务。

## 2. Record 关系语义

| 字段 | 精确语义 | 是否递归水合 | 是否传播 stale |
|---|---|---:|---:|
| `depends_on` | 当前 record 的验证资格依赖另一 record；依赖变 stale 会影响当前 record | 是 | 是 |
| `research_parent` | 所属研究母题、工作线或概念谱系 | 否 | 否 |
| `related_records` | 历史先后、相邻结果、报告所概括条目或其它叙事关系 | 否 | 否 |

新增或改变为非空的 `depends_on` 必须同时写 `dependency_semantics: verification_staleness`。仅仅“上一轮做了什么”“本报告谈到哪些条目”“样本批次先后相接”不构成验证依赖。

删除错误 `depends_on` 不删除历史关系：原关系改由 `research_parent`/`related_records` 保存；旧状态由 Git 基线恢复。

## 3. Record 主路径模式

默认 `path_mode=document`：`path` 必须是可读取的 UTF-8 正文，并在显式 task hydration 中加载。

`path_mode=scope_locator` 只用于记录的自然对象是目录、集合或其它定位范围时：

- `path` 必须在当前文件系统中是目录；
- 目录本身不作为正文读取；
- record 必须有 `full_sources` 或 `resolution.evidence` 指向可读证据；
- loader 仍验证目录身份，但只把证据文件加入 plan。

该模式用于 `A-KC-AUDIT-GAP-001` 这类“多个 Session 目录的结构性缺口”，不能用来绕过本应读取的文档。

## 4. Task hydration 验收

`plan --profile research --task <ID>` 除原有 `review_required` 外，必须输出：

- `total_bytes`、`total_lines`；
- `hydration_diagnostics.document_count`；
- `hydration_diagnostics.query_first_promoted`；
- `hydration_diagnostics.largest_documents`。

验收顺序：

1. task 主记录、真实验证依赖、直接 `full_sources`、resolution evidence 和 source-hash 目标完整存在；
2. `automatically_included_historical_sessions=[]`；
3. query-first 原件只有在当前任务明确要求全文审计该原件时才允许被提升；
4. 若 query-first 原件只是经历史链间接进入，修正关系图后再研究；
5. 实际按 snapshot 逐文件读取并完成 emitted-byte coverage；工具结果仍不认证模型理解。

本合同不设置任意通用字节硬上限。装配判定同时使用当前 Host context、实际文档规模、是否有超大原件和本轮剩余推理空间；机械验收至少必须消除无意 query-first promotion，并记录前后实测。

## 5. Applied checkpoint 输入合同

Checkpoint payload 必须包含全部 mutable current owners，并在同一事务中新增：

```text
.codex/research/hott/sessions/<session-id>/SESSION.md
.codex/research/hott/sessions/<session-id>/RUNS.json
.codex/research/hott/sessions/<session-id>/CORE_COGNITION_AUDIT.md
```

运行器在任何写入前检查：

- Session ID 合法、与 SESSION/RUNS/audit 身份一致；
- `RUNS.json` 是带 schema 与相同 session ID 的 JSON object；
- audit 声明当前 core generation；
- audit 按 `KC-000001` 到当前 `kc_count` 连续、有序、无重复覆盖；
- relation 属于允许枚举；assessment 与 evidence locator 非空；
- `core_change`、`direction_change`、`panorama_change`、`update_decision`、`cross_conflicts`、`unresolved` 六个三件套字段齐全。

这些检查只证明结构、顺序和证据定位存在，不证明语义评价正确。

## 6. 事务、崩溃与唯一收据

`checkpoint --apply` 的顺序为：

1. 取得独占 writer lock；
2. 重新核 snapshot 与所有 expected hashes；
3. 在 `.codex/cognition/checkpoints/<session-id>/` 写 before/after 副本；
4. 写 canonical `transaction.json`，再发布活动 transaction journal；
5. 原子替换 payload 文件，HEAD 最后写；
6. 逐路径核新 hash；
7. 写 `result.json`，其 `status` 必须为 `CHECKPOINT_COMMITTED`；
8. 删除活动 journal与 lock。

只有第 7 步的 canonical result 能证明 checkpoint 已应用。`POST-CHECKPOINT.json` 是 result 之后的可选派生摘要，至少应记录 result path/hash/status；它不能自写 `checkpoint_applied=true` 取得证明资格。

中断后继续使用既有 `recover finish|rollback` 合同。缺 transaction/result 的历史 Session 不能通过新建相同目录补造，因为那会伪造当时的 snapshot、lock、before/after 与执行顺序。

## 9. 非目标

- 不建设常驻数据库、全函数 trace、Session 调度平台或语义 Hook；
- 不让脚本自动判断 KC 语义是否“真正对齐”；
- 不把 task plan 紧凑性等同于数学正确性；
- 不把 checkpoint commit 等同于 proof assistant 证明；
- 不自动 push、发布或恢复用户移走的来源。

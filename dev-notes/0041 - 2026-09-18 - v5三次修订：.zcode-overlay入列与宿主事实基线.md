**需要，但是增量更新而非结构返工。判断依据：v5 的核心架构（树不动、T0–T3 分级、宿主最小合同、真值单株）是按最坏情况假设保守设计的，`.zcode/` 事实修正只让加速层升级——所以改的是三处，不动骨架。已全部落进设计稿。**

更新一（分片 003 新增 §2.4）：**`.zcode/` workspace overlay 升为一等交付物**。内容：`skills/` 下三枚指向 `.codex/skills/<name>` 的符号链接（ZCode 原生发现、真值单株、全局零足迹）；`commands/` 下 2–3 枚纯 .md 治理命令（`/closure`=档位声明+plan/check 组合、`/checkpoint-dry`=checkpoint 干跑包装）——包装的是同一条 runtime 命令，不是第二套逻辑；`.zcode/config.json` 默认不建。关键决策：workspace hooks 虽经指南确认存在，但 (a) 你的全局宪法"Project Hook 被忽略"条款与之冲突未裁定，(b) v5 的强制哲学是"以必然性强制"（fail-closed 状态机），所以 hooks 只作 P3+ 可选项，待 ROI 遥测显示需要且宪法冲突解决后再议。降级路径明确：任一宿主对 symlink 发现不生效 → 加速层静默失效 → 回退文本路由，合同层零影响（宿主最小合同本就不依赖加速器）。

更新二（分片 010）：P2 交付物加入 `.zcode/` overlay；验收门加两条实测——ZCode 会话须实测 symlink 农场可被发现触发、`/closure` 等命令可经 `/` 菜单调用。

更新三（分片 002）：**宿主事实基线钉版**——本方案对 ZCode 机制的引用源钉定为随产品发布的 zcode-guide 插件 0.1.0（本地路径+检索日 2026-09-18），宿主升级须复核；用户全局宪法的产品条款与基线冲突时以较新者为准并提请你更新。这条是对本次"把未见当不存在 + 宪法过期"双重教训的制度化：产品事实类主张从今以后必须带版本锚。

"巧妙地让 ZCode 一样工作"的机制总结（设计已成型的完整链）：主体工程在 Codex 侧（P0 修复→P1 减容→P2 合同 v5），ZCode 跟进靠三层——(1) 合同层零成本继承（根 AGENTS.md 无条件注入两宿主，档位路由/SOP 全文/runtime 命令全部同路径同语义）；(2) 加速层 repo 内对等（.zcode/skills symlink + commands，随 git 提交，无全局足迹）；(3) 证据层同权（SESSION.md 的 host/model/tier 收据、同一 checkpoint 原子事务）。唯一已知的剩余不对称：ZCode 无 CLI/ACP（P2 试金石须人工执行）、project memory 宿主侧（已声明非真值）、无嵌套 AGENTS（本设计不用嵌套）。

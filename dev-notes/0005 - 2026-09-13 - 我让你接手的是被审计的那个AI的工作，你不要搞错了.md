### 为什么不应整体交接

完全不交换结果同样不合适。第一次统观需要机器线补上系统枚举、搜索边界、反例反馈和可恢复运行证据；机器线则需要第一次统观提供 TaskSpec 的语义忠实性、现实任务、完成标准、反解释、已知机制去重和正式数学证据入口。两边若各自重建 Theory Schema、C11、proof capture 和 current truth，会形成重复系统和竞争 owner。

## 4. 一次标准通信怎样发生

1. 发送方先冻结自己的 exact commit 和 packet SHA-256；
2. 通过 Codex task message 发出握手，明确对方只能写哪个 worktree；
3. 接收方回复 ACK，列出它实际看到的 source OID、packet hash、自己的 HEAD/dirty、接受范围、冲突和下一动作；
4. 接收方只在自己的 worktree 工作，保留失败，形成 clean commit 和证据包；
5. 发送方或主库汇合者按 exact OID 独立审查；
6. 结果被 `ACCEPTED_WITH_SCOPE`、降级、驳回或发回修订；
7. 只有满足相应 Gate，成果才进入主库 current truth。

若消息发送后超时，状态是 `DELIVERY_UNCERTAIN`，我会用 `read_thread`/`wait_threads` 核实，而不会重复发送同一任务。若对方被 fork 或 handoff，我会重新发现新 task ID；不能只凭标题猜。若消息自述与 Git/run 冲突，以 exact code、run 和 Git 证据判断实际状态。

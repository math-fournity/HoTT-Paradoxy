# v5 设计修订：.codex 树不迁移（Codex 项目级 Skill 默认发现）（2026-09-18）

## 用户提问（逐字）

> 你忘了一件事，codex cli会默认加载repo内的`.codex`中内容，你这样移动了之后，codex那一侧的repo内的治理框架会不会就彻底失效了？

（用户并引用了设计报告 003 分片的原句："据此设计：.codex/ git mv 为 .cognition/ 单一真值树（不留复本 stub——两宿主入口本来就是根 AGENTS.md）；"）

## AI 最终回复（逐字，与对外回复一致）

**你说得对，我已经撤回那句"不留 stub、损失为零"并修订了设计报告。联网查证坐实：Codex CLI 的 Skill 发现确有两个默认位置——个人级 `~/.codex/skills/` 和项目级 repo 内 `.codex/skills/`（OpenAI Skills 官方文档及多源一致）。所以搬走整棵树不是"彻底失效"，但确实会让 Codex 侧实质降级。**

精确的失效面分析：搬走后**活下来的是治理链本身**——Codex 的指令注入走 AGENTS.md 层级（全局 `~/.codex/AGENTS.md` + repo 根 `AGENTS.md` + 嵌套），不依赖 `.codex/` 目录；根 AGENTS.md 用文本路由指向任何路径都照常工作。**死掉的是 Codex 的原生宿主机制**：`.codex/skills/` 的自动发现、每会话的 Skill 元数据注入、按 description 自动触发、`$skill-name` 调用——三枚 SOP（hott-paradox-research / hott-paradox-search-sop / hott-local-session-governance）会从 Codex 的"一等公民"降级为"需要文本路由才读到的普通文件"。此外任何版本相关的 `.codex/` 默认读取也会一起失效。我原稿把"AGENTS 任务路由节才是路由职责"当成了"原生发现无价值"——这是错的：自动触发和元数据注入本来就是价值，只是本 repo 的合同没有依赖它而已。

修订后的设计（已写入报告分片 001/002/003/004/005/009/010）：**默认方案改为"树不动"**——`.codex/` 保持原位，Codex 项目级 Skill 发现零损失；宿主中立只在真正发生绑定的三层实现：(1) 叙事层：根 AGENTS 与 .codex/AGENTS 明文声明"目录名为历史遗留，不构成宿主绑定；任何能读文件+跑 python3 的宿主共用本树"（validator R3 禁排他措辞兜底）；(2) 路由层：AGENTS v5 分档路由表统一给 `.codex/…` 路径，两宿主同路径同命令；(3) 证据层：SESSION.md 加 host/model/tier/load_receipt 元数据，ZCode 会话在 STATE/checkpoint 走完全相同的原子事务。ZCode 侧默认纯文本路由，可选按机器用 ZCode 官方 symlink 导入通道把 `.codex/skills/<name>` 链到 `~/.zcode/skills/`。原迁移方案降为**备选**（仅当你坚持去供应商命名时）：真值树迁 `.cognition/`，`.codex/skills/<name>` 改为指向新址的目录符号链接（纯兼容层、零内容复本、不算两套），`.codex/AGENTS.md` 留 3 行指针；硬验收门 = fresh Codex 会话实测三枚 skills 全部可发现、可 `$` 调用、plan/checkpoint 完好——Codex 对 symlink 目录的发现行为未在本 repo 实测过，这正是它只作备选的原因。

为什么默认方案仍然满足你的三个约束：Codex 不失效（两个原生通道全保留）；ZCode 能用（同路径文本路由 + runtime 纯 python3，本 Session 已实际运行过 plan）；零两套（单物理树，可选项全在宿主侧）。去供应商命名的外观收益不值得用 Codex 侧降级去换——"宿主中立"的实质在声明、路由与证据，不在目录名。

# repo 内 Skill 的真实身份：治理合同而非便利技能（2026-09-18）

## 用户提问（逐字）

> codex cli在repo内的的那些Skill，是不是repo内治理框架约束AI运行用的？而不仅仅是一个用户可以随手调用的skill，也就是说，它们是自动被AI在治理框架的要求下加载和调用的？

## AI 最终回复（逐字，与对外回复一致）

**是的——在本 repo 的实际设计里，这三枚 Skill 的真身是"治理框架约束 AI 运行的合同文档"，"用户随手调用的 skill"只是它们顺带保留的宿主外衣。但"自动"要拆成三层说才精确：宿主层只自动到元数据；合同层才是强制的来源；验证层给强制配了机械收据。**

第一层（宿主层，Codex 的 Skill 机制本身）：Codex 对 `.codex/skills/` 的"自动"只到**发现 + 元数据可见**——每会话把 name+description 暴露给模型，正文（SKILL.md body）从不自动加载，要靠模型按描述匹配主动展开或用户 `$` 调用。所以如果只看宿主机制，它们确实"仅仅是个可条件加载的技能"。

第二层（合同层，本 repo 的治理要求——真正的强制来源）：repo 的宪法与加载清单把这三枚 Skill 定义为**分条件的全文必读义务**：`hott-local-session-governance` 在 LOAD_SET 的 always_full_boot（每会话全文，与 AGENTS/PROTOCOL 同层）；`hott-paradox-research` 在 research_full（研究类会话全文）；`hott-paradox-search-sop` 由根 AGENTS 任务路由节规定"执行方案步骤前先完成闭包再加载"。也就是说：AI 不是"可以调用它们"，而是**在对应任务条件下被合同要求全文加载并遵循其程序**——"调用"（按 SOP 的循环/门禁执行）同样是义务不是选项。

第三层（验证层）：cognition_runtime 的 plan 把这些文件列入 documents，check_coverage 要求逐字节发射（FULL_EMITTED_BYTES_MATCH）——加载义务不是口头要求，有机械收据。

最硬的一条证据是 repo 自己声明的：`.codex/skills/SKILL_ROLES.json` 明文 `"automatic_host_discovery": "NOT_ASSUMED; root entry routes the roles"` ——框架**不依赖**宿主的自动发现，路由权在根 AGENTS 的任务路由节。换句话说：这三枚文件的"Skill 身份"对治理而言是冗余的加速器（元数据注入提高被想起的概率），它们的本体是**合同化 SOP 文档**。这也正是 ZCode 侧能用同一套的原因：合同执行力 = 根 AGENTS 注入 + 文本路由 + runtime fail-closed，与宿主 Skill 机制完全正交。v5 设计只是把这个事实显式化：SOP 按 tier 条件化加载，Skill 发现降级为可选加速器。

诚实的边界：合同强制 ≠ 物理强制。AI 若不遵守，宿主不会拦（两宿主都无项目 Hook）；真正的拦截来自"以必然性强制"——不加载就没有覆盖收据、拿不到 CHECKPOINT_COMMITTED、工作在证据链上留下不可伪造的缺口（S170–176 绕过 checkpoint 后 HEAD 漂移锁死 canonical 出口，就是这个机制的现场演示）。

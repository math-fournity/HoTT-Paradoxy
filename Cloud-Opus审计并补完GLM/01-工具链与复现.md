## 1. 结论先行

- **工具链**：Agda v2.8.0 的 **Linux x86-64** release 资产 + cubical v0.9。cubical 与冻结记录（`HoTT/formal/dedekind-omega-missile/TOOLCHAIN.json`，macOS arm64）**逐字节一致**（release 包、库文件、1111 个文件的确定性树哈希全部相同）；Agda 是同一 release 的另一平台资产，不是同一个文件。
- **GLM 六运行的 Linux 复现**：退出码六项全同；每个运行检查的**模块序列与 GLM 原运行逐项相同**（76／77／76／44／75／76 个模块）；两个负控制的错误标签、源码位置与错误正文在去掉路径前缀后逐字相同。

- **本会话 21 个运行**：两轮逐字节重放核验。第一轮 20/21 一致，唯一不一致是首次捕获的冷启动输出（§5）；处理后第二轮 **21/21 逐字节一致**（§6，`11-收据核验结果.json`）。

## 4. 怎样复现

### 4.1 布置工具链

`RUN.json` 的 `command_argv` 写的是绝对路径（`/home/user/toolchain/…` 与 `/home/user/HoTT-Paradoxy/…`），逐字节重放需要相同路径；换路径时应重新捕获，而不是改收据。

```sh
T=/home/user/toolchain
mkdir -p $T/xdg-data $T/xdg-config $T/tmp $T/cubical-release
curl -L -o $T/Agda-v2.8.0-linux.tar.xz https://github.com/agda/agda/releases/download/v2.8.0/Agda-v2.8.0-linux.tar.xz
tar -xJf $T/Agda-v2.8.0-linux.tar.xz -C $T                 # 得到 $T/agda
curl -L -o $T/cubical-0.9.tar.gz https://github.com/agda/cubical/releases/download/v0.9/cubical-0.9.tar.gz
tar -xzf $T/cubical-0.9.tar.gz -C $T/cubical-release         # 得到 $T/cubical-release/cubical
sha256sum $T/Agda-v2.8.0-linux.tar.xz $T/agda $T/cubical-0.9.tar.gz   # 与 TOOLCHAIN.linux-x86_64.json 对照
```

库注册文件是仓库内的 `HoTT/formal/cloud-opus-glm-audit/AGDA_LIBRARIES.linux-x86_64`（一行：cubical 库文件的绝对路径）。

### 4.2 热身（重要）

Agda 在一个新的 `XDG_DATA_HOME` 下第一次类型检查时，会额外检查一批 `Agda.Builtin.*` 模块并把它们的接口写进数据目录；之后的运行不再检查它们。所以在新环境里，**第一个**运行的 stdout 会比收据多出这些行（§5 就是这样发现的）。逐字节重放前先在仓库根目录热身一次（生成的 `.agdai` 被 `.gitignore` 排除）：

```sh
env XDG_DATA_HOME=$T/xdg-data XDG_CONFIG_HOME=$T/xdg-config TMPDIR=$T/tmp \
  $T/agda --library-file=HoTT/formal/cloud-opus-glm-audit/AGDA_LIBRARIES.linux-x86_64 -l cubical-0.9 \
  -i HoTT/formal/glm-russell/iota-syntax HoTT/formal/glm-russell/iota-syntax/ArtificialEquationControl.agda
```

### 4.3 核验

```sh
# 单个运行（负控制加 --expect-rejected；不加 --rerun 只做静态检查）
python3 -B Cloud-Opus审计并补完GLM/tools/verify_copus_run.py --run-dir HoTT/verification/runs/<run-id> --rerun
# 全部 21 个运行，结果写入 11-收据核验结果.json（约 17 分钟）
python3 -B Cloud-Opus审计并补完GLM/tools/verify_all_runs.py --rerun
```

### 4.4 重新捕获（只在换环境或确有必要时）

`tools/capture_all_runs.sh` 与 `tools/capture_q7_run.sh` 记录了每个运行的完整捕获参数；`capture_copus_run.py` 拒绝覆盖已存在的运行目录。

### 4.5 目标内验证器与 canonical 验证器的差异

`tools/verify_copus_run.py` 加载 `scripts/audit/verify_formal_proof_run.py` 并复用它的全部检查（必需文件、RUN/source-manifest 的 schema 与身份、工件哈希、源码哈希、Agda 禁用标记、`--safe --cubical` 编译指示、外部工具链的文件与树哈希、按 `command_argv` 逐字节重放）。两处不同：

1. **索引检查**：canonical 要求运行已登记进 `PROOF_VERSION_CLOSURE.json`，那是 integrator 的文件；这里改为"本目录 `证据索引.md` 中每个身份恰有一行 + 共享矩阵中身份在场"，结果标为 `GOAL_LOCAL_INDEX_PLUS_MATRIX_PRESENCE`，不冒充 canonical 的 `INDEXED_IN_CLAIM_EVIDENCE_MATRIX`。
2. **多一条更严的检查**：去掉注释与字符串后，代码中不得出现 `postulate` 关键字（canonical 只依赖 `--safe`）。这条检查的第一版用的是子串匹配，把注释里的"postulate"一词判成违规；已改为代码级检查并单测（见 `00-工作日志.md` 06:47 条）。

## 5. 首轮核验的不一致与处理

- **现象**：第一轮 `--rerun` 核验中，`20260927-COPUS-REPLAY-GLM-IOTA-SYNTAX-01` 报 `REPLAY_OUTPUT_MISMATCH`，其余 20 个逐字节一致。
- **诊断**：重放的 stdout 与收据相比恰好少 19 行，全部是 `Checking Agda.Builtin.*`；没有任何新增行；退出码都是 0，stderr 都为空。原因：这个运行是新建 `XDG_DATA_HOME` 之后的第一次类型检查（数据目录建于 06:18，本运行开始于 06:24:18，`Agda/Builtin/Bool.agdai` 写于 06:24:24）。
- **处理**：
  1. 首次捕获整体移入 `附件/首次捕获-20260927-COPUS-REPLAY-GLM-IOTA-SYNTAX-01/`，原样保存（stdout sha256 `ffcfb0f695eb189cc5ae7a7de63083bfab045c140dd8cbfe6eb642553c87027e`，RUN.json sha256 `5bdd1e56…cb9f`）；
  2. 第一轮核验结果另存为 `附件/11-首轮核验结果（IOTA-SYNTAX-01不一致）.json`；
  3. 以相同参数、相同 ID 重新捕获，RUN.json 的 `audit_notes` 写明原因；新 stdout 检查 76 个模块，序列与 GLM 原运行完全相同；
  4. 21 个运行整体重新核验一轮（§6）。
- **不影响的东西**：证明源码、命令、退出码与内核判词都没有变化；受影响的只是 stdout 里的检查清单。

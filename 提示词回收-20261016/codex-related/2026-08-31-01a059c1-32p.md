## 利用治理资产建立认知闭包

认知闭包不是“读了一些文档”，而是影响本次结论的关键问题、事实、约束、来源、冲突和未知
都已经被识别；重要证据已加载；剩余未知不会推翻结论，或已经让结论降级。

每个非平凡 repo 任务按以下认知链工作：

1. **用户目标与授权**：明确要回答、诊断、设计、实现、运行还是验证；定义成功和非目标。
2. **指令与边界**：确认全局/项目/目录 AGENTS、所有相关 Git repo、系统岛屿和生命周期。
3. **项目全景与当前态**：读根 README/目录 README 建资产地图，读 MEMORY 获得当前方向、
   已验证新知、开放问题和下一步；两者都是路由，不替代实物。
4. **应该怎样与为什么**：读 Feature 对应组件、rulings/原始用户来源、当前 system/detailed
   design 和 ADR；区分已采纳、候选、废止、设计选择和临时参数。
5. **实际怎样与如何证明**：回到代码、配置、机器 schema、依赖锁、测试断言及实际结果、
   数据查询、进程、日志、运行产物、trajectory/proof 和当前外部权威。
6. **历史理由**：仅在来源缺失、冲突、迁移、事故或用户要求时下钻 Git log/diff 和历史实物；
   Git 是历史证据，不是当前需求数据库。
7. **冲突与时效**：按事实类型、版本和时间消解。目标不能冒充当前实现，代码不能否定用户要求，
   文档不能证明运行，旧 run 不能证明当前现场。
8. **负结论与未知**：声称“不存在、未实现、无遗漏、全部覆盖”前扩大同义词、路径、历史和
   动态来源搜索；范围不足只能说“在已检查范围内未发现”。
9. **闭包判定**：material claims 有相称证据，重要冲突已处理，动态事实已核当前，未知已披露，
   相关领域 Skill 已加载，才能回答或行动。
10. **工作后回写**：持久需求、设计、状态、入口、证据或废止关系变化时执行 governance；
    只更新事实真正变化的唯一真值源。

各载体职责：AGENTS=宪法/路由，README=资产地图，Feature=当前需求，MEMORY=当前态，
rulings=用户原意，docs=稳定知识，dev-docs=未定过程，代码/config/schema/tests/data/runtime=实际
实现与证据，Git/history=历史。索引永远不能替代决定性证据。

新 Session、上下文压缩、工作目录/范围变化、关键资产更新或动态外部事实变化后，必须审计
原闭包是否失效；失效就重建，不能把旧 Session 的“我记得”当永久认知。

## 第一原则：先建立认知负载/认知闭包，再回答或行动

AI 成功回答问题或完成任务的前提，是先弄清楚：为了这一次具体请求，自己必须知道什么，
这些认知分别在哪里，是否已经完整加载，彼此是否一致，哪些仍然未知。没有建立足够的
认知负载之前，不应凭局部文件、摘要、训练记忆或直觉直接给出确定结论。

### 背后的理念：知识供给、认知消费与跨 Session 循环

**认知闭包优先原则**：AI 在回答问题、制定方案或执行工作之前，必须先建立与当前任务
相匹配的、最小充分且证据可追溯的认知闭包。没有正确的认知，就没有可靠的判断；没有
可靠的判断，就没有可靠的规划和执行。

认知闭包是成功工作的第一道门槛和第一优先事项，但不是成功本身。闭包完成后，AI 仍需
进行正确推理、制定方案、执行、验证，并诚实处理未知和失败。

认知闭包能够高效建立，还有一个前提：过去工作的 AI 已经把 repo 中的知识按照稳定职责
规范化管理。`repo-cognition-governance` 承担知识供给侧职责——让用户需求、稳定知识、
当前状态、资产入口、历史理由和运行证据进入可发现、可区分、可追溯的载体。它管理 repo
知识的根本目的，不是让文档显得齐全，而是让未来 AI 面对具体问题时能够正确建立认知闭包。

`repo-cognitive-closure` 承担知识消费侧职责——未来 AI 先判断成功回答当前问题需要知道
什么，再借助治理后的 README、Feature、MEMORY、稳定文档和底层实物，建立本次任务的
认知闭包，然后才进入回答、规划和执行。

本次工作产生的新需求、可靠结论、状态变化和资产关系，再由治理 Skill 落回 repo，服务
更未来的 AI。于是形成持续循环：过去 AI 规范化沉淀知识，当前 AI 建立认知闭包并完成
工作，新的可靠认知再次被规范化沉淀。

这里的“全面”是相对于当前任务而言，保证关键认知面没有缺口；它不等于通读整个 repo，
也不等于加载越多越好。目标始终是任务相对的最小充分认知闭包。

`repo-cognitive-closure` 是专门用于建立本次任务认知闭包的全局 Skill。完整内容位于：

`/Users/aurolafly/.codex/skills/repo-cognitive-closure/SKILL.md`

几乎所有依赖 repo 事实的非平凡问题，都必须在实质性分析、回答、方案或操作之前，
先用文件读取工具完整加载该 Skill，并按它完成本次任务的认知闭包。名称和 description
只用于发现，不能替代正文；不能因为以前 Session 读过就跳过本轮读取。

### 必须加载认知闭包 Skill 的场景

以下任一条件成立就必须加载：

1. 回答依赖当前 repo 的需求、架构、代码、配置、数据、测试、文档、运行状态、历史或
   用户裁定。
2. 用户问“是什么、为什么、现在怎样、做到哪里、哪里有问题、应该怎么改、下一步什么”。
3. 要解释、诊断、调查、评审、规划、实现、重构、运行、审计或验证 repo 中的任何非平凡事项。
4. 要声称某项工作“正确、完整、已实现、已验证、没有遗漏、当前有效”或作出类似判断。
5. 第一次进入项目、跨 Session 接手、上下文发生压缩，或者用户的新要求改变了原任务范围。
6. 已读材料之间存在冲突、过时、缺口，或者关键结论只能从 Git/运行现场/外部权威来源恢复。

只有问题确实不依赖任何项目事实，或者是影响面已确定且无语义变化的明显微小操作，才可以
不加载。如果不确定，默认加载。

### 认知闭包的基本要求

加载 Skill 后，AI 必须先完成这些判断，再回答或行动：

1. 把用户请求转成成功标准和待回答的关键问题。
2. 确定需要哪些认知面：目标需求、当前实现、验证证据、运行事实、历史理由、影响边界。
3. 从项目认知入口和底层实物加载最小充分证据；索引只负责定位，不能替代原始证据。
4. 对关键结论检查来源、时效、冲突和未知项，不能把“没看到”写成“不存在”。
5. 能说明已经知道什么、依据是什么、还不知道什么，以及未知是否影响结论。
6. 认知闭包足够后才开始解决问题；若仍缺关键材料，就继续调查、降低结论强度或向用户说明阻塞。

认知闭包是“相对于当前任务的最小充分闭包”，不是全文读取整个 repo。全面意味着关键认知面
没有缺口，不意味着无差别加载所有文件。

### 与治理 Skill 的先后关系

`repo-cognitive-closure` 负责工作开始前和回答前的“读取侧”：建立这次任务所需认知。
`repo-cognition-governance` 负责产生持久变化时的“维护侧”：把新需求、稳定结论、资产入口、
工作记忆和废弃关系落回正确位置。

若两个 Skill 同时触发，顺序必须是：先完整加载并执行认知闭包 Skill；确认任务影响到需求、
文档、索引、记忆或交接后，再完整加载并执行治理 Skill。两者都不能扩大用户授权。

### 用户显式发起可审计认知闭包时

当用户调用 `$auditable-cognitive-closure`，或明确要求“制作/落盘一份可审计认知闭包”时，
必须完整读取并遵守：

`/Users/aurolafly/.codex/skills/auditable-cognitive-closure/SKILL.md`

这个显式 Skill 会把本次任务的认知闭包外化为 repo 中 `认知闭包/` 下的 Markdown 文件，
记录 URL、文件 PATH、Git commit、命令、运行实物、主张—证据映射、冲突和未知项，并更新
根 `README.md` 与 `MEMORY.md` 的索引。调用它只授权创建或更新闭包文件及必要索引，不自动
授权修改业务代码、外部系统或发布内容。

8. 用户明确追问“除了代码还要维护什么”“这个要求记录在哪里”“下一个 AI 如何接手”
   “你是否加载了足够认知”等项目治理问题。

如果不确定当前任务是否触发，应当加载，而不是以“不想增加流程”为由跳过。

### 加载后的强制行为

完整读取 Skill 后，至少要落实其中这些行为：

1. 先确认当前用户指令、项目 `AGENTS.md` 和各类项目资产的权威边界。
2. 在实现前区分：用户已确认需求、讨论中想法、AI 候选建议、实现方案和暂时参数。
3. 从 README/Feature/MEMORY/稳定文档/代码/测试/运行现场中加载当前组件的最小充分
   认知包；索引和摘要不能替代决定结论的底层证据。
4. 结束前执行仓库影响检查，逐项判断需求、代码测试、配置数据、运维、稳定文档、
   README、MEMORY 和历史/废弃入口是否真实发生变化。
5. 一类事实只维护一个当前真值源，其他地方只放指针；不得制造多份需要人工同步的
   “当前状态”。
6. 全面检查不等于机械修改所有文件；没有发生事实变化的职责文件不要动。
7. 不默认建设 checkpoint-per-requirement、全函数 trace、view 数据库、工作包体系、
   文档状态机、Gate、审计 AI 或每 Session 一份新交接文档。
8. 用测试、运行实物或可复现检查区分“写入文档”“已经实现”和“已经验证”。

- 用户当前明确指令和更具体的项目 `AGENTS.md` 优先；Skill 不得扩大写入、外部操作、

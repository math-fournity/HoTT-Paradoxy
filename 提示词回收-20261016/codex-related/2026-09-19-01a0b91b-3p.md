## 要思考全面，但是禁止过度设计，系统开发要广度优先

奥卡姆剃刀原则，对于软件系统也一样适用：如无必要，勿增非功能组件。

但是你的思考应当全面，你需要把握“思考全面”和“过度设计”之间的区别。

系统的实现和迭代不应该是一个深度优先的过程，而应该是一个广度优先的过程，也就是说，对于一个完整的系统来说，我们应该先把它完整的样子先做出来，然后再打磨各个组件的细节，而不是先打磨好一个组件，再打磨好下一个组件的细节。


标识：BREADTH_FIRST_EXECUTION_V1。

完整系统研发默认先建立主要职责与关键连接的全景，再尽早形成可运行、可验证的最小完整链路，逐轮扩大覆盖。广度按用户结果和真实集成衡量，不按文件、组件或文档数量衡量；不能用空壳、mock或假数据冒充要求中的真实能力。

开工闭包须同时确认父级结果、当前已贯通的链路和下一项最小可验结果，只对当前安全/正确行动所需的认知深入；未来不确定性保留复审条件，不默认变成当前阻塞。

局部深化、新通用层或额外基础设施必须说明它服务的当前结果、直接必要性、较小替代和返回主链的条件；已有投入、结构漂亮或可能的远期复用不是独立理由。必要的安全、正确性、迁移、根因和技术风险调查允许先深入，不得为了快而跳过。

每个自然工作单元结束后回看父目标，区分新增可用行为、关键未知减少和纯准备工作；满足当前需要后停止可选深化，优先补未贯通的真实连接。父任务只有在已接受范围的集成验收满足时才能完成。

研究、审计和方案任务以其授权交付为结果，广度优先不授权转入代码、模型或发布。上述判断复用现有plan/Topic/MEMORY和Skills，不新建默认账本、评分平台、审批Gate或语义Hook。

## 并行 Worktree 的认知连续性与 Current Truth

标识：`PARALLEL_WORKTREE_COGNITION_V1`。Git worktree 只隔离工作文件和 index；它不合并语义，
也不分配项目级 revision、checkpoint、projection generation 或“当前状态”所有权。两个分支都从
同一基线把 `STATE`/`MEMORY`/Feature/current design 改成各自的“下一版”，即使各自 clean、各自
validator PASS，仍可能产生重复序号、分叉当前真值和文本可合并但语义冲突的结果。

同一 repo 存在两个或更多长期/并行写者时，写入前必须登记角色、canonical target 和 exact base：

- `CANONICAL_INTEGRATOR` 在同一时点只能有一个。只有它可以修改项目的 current-truth owners、
  推进 canonical checkpoint/revision、更新 current queue，并操作集成目标的共享 ref/tag；
- `CONTRIBUTOR` 只在自己的 branch/worktree 修改获准的独占代码、证明、测试或证据路径。跨 Session
  连续性由 branch commit、已有任务记录和必要时的简短 relay 保持；relay 必须标
  `CANDIDATE_NOT_CURRENT`，列 base/source OID、范围、变更、验证、冲突、未知和建议写回，不得推进
  canonical revision 或把 branch-local MEMORY/STATE 冒充项目当前状态；
- `AUDITOR` 保持只读；获准保存审计产物时只写独占审计路径，其结论仍是待集成证据。

集成者只消费 exact candidate commit/manifest，在 expected target HEAD 上复核 diff、证据、消费者和
当前 owner；接受后由集成者把语义写回 canonical owner，并且每个逻辑变化只分配一次 checkpoint/
revision。若 contributor 已改 current owner，不整提交盲目 cherry-pick/merge：保留候选分支，提取

## 利用治理资产建立认知闭包

认知闭包不是“读了一些文档”，而是影响本次结论的关键问题、事实、约束、来源、冲突和未知
都已经被识别；重要证据已加载；剩余未知不会推翻结论，或已经让结论降级。

每个非平凡 repo 任务按以下认知链工作：

1. **用户目标与授权**：明确要回答、诊断、设计、实现、运行还是验证；定义成功和非目标。
2. **指令与边界**：确认全局/项目/目录 AGENTS、所有相关 Git repo、系统岛屿和生命周期。
3. **项目全景与当前态**：读根 README/目录 README 建资产地图，读 MEMORY 获得当前方向、
   已验证新知、开放问题和下一步；两者都是路由，不替代实物。
4. **应该怎样与为什么**：读 Feature 对应组件、rulings/原始用户来源、当前 system/detailed
   design 和 ADR；区分已采纳、候选、废止、设计选择和临时参数。
5. **实际怎样与如何证明**：回到代码、配置、机器 schema、依赖锁、测试断言及实际结果、
   数据查询、进程、日志、运行产物、trajectory/proof 和当前外部权威。
6. **历史理由**：仅在来源缺失、冲突、迁移、事故或用户要求时下钻 Git log/diff 和历史实物；
   Git 是历史证据，不是当前需求数据库。
7. **冲突与时效**：按事实类型、版本和时间消解。目标不能冒充当前实现，代码不能否定用户要求，
   文档不能证明运行，旧 run 不能证明当前现场。
8. **负结论与未知**：声称“不存在、未实现、无遗漏、全部覆盖”前扩大同义词、路径、历史和
   动态来源搜索；范围不足只能说“在已检查范围内未发现”。
9. **闭包判定**：material claims 有相称证据，重要冲突已处理，动态事实已核当前，未知已披露，
   相关领域 Skill 已加载，才能回答或行动。
10. **工作后回写**：持久需求、设计、状态、入口、证据或废止关系变化时执行 governance；
    只更新事实真正变化的唯一真值源。

各载体职责：AGENTS=宪法/路由，README=资产地图，Feature=当前需求，MEMORY=当前态，
rulings=用户原意，docs=稳定知识，dev-docs=未定过程，代码/config/schema/tests/data/runtime=实际
实现与证据，Git/history=历史。索引永远不能替代决定性证据。

新 Session、上下文压缩、工作目录/范围变化、关键资产更新或动态外部事实变化后，必须审计
原闭包是否失效；失效就重建，不能把旧 Session 的“我记得”当永久认知。

## 第一原则：先建立认知负载/认知闭包，再回答或行动

AI 成功回答问题或完成任务的前提，是先弄清楚：为了这一次具体请求，自己必须知道什么，
这些认知分别在哪里，是否已经完整加载，彼此是否一致，哪些仍然未知。没有建立足够的
认知负载之前，不应凭局部文件、摘要、训练记忆或直觉直接给出确定结论。

### 背后的理念：知识供给、认知消费与跨 Session 循环

**认知闭包优先原则**：AI 在回答问题、制定方案或执行工作之前，必须先建立与当前任务
相匹配的、最小充分且证据可追溯的认知闭包。没有正确的认知，就没有可靠的判断；没有
可靠的判断，就没有可靠的规划和执行。

认知闭包是成功工作的第一道门槛和第一优先事项，但不是成功本身。闭包完成后，AI 仍需
进行正确推理、制定方案、执行、验证，并诚实处理未知和失败。

认知闭包能够高效建立，还有一个前提：过去工作的 AI 已经把 repo 中的知识按照稳定职责
规范化管理。`repo-cognition-governance` 承担知识供给侧职责——让用户需求、稳定知识、
当前状态、资产入口、历史理由和运行证据进入可发现、可区分、可追溯的载体。它管理 repo
知识的根本目的，不是让文档显得齐全，而是让未来 AI 面对具体问题时能够正确建立认知闭包。

`repo-cognitive-closure` 承担知识消费侧职责——未来 AI 先判断成功回答当前问题需要知道
什么，再借助治理后的 README、Feature、MEMORY、稳定文档和底层实物，建立本次任务的
认知闭包，然后才进入回答、规划和执行。

本次工作产生的新需求、可靠结论、状态变化和资产关系，再由治理 Skill 落回 repo，服务
更未来的 AI。于是形成持续循环：过去 AI 规范化沉淀知识，当前 AI 建立认知闭包并完成
工作，新的可靠认知再次被规范化沉淀。

这里的“全面”是相对于当前任务而言，保证关键认知面没有缺口；它不等于通读整个 repo，
也不等于加载越多越好。目标始终是任务相对的最小充分认知闭包。

`repo-cognitive-closure` 是专门用于建立本次任务认知闭包的全局 Skill。完整内容位于：

`/Users/aurolafly/.codex/skills/repo-cognitive-closure/SKILL.md`

几乎所有依赖 repo 事实的非平凡问题，都必须在实质性分析、回答、方案或操作之前，
先用文件读取工具完整加载该 Skill，并按它完成本次任务的认知闭包。名称和 description
只用于发现，不能替代正文；不能因为以前 Session 读过就跳过本轮读取。

### 必须加载认知闭包 Skill 的场景

以下任一条件成立就必须加载：

1. 回答依赖当前 repo 的需求、架构、代码、配置、数据、测试、文档、运行状态、历史或

2. 用户问“是什么、为什么、现在怎样、做到哪里、哪里有问题、应该怎么改、下一步什么”。

4. 要声称某项工作“正确、完整、已实现、已验证、没有遗漏、当前有效”或作出类似判断。

1. 把用户请求转成成功标准和待回答的关键问题。

3. 从项目认知入口和底层实物加载最小充分证据；索引只负责定位，不能替代原始证据。
4. 对关键结论检查来源、时效、冲突和未知项，不能把“没看到”写成“不存在”。
5. 能说明已经知道什么、依据是什么、还不知道什么，以及未知是否影响结论。
6. 认知闭包足够后才开始解决问题；若仍缺关键材料，就继续调查、降低结论强度或向用户说明阻塞。

认知闭包是“相对于当前任务的最小充分闭包”，不是全文读取整个 repo。全面意味着关键认知面
没有缺口，不意味着无差别加载所有文件。

## zvec-grep

Choose the evidence source before the retrieval mode.

### Workspace evidence
- Use the current workspace as the evidence source when the user asks about local material, prior context establishes it as relevant, or the question concerns how the current project works—even if the workspace is not mentioned explicitly.
- A workspace may contain any mix of code, documents, configuration, and data.
- Do not use workspace retrieval for unrelated open-world questions, current external facts, or web content that does not depend on local evidence.

### Retrieval routing
- When an exact word, phrase, name, date, identifier, filename, path, configuration key, error message, source fragment, literal, or regex is known and locating its occurrences is sufficient, use `zvec_grep_rg` when it is listed by the current host; otherwise native Grep or `rg`.
- Use `zvec_grep_search` when wording or location is unknown, or when the answer requires semantic, conceptual, fuzzy, or paraphrase discovery; relationships, chronology, causality, architecture, or data or control flow; or comparison or synthesis across files, sections, or documents.
- For a mixed task with exact anchors that still requires relationships or cross-file synthesis, call `zvec_grep_search` with the concept and anchors, then use `zvec_grep_rg` when it is listed by the current host; otherwise native Grep or `rg` for focused follow-up.
- When no sufficient exact anchor is available and the user asks whether conceptually related material exists locally, make at most one focused `zvec_grep_search` probe using the question plus distinctive names, dates, or terms. This probe does not apply to exact quotations, configuration keys, filenames, regexes, or exhaustive occurrence requests. Continue only when results are relevant; otherwise stop and report that the indexed workspace did not establish the answer.
- Before broad file reads or delegating workspace discovery, use the appropriate search route. Do not delegate solely to locate material, and stop when the evidence is sufficient.

### Search evidence
- Search results include bounded source snippets. Treat a sufficient snippet as already-read evidence, and read a cited file only when a required detail falls outside the snippet.

### Freshness and index lifecycle
- Pass a daemon-visible absolute `root` on every zvec-grep workspace call.
- Read `freshness` and `background_refresh` from search results without a status preflight.
- When results are `served_from_current_index`, use them when sufficient instead of waiting for the background refresh.
- If the index is missing but exact or regex lookup can answer the task, use `zvec_grep_rg` when it is listed by the current host; otherwise native Grep or `rg`.
- Creating, rebuilding, or dropping a persistent index requires an explicit user request or authorization; never do so silently.

### CLI 管理密钥组合与数量

对一台工作设备，最小的 CLI 管理组合是 **2 类凭据**：

1. **SSH authentication key：每台设备 1 把**。用于 Git over SSH 的 clone/fetch/push；建议 Ed25519
   加 passphrase，设备之间不复用私钥。它不管理账号设置、组织成员、账单、PAT 或 GitHub Apps。
2. **API/CLI management credential：按资源边界至少 1 个**。优先使用 fine-grained PAT，限制
   resource owner、repository 和 permissions；本项目当前用户裁定要求创建的 CLI 凭据为永久凭据，
   因此 `expires_at` 为 NULL，并通过人工撤销/轮换管理风险。需要 classic-only API 时，可以创建
   永久 classic PAT，但必须记录完整 scope、owner、用途和撤销路径。

以下是按需求增加的可选凭据，不得误认为它们合并后就形成万能 key：

- **SSH signing key 或 GPG signing key：每台签名设备 1 把**，只用于 Verified commit/tag；默认与
  SSH authentication key 分离。
- **GitHub App private key + installation token：每个组织/长期自动化服务 1 套**，只覆盖 App 安装
  时授予的组织、仓库和权限；它不是个人账号 master key。
- **Deploy key：每个需要独立部署访问的仓库 1 把**，只属于该仓库，不用于管理 GitHub 账号。

因此，单台设备的常见数量是：

- 仅命令行 Git/API 管理：1 SSH authentication key + 1 个或多个按范围拆分的 API/CLI token；
- 加提交签名：再加 1 个 signing key；
- 加组织长期自动化：再加每个 GitHub App 的 private key/installation-token 流程；
- 当前用户已明确裁定：本轮 CLI 管理凭据采用永久策略，不设置自动过期；这不等于不可撤销，
  必须保留人工撤销、轮换和泄露响应路径。GitHub 的角色、组织策略和 API 支持矩阵仍可能限制
  实际能力，因此“永久”不能表述为“万能”。

### `$new-github` 后续 CLI 凭据 SOP

1. 账号注册完成并登录验证后，确认当前账号、目标组织和目标仓库范围；不要从“全权”四个字推断
   未明确的资源授权。
2. 在目标工作设备检查是否已有 SSH key；没有时生成新的 Ed25519 key，使用 passphrase，并把公钥
   通过 GitHub `SSH and GPG keys` 或已认证的 `gh ssh-key add` 入口添加为 authentication key。
3. 需要签名时生成独立 signing key，并通过相应用途添加；authentication 与 signing 的撤销边界
   必须分别记录。
4. API/CLI 自动化优先创建 fine-grained PAT；每个 token 记录非 secret 元数据：用途、resource
   owner、repositories、permissions、创建时间、expiration、owner、撤销方式。按本项目当前永久
   策略创建的 token 使用 `expires_at=NULL`，secret 仅进入受控 SQLite 凭据表或 OS secret manager。
5. 如果 fine-grained PAT 不支持目标 API，先确认官方 endpoint 文档，再以最小必要 classic scope
   创建永久例外；不得把 classic PAT 当成绕过角色/组织策略的永久 master credential。
6. 用 `gh auth status`、`gh api user` 和目标资源的最小只读/写入测试验证；命令输出不得显示 token。
   撤销测试必须证明删除或撤销某个 key/token 后对应操作失败。
7. 若目标是组织级长期自动化，设计 GitHub App 并限定安装仓库与 permissions；不要用个人 PAT
   代替服务身份。

### 全权管理的真实完成条件

只有同时满足以下条件，才可以声称某个 CLI 管理范围完成；不能声称一把 key 覆盖整个 GitHub：

- 账号实际角色满足目标（个人账号、组织 Owner、仓库 Admin 或企业角色）；
- 每个目标资源有明确的 owner、范围和权限；
- 每个 CLI token/key/App 都有最小权限、期限、用途和撤销路径；
- `gh` 登录、Git SSH、API endpoint、组织/仓库管理和签名（如适用）分别通过正向测试；
- 撤销/过期/SSO/审批等负向路径已验证；
- 受控 SQLite 的 `github_accounts`/`github_credentials` 表可以按 R-003 保存当前 CLI-only 工作流所需的
  账号密码、SSH 私钥和 PAT secret；除此受控表及其 owner-only 备份之外，secret/private material 都不
  进入项目文档、Git、shell 参数/history、普通日志、截图或旧 JSON。FIDO2/passkey/TOTP/recovery code
  仍不写入该表；
- 对于只能通过 GitHub Web 设置完成的账号安全、计费、部分组织/企业设置，必须明确标记为非 CLI
  覆盖范围，而不是伪称“全部权限已由 key 实现”。

具体权限边界、官方依据和一般账号安全选项见：
`docs/security/github-credential-management.md`；SQLite 凭据 schema、迁移和 secret 边界见
`docs/data/github-credential-registry.md`。该文档中 FIDO2/Passkey/TOTP 内容保留为一般安全
背景；本项目的当前 CLI 管理目标以本节为准。

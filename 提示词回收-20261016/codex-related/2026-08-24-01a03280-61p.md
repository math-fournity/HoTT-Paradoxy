### 背后的理念：知识供给、认知消费与跨 Session 循环

**认知闭包优先原则**：AI 在回答问题、制定方案或执行工作之前，必须先建立与当前任务

可靠的判断，就没有可靠的规划和执行。

认知闭包是成功工作的第一道门槛和第一优先事项，但不是成功本身。闭包完成后，AI 仍需
进行正确推理、制定方案、执行、验证，并诚实处理未知和失败。

认知闭包能够高效建立，还有一个前提：过去工作的 AI 已经把 repo 中的知识按照稳定职责

`repo-cognitive-closure` 承担知识消费侧职责——未来 AI 先判断成功回答当前问题需要知道

## 系统架构概要

### 当前主线：MATH-MINING · 数学证明对话录挖掘

> 详细架构演进与决策记录：`dev-notes/MATH-MINING/EXECUTOR-SWITCH-opencode-acp.md`（真理源）

**目标**：对 `AI-ALL-Markdown/` 全部 2093 个对话录做 Pass 1 分析，每份产出双 JSON——`results/{fid}.rounds.json`（逐轮问答摘要）+ `results/{fid}.proofs.json`（文件级判定 + 证明清单，带行号可反查）。

**架构**：编排器 + opencode ACP 执行器 + Redis 任务队列 + SQLite 密钥池

```
orchestrator.py (v6, tmux, 可重启)
  ├─ Redis: mathmining:queue (LIST, 待分配) → mathmining:inflight (ZSET, 租约)
  ├─ key-pool.sqlite: api_keys 主表 + 每钥专属并发表 (max_conc≤2)
  ├─ ThreadPoolExecutor (ceiling=128, 实际并发=min(30, Σ max_conc))
  │   └─ 每文件: acquire key → setup workdir → spawn acp_proxy.py → validate → release
  ├─ acp_proxy.py (每文件独立, setsid脱离父进程组, orchestrator重启不杀)
  │   ├─ 本地模式: opencode acp (proxy的子进程, Unix socket双向转发JSON-RPC)
  │   ├─ Docker模式(--use-docker): docker_pool 取容器 → docker exec -i opencode acp
  │   ├─ 控制客户端 (orchestrator, 第一个连接, 收response+notification, 可发请求)
  │   └─ 观察客户端 (monitor, 后续连接, 只收notification广播, 只读)
  ├─ docker_pool.py (Docker模式, 后台持续构建10个ready容器, 用完即弃)
  │   ├─ opencode-base:arm64 镜像 (Alpine + opencode linux-arm64-musl, 278MB)
  │   ├─ opencode-ready-{N} (池中待启动容器, 挂载auth.json+work/)
  │   └─ opencode-run-{fid} (运行中容器, 用完后docker rm -f)
  ├─ /tmp/mathmining-sock/{fid}.sock (Unix socket) + {fid}.sock.state.json (状态文件)
  ├─ results/{fid}.rounds.json + {fid}.proofs.json (ingest.py 写入)
  ├─ ledger.json (全文件状态: completed/pending/running/dead)
  └─ dead-letter/{fid}.json (3次重试失败的文件)
```

**进程隔离架构（方案A）**：orchestrator 重启不杀 acp。每文件 spawn 独立的 acp_proxy.py（setsid 脱离父进程组），proxy 管理 opencode acp 子进程并通过 Unix socket 对 orchestrator 透明转发。orchestrator 重启后扫描 `/tmp/mathmining-sock/*.sock`，读状态文件恢复 session_id/counts，重新连接接管。

**Docker 隔离模式（`--use-docker`）**：每个 acp 跑在全新 Docker 容器中，用完即弃。后台 `docker_pool.py` 持续构建 10 个 ready-for-run 容器（Alpine + opencode 二进制），proxy 启动时从池取一个容器，`docker exec -i` 启动 acp，用完后 `docker rm -f` 删除容器。每个 acp 实例认为自己在一个全新的机器中。容器挂载 `auth.json`（ro）+ `work/` 目录（rw）。不加 `--use-docker` 则用本地模式（直接 spawn opencode acp 子进程），完全向后兼容。

**多客户端模型**：proxy 支持多个客户端同时连接，分两种角色：
- **控制客户端**（orchestrator）— 第一个连接，可发 JSON-RPC request（有 id），收对应 response；notification 也收到。断开后下一个新连接成为控制客户端（重连场景）。
- **观察客户端**（monitor）— 后续连接，只收 notification 广播（session/update），不发请求，不收 response。可同时多个。
- **路由规则**：response（有 id）只发给控制客户端；notification（有 method 无 id）广播给所有客户端；server request（如 request_permission）只发给控制客户端。观察客户端发来的消息被忽略（只读）。
- **用途**：monitor 客户端可以实时观察 acp 的工作流程（thought/message/tool_call 流），不影响 orchestrator 的控制。

**优雅停机（STOP 文件）的含义**：
1. `touch STOP` → orchestrator 停止从 Redis 队列取新文件
2. 在跑的任务继续直到完成（`process_file` 循环检查 STOP 后返回 `stopped`）
3. 所有在跑任务完成后 orchestrator 退出，日志出现 `STOP 生效且已排空，退出`
4. proxy+acp 在 `acp_client._finish()` 中收到 `session/cancel` + `session/close` 后自然退出
5. **STOP 不会杀 proxy+acp**——它们等 acp 自然结束或 orchestrator 通过 socket 发 cancel 后退出

**强制完全停机的必要性**：紧急情况（如密钥全部失效、磁盘满）下需要立即停止一切。此时必须按顺序杀三层进程（orchestrator → proxy → acp），并清理 socket 文件。**漏杀 proxy 会导致僵尸 proxy 继续占用密钥槽位**。

**持久化设计**：
- **ledger.json 是真理源**：文件级状态（completed/pending/running/dead），JSON 文件持久化在磁盘，计算机重启不丢
- **Redis 是运行时加速**：queue（待分配 LIST）+ inflight（租约 ZSET），重启可能丢失
- **orchestrator 每次启动从 ledger 重建 Redis 队列**：幂等操作，`redis_rebuild.py` 是手动版本
- **SQLite 密钥池持久化**：key-pool.sqlite 在磁盘，重启不丢。但 running 标记需清理：`KP.startup_recovery()` 在 orchestrator 启动时自动执行

## 第一原则：先建立认知负载/认知闭包，再回答或行动

AI 成功回答问题或完成任务的前提，是先弄清楚：为了这一次具体请求，自己必须知道什么，
这些认知分别在哪里，是否已经完整加载，彼此是否一致，哪些仍然未知。没有建立足够的
认知负载之前，不应凭局部文件、摘要、训练记忆或直觉直接给出确定结论。

### 背后的理念：知识供给、认知消费与跨 Session 循环

**认知闭包优先原则**：AI 在回答问题、制定方案或执行工作之前，必须先建立与当前任务
相匹配的、最小充分且证据可追溯的认知闭包。没有正确的认知，就没有可靠的判断；没有
可靠的判断，就没有可靠的规划和执行。

认知闭包是成功工作的第一道门槛和第一优先事项，但不是成功本身。闭包完成后，AI 仍需
进行正确推理、制定方案、执行、验证，并诚实处理未知和失败。

认知闭包能够高效建立，还有一个前提：过去工作的 AI 已经把 repo 中的知识按照稳定职责
规范化管理。`repo-cognition-governance` 承担知识供给侧职责——让用户需求、稳定知识、
当前状态、资产入口、历史理由和运行证据进入可发现、可区分、可追溯的载体。它管理 repo
知识的根本目的，不是让文档显得齐全，而是让未来 AI 面对具体问题时能够正确建立认知闭包。

`repo-cognitive-closure` 承担知识消费侧职责——未来 AI 先判断成功回答当前问题需要知道
什么，再借助治理后的 README、Feature、MEMORY、稳定文档和底层实物，建立本次任务的
认知闭包，然后才进入回答、规划和执行。

本次工作产生的新需求、可靠结论、状态变化和资产关系，再由治理 Skill 落回 repo，服务
更未来的 AI。于是形成持续循环：过去 AI 规范化沉淀知识，当前 AI 建立认知闭包并完成
工作，新的可靠认知再次被规范化沉淀。

这里的“全面”是相对于当前任务而言，保证关键认知面没有缺口；它不等于通读整个 repo，
也不等于加载越多越好。目标始终是任务相对的最小充分认知闭包。

### 当前主线：MATH-MINING · 数学证明对话录挖掘

**目标**：对 `AI-ALL-Markdown/` 全部 2093 个对话录做 Pass 1 分析，每份产出双 JSON——`results/{fid}.rounds.json`（逐轮问答摘要）+ `results/{fid}.proofs.json`（文件级判定 + 证明清单，带行号可反查）。

**架构**：编排器 + opencode ACP 执行器 + Redis 任务队列 + SQLite 密钥池

```
orchestrator.py (v6, tmux, 可重启)
  ├─ Redis: mathmining:queue (LIST, 待分配) → mathmining:inflight (ZSET, 租约)
  ├─ key-pool.sqlite: api_keys 主表 + 每钥专属并发表 (max_conc≤2)
  ├─ ThreadPoolExecutor (ceiling=128, 实际并发=min(30, Σ max_conc))
  │   └─ 每文件: acquire key → setup workdir → spawn acp_proxy.py → validate → release
  ├─ acp_proxy.py (每文件独立, setsid脱离父进程组, orchestrator重启不杀)
  │   ├─ 本地模式: opencode acp (proxy的子进程, Unix socket双向转发JSON-RPC)
  │   ├─ Docker模式(--use-docker): docker_pool 取容器 → docker exec -i opencode acp
  │   ├─ 控制客户端 (orchestrator, 第一个连接, 收response+notification, 可发请求)
  │   └─ 观察客户端 (monitor, 后续连接, 只收notification广播, 只读)
  ├─ docker_pool.py (Docker模式, 后台持续构建10个ready容器, 用完即弃)
  │   ├─ opencode-base:arm64 镜像 (Alpine + opencode linux-arm64-musl, 278MB)
  │   ├─ opencode-ready-{N} (池中待启动容器, 挂载auth.json+work/)
  │   └─ opencode-run-{fid} (运行中容器, 用完后docker rm -f)
  ├─ /tmp/mathmining-sock/{fid}.sock (Unix socket) + {fid}.sock.state.json (状态文件)
  ├─ results/{fid}.rounds.json + {fid}.proofs.json (ingest.py 写入)
  ├─ ledger.json (全文件状态: completed/pending/running/dead)
  └─ dead-letter/{fid}.json (3次重试失败的文件)
```

**进程隔离架构（方案A）**：orchestrator 重启不杀 acp。每文件 spawn 独立的 acp_proxy.py（setsid 脱离父进程组），proxy 管理 opencode acp 子进程并通过 Unix socket 对 orchestrator 透明转发。orchestrator 重启后扫描 `/tmp/mathmining-sock/*.sock`，读状态文件恢复 session_id/counts，重新连接接管。

**Docker 隔离模式（`--use-docker`）**：每个 acp 跑在全新 Docker 容器中，用完即弃。后台 `docker_pool.py` 持续构建 10 个 ready-for-run 容器（Alpine + opencode 二进制），proxy 启动时从池取一个容器，`docker exec -i` 启动 acp，用完后 `docker rm -f` 删除容器。每个 acp 实例认为自己在一个全新的机器中。容器挂载 `auth.json`（ro）+ `work/` 目录（rw）。不加 `--use-docker` 则用本地模式（直接 spawn opencode acp 子进程），完全向后兼容。

**多客户端模型**：proxy 支持多个客户端同时连接，分两种角色：
- **控制客户端**（orchestrator）— 第一个连接，可发 JSON-RPC request（有 id），收对应 response；notification 也收到。断开后下一个新连接成为控制客户端（重连场景）。
- **观察客户端**（monitor）— 后续连接，只收 notification 广播（session/update），不发请求，不收 response。可同时多个。
- **路由规则**：response（有 id）只发给控制客户端；notification（有 method 无 id）广播给所有客户端；server request（如 request_permission）只发给控制客户端。观察客户端发来的消息被忽略（只读）。
- **用途**：monitor 客户端可以实时观察 acp 的工作流程（thought/message/tool_call 流），不影响 orchestrator 的控制。

**优雅停机（STOP 文件）的含义**：
1. `touch STOP` → orchestrator 停止从 Redis 队列取新文件
2. 在跑的任务继续直到完成（`process_file` 循环检查 STOP 后返回 `stopped`）
3. 所有在跑任务完成后 orchestrator 退出，日志出现 `STOP 生效且已排空，退出`
4. proxy+acp 在 `acp_client._finish()` 中收到 `session/cancel` + `session/close` 后自然退出
5. **STOP 不会杀 proxy+acp**——它们等 acp 自然结束或 orchestrator 通过 socket 发 cancel 后退出

**强制完全停机的必要性**：紧急情况（如密钥全部失效、磁盘满）下需要立即停止一切。此时必须按顺序杀三层进程（orchestrator → proxy → acp），并清理 socket 文件。**漏杀 proxy 会导致僵尸 proxy 继续占用密钥槽位**。

**强制停机后的数据修复**（必须执行，否则下次启动会出错）：
```bash
# 1. 修复 ledger：running → pending（被强制杀的 acp 没有完成）
python3 dev-notes/MATH-MINING/pass1/scripts/redis_rebuild.py --fix-running --clean
# 2. 这会同时重建 Redis 队列（从 ledger 真理源）
# 3. 然后正常启动 orchestrator
```

**计算机重启后的恢复**（Redis 数据丢失，从 ledger 重建）：

**持久化设计**：
- **ledger.json 是真理源**：文件级状态（completed/pending/running/dead），JSON 文件持久化在磁盘，计算机重启不丢
- **Redis 是运行时加速**：queue（待分配 LIST）+ inflight（租约 ZSET），重启可能丢失
- **orchestrator 每次启动从 ledger 重建 Redis 队列**：幂等操作，`redis_rebuild.py` 是手动版本
- **SQLite 密钥池持久化**：key-pool.sqlite 在磁盘，重启不丢。但 running 标记需清理：`KP.startup_recovery()` 在 orchestrator 启动时自动执行

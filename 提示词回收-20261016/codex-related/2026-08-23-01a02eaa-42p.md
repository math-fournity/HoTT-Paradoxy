**针对 Linux Kernel 这种规模的复杂工程 repo（百万行级、数万文件、深层依赖、长期演进、子系统众多），重点不是简单的 skill 或通用 AGENTS.md，而是“结构化上下文基础设施 + 语义导航 + 分层/多 agent 治理”。**

单纯靠一个大 prompt 或扁平 skills，在 400k+ LOC 以上就会系统性失败（上下文爆炸、找错文件、局部修改、依赖丢失）。社区和论文里针对这种规模的实践，核心是把“长期软件工程实践”编码成**可导航、可分层、可持久的机器可读基础设施**。

### 1. 最贴合的：Codified Context Infrastructure（复杂 codebase 专用）

**GitHub**：[https://github.com/arisvas4/codified-context-infrastructure](https://github.com/arisvas4/codified-context-infrastructure)\
（配套论文 arXiv:2602.20478，作者用它在 108k 行 C# 分布式系统上跑了 283 个 session，知识/代码比约 24%）

三层架构，专为大规模长期维护设计：

- **Tier 1 Hot Memory（Constitution）**：类似超级 AGENTS.md，始终加载的全局公约（约定、触发表、路由协议、检查清单）。约几百行，控制一切。
- **Tier 2 Specialized Domain Agents**：19+ 个子系统专家 agent（网络、调试、架构等），每个嵌入本领域知识 + 行为规范。任务触发时自动路由。
- **Tier 3 Cold Memory（Knowledge Base）**：34+ 份按需加载的规格文档（子系统设计、历史决策、失败模式），通过 MCP 或检索暴露。

这正是“让 AI 懂长期实践”的核心：不是一次性 prompt，而是把 repo 的演进历史、边界、架构决策固化成 agent 可依赖的基础设施。可直接扩展到 Kernel 式子系统划分（arch、drivers、mm、net 等）。

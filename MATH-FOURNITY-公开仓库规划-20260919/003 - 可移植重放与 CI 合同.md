# 可移植重放与 CI 合同

## 1. 不能直接重用当前 `command_argv`

现有收据中的 `command_argv` 和 `compile.sh` 指向本机绝对路径，例如 `/Volumes/D/HoTT-toolchain-cache/...` 与 `/Volumes/D/HoTT_AI_HANDOFF_20260911/...`。它们是原项目证据，必须原样保留；但不能被当成 GitHub Actions 的可执行合同。

公开包必须新增一个以仓库相对路径工作的 replay runner。它不修改历史收据，而是读取 manifest、解析每个单位的公共源/依赖、建立受控工具链环境并产生新的 `portable-replay-receipt`。

## 2. Replay runner v1 合同

计划中的入口：

```text
python3 tools/replay_release.py --manifest release/release-manifest-v1.json
python3 tools/replay_release.py --manifest release/release-manifest-v1.json --unit R08-REAL-LAYER-SUFFICIENCY
```

Runner 的职责：

1. 校验 manifest schema、source commit/tree、每个公开文件 hash、run ID 与公开 claim 映射；
2. 从 release-local 的 toolchain descriptor 取得精确 Agda/Cubical 版本和下载/校验信息，不读取开发机绝对路径；
3. 在 `$RELEASE_ROOT` 与 `$TOOLCHAIN_ROOT` 下执行相对路径命令；
4. 对每个单位比对声明的 exit class、stdout/stderr 的**规范化** hash 与源/依赖 hash；
5. 产生机器可读 summary：`PASS`、`EXPECTED_NEGATIVE_PASS`、`MANIFEST_INVALID`、`TOOLCHAIN_UNAVAILABLE`、`SOURCE_DRIFT` 或 `REPLAY_MISMATCH`；
6. 默认失败关闭：未知文件、绝对开发机路径、缺少 hash、没有处置的 run 或不匹配的预期结果一律 non-zero 退出。

输出路径不同会使原始诊断文本包含不同绝对路径时，runner 的 hash 合同必须采用**声明的路径规范化**：只替换 manifest 指定的 source root 和 toolchain root 为稳定标记，其他字节不改。原始历史 stdout/stderr 仍随原收据保存；公开 replay receipt 明确标为 `NORMALIZED_PORTABLE_REPLAY`，不得冒充旧运行的 raw byte identity。

## 3. CI 的最小路径

`.github/workflows/replay.yml` 只有在下列本地验收通过后才创建：

1. 在与原工作区不同的临时目录完成 release runner 全量 replay；
2. 再在没有开发机绝对路径、没有私有缓存/凭据的干净环境完成同一 replay；
3. manifest validator、provenance validator、reader-content allowlist 检查均通过；
4. 每个 `EXPECTED_NEGATIVE_CONTROL` 都被显式断言为预期行为，不能因为非零 exit 使 CI 误报，也不能被当作普通 green proof；
5. CI summary 只显示公开单位、版本和结论，不上传完整私有日志、用户内容或未公开的失败轨迹。

在此之前，README 不能承诺“bit-for-bit CI replay”。更准确的临时表述是“公开 release manifest 仍在构建，尚未提供独立 CI replay”。

## 4. 可恢复性与安全

失败不自动删除历史收据或重写 manifest。若工具链下载、hash、许可证清单或任一 unit replay 失败，发布包保持 `NOT_RELEASE_READY`，并保留失败 locator。Runner 不读取 `~/.ssh`、GitHub token、`private-audit/` 或任何用户对话；CI 没有 push、release 或 secrets 写入权限。

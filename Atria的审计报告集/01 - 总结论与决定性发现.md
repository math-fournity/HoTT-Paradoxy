# 01 - 总结论与决定性发现

## 0. 总裁决

**机器统观项目在证据纪律、防误报与治理连续性上确实达到罕见的高质量；GPT 方案 v2.1 的执行架构
（FR→PSJ/TGSQ→R4X/CAN）方向正确，九轮互审的主要让步已真实落盘。但从"最终确保机器统观成功"
的角度，本审计独立发现了八项决定性事实，其中 A1–A4 是既有全部审计（GLM、GPT、Astra、DeepSeek）
都未指出的，且任一项都足以改变下一轮的执行条件。它们的共同含义是：当前瓶颈不是"数学证得不够"，
而是"证据契约、生成器能力与目标契约身份三处基础设施尚未闭合"。在这三处闭合前推进
PSJ/TGSQ/R4X，会在不稳定的证据基座上累积判词。**

四项既有审计都未指出的事实（详见 §1–§4）：

1. **A1（P0）根 `goal.md` 从未被 Git 提交，且无任何工作树备份**；FR-001 的"路径 A：旧 bytes
   可恢复"对它在物理上不成立，而时间线证据不对称地支持"actual 内容即用户的最终编辑"。
2. **A2（P0）14/25 个 later proof package 的版本闭合校验失败与 Git 无关**（7 命令源不匹配、
   6 外部依赖未登记、1 来源哈希漂移）；纯 commit 无法修复，而 GPT 方案的 VC-001 不含此项。
3. **A3（P0）机器统观引擎经本审计独立运行（selftest 94/94）确认是"声明文法校准器"**，不是
   开放候选生成器；方案要求的六类生成器真实链仍是 PARTIAL，但没有任何早期验收单元覆盖它。
4. **A4（P0）九轮互审、Astra、DeepSeek 与根 `goal.md` 自身全部 untracked**；整条审计证据链与
   目标契约处于单一副本风险，且目标契约连"当前版本"都不可从 Git 固定。

四项对既有审计的复核/强化（§5–§8）：

5. **A5（P1）Astra 审计集自身不完整**：其 01 报告引用不存在的 `04 - 证明语义…md`，其 00 方案
   承诺的 A01–A12 十二面与约九份报告只交付三份——最有价值的发现没有完整报告载体。
6. **A6（P1）验收门之争有了用户原文级判别证据**：KC-000005/010/011 的"构造悖论"语气与
   rulings §23 的"Goal 链含自然 consumer"是**两处用户原文之间的张力**，不是"AI 门设错了"。
7. **A7（P1）文献截止日义务是用户裁定级**（rulings §23 明文要求"具名截止日学术覆盖"），
   GPT 方案 008 §10 的 as-of 再解释软化了一条用户裁定，等级高于 DeepSeek 的"缺口 2"。
8. **A8（P1）EXP 排序缺口有 KC 锚点**：KC-000031/000035 是用户显式要求，方案自认"不可替代"
   却无任何早于 R4X 的里程碑位置——确认 DeepSeek 缺口 1 并补上原文依据。

## 1. A1（P0）：goal.md 从未被提交，FR-001 路径不可对称

### 事实（observed）

- `git log --all --oneline -- goal.md` 在**全部引用**返回空 → goal.md 从进入项目以来从未被任何
  commit 跟踪；`git ls-files goal.md` = 0。
- 四个工作树（main、detached `eb7b`、`HoTT-machine-overview`、`HoTT-semantic-overview`）中
  **只有 main 有 goal.md**，其余三处均不存在；`/Volumes/D/ALL-Markdown` 亦无。
- `git cat-file -p f302d37a…` 与 `6cb41c9b…` 均返回 "Not a valid object name" → 两个 pinned
  哈希不是 Git 对象。
- S151 checkpoint（`.codex/cognition/checkpoints/S-RES-20260915-151-R3-SOURCE-REPLAY/`）的
  before/after 只快照了 `STATE.json`、`HEAD.json`、session `RUNS.json`，**不含 goal.md 与 R4
  TaskSpec**。

### 结论

FR-001 在 GPT 方案 003 片被写成"路径 A 可恢复 / 路径 B 不可恢复"的双路径，并以"在 7,484 个已查
文件中未恢复旧 bytes"作为 `PINNED_BYTE_SNAPSHOTS_NOT_RECOVERED_IN_CHECKED_REPO_EVIDENCE`。
本审计的复核把这个判词**从"未找到"升级为"不可能存在"**：对 goal.md 而言，可恢复位置只有
（a）Git 历史——为空；（b）checkpoint 前后副本——未快照该文件；（c）其它工作树——不存在。
因此 **goal.md 只有路径 B（语义重建）可用**，且由于缺 byte baseline，其 intended-content 判定
只能依赖语义证据。

### 不对称性（本审计的关键推断，candidate）

时间线（observed）：S151 checkpoint `2026-09-15T06:38:03Z`；GLM 独立审计 README 诞生
`07:06:35Z`；goal.md mtime `07:10:11Z`；R4 mtime `07:10:41Z`。即两个文件的修改发生在
"GLM 审计交接准备"窗口内，且在 checkpoint 之后 32 分钟。

GPT 方案把局面表述为"actual 与 pinned 各自自称 current、不预先判定哪版正确"。本审计认为这个
对称框架**过强**：

- actual 版没有竞争版本可对照（旧 bytes 不存在），它不是"两个版本之一"，而是**唯一存在的版本**；
- actual goal.md §11 的完成门与 `rulings.md` §23 的用户裁定（"至少一个候选贯通…自然 consumer、
  现实同任务对应和方向 A/B"、"具名截止日学术覆盖"）逐项吻合 → actual 内容与用户既定意图一致；
- 修改时点与用户准备外部审计的动作同窗。

因此**证据不对称地支持"actual 内容即 intended current、STATE pin 仅为 S151 时刻的过期快照"**。
本审计不能证明编辑者身份（这是 source-reported 级别的事实），但可以说：FR-001 的正确完成路径
是"以 actual 为 intended 候选、用 rulings/Feature/用户原文做语义佐证、登记 pin 过期并重钉，
同时登记'目标契约从未进入版本控制'这一根因"，而不是"在两个版本间中立裁决"。

### 影响

若执行者按 003 片的双路径花时间搜旧 bytes，对 goal.md 是空转；若把"改 pin 为 actual"当作完成，
又跳过了"登记根因 + 目标契约纳入版本控制"这一真正修复。修订见 `Atria的方案/修订片/001`。

### 最强反解释

可能存在本审计未搜索到的备份（如主机级 Time Machine、用户私存的编辑前副本）。该反解释不改变
"在项目可及范围内不存在"这一定范围负结论，但把"不可能存在"降级为"在已检查范围内不存在"——
本审计已在报告与收据中保留该限定。

## 2. A2（P0）：版本闭合的 14 项失败与 Git 无关

### 事实（observed，本审计独立复算）

`verify_proof_version_closure.py` 全量运行返回 `BLOCKED / GIT_FAILED`（C-188 资产 untracked）。
绕过 Git 前置、直接对 25 个 later packages 逐包调用 `check_later_package`：

```text
later_packages: 25  OK: 11  FAIL: 14
 7 × LATER_COMMAND_SOURCE_MISMATCH        （包装脚本 argv 未让源码路径恰好出现一次）
 6 × LATER_DEPENDENCY_GAP_NOT_ALLOWLISTED （外部 Cubical 源树依赖未登记）
 1 × LATER_SOURCE_HASH_DRIFT             （LIT 说明更新后未同步 manifest）
```

分类与 Astra 一致（Astra 亦报 14 包），本审计独立确认并补充分类计数。

### 结论

GPT 方案 003 片 §9 的 VC-001 流程是"冻结 status → 逐包枚举 → 跑 closure verifier → 精确
stage/commit → 翻转 version status"。但**上述 14 项失败全部与 Git 跟踪状态无关**：即使把全部
218 个 changed 路径提交，这 14 包仍会失败。方案没有把"修复包装脚本契约 / 登记外部依赖树 /
同步 LIT manifest 哈希"列为前置工作包，因此 VC-001 按当前写法会在 commit 后立刻暴露 14 项
新失败，且没有处置路径。

这不是"数学证明为假"的证据（run 收据本身的 KERNEL_ACCEPTED 状态未变），而是**证据契约层**
失配：F-011 要求的 source→run→index 三方绑定在 14 个包上不闭合。

### 影响

F-011 的 `VERSION_CLOSED` 状态对 14 个包不可达；`feature-list.md` F-011 自述"全库 version-closure
因未跟踪 C-188 起资产正确阻塞"只覆盖了 Git 侧，未覆盖契约侧。任何以"提交后证据就闭合"为前提
的下游判词都建立在不成立的基础上。修订见 `Atria的方案/修订片/002`（新增 EC-001 证据契约修复工作包）。

### 最强反解释

校验器自身可能有 bug（例如"源码路径必须在 argv 出现一次"的假设对某些正当封装过严）。该反解释
不消除问题：无论责任在包还是在校验器，14 项失配必须被显式裁决并修复，才能让版本闭合前进；
把它留在原处只会让 VC-001 失败看起来像"Git 未授权"。

## 3. A3（P0）：机器统观引擎是声明文法校准器，不是开放候选生成器

### 事实（observed）

- 本审计在 `/Volumes/D/HoTT-machine-overview` 独立运行 `mo.py selftest`：**94 tests / OK**，
  `validate` 亦通过——Astra 的运行结果独立复现。
- `machine_overview/search.py` 顶部契约明文："The search walks the *declared* grammar only."
- L1 文法 `l1-v2.json` 的界：`delay_index_max=2`、`race_partner_index_max=2`、
  `context_depth_max=2`、`deadline_horizons=[0,1,2]`；`calibration_benchmark` 直接嵌在文法里，
  `claim_refs: ["C-73","C-74"]`，并注明"Complete enumeration only for this finite L1 calibration
  grammar"。
- `registry.json`：`implemented_stages = [M0, M1, M3]`；`partial_stages` 中 **M2 = "one symbolic-horn
  proof-search slice …; no general dependent/higher-path search"**；M4、M5 的集成与版本闭合仍 open。
- 程序化完备性规划 005 片自评：`P2 生成器横向骨架 = PARTIAL`、`P6 高阶/模态深度 = PENDING`、
  `P7 现实/时间桥梁 = UNRESOLVED`、`P8 独立评估 = M4_LITE_ONLY`、`P9 学术综合 = PENDING`。
- 三个 research extension（tick-irrelevance、reflected-tick、quotation-bridge）的判词全部为
  "表示边界 / HoTT bug 未建立"。

### 结论

"机器统观"目前的真实能力是：**在人工声明的有限文法上做完整枚举、grammar-preserving 归约、
原生核校验与收据化**。这是高价值的校准/验证设施，但它**不生成**新的理论构造、新的 consumer、
新的抽象变换或新的现实任务。方案 007 片要求"六类生成器各一条 input→candidate→oracle→receipt
真实链"，而当前只有声明文法枚举（第 1 类的部分）+ 三个研究扩展（属第 5/6 类的个案）。

GLM 的 B4（基础设施偏好、验证侧扩张而假设生成侧无对应投入）与 Astra 的 3.3（把新候选生成提前
到第一轮验收）都触及了这一点，但**没有任何一份审计把它标为 P0 级的"确保成功"能力缺口**，
GPT 方案的里程碑 M0–M6 也没有一个单元验收"生成器获得新能力"。

### 影响

这是"机器统观能否成功"最直接的能力约束：若不建设生成器，无论 PSJ/TGSQ/R4X 的判词多干净，
候选空间始终由人工预置的文法与任务决定，"统观"退化为"对已知族的穷举校准"。这与 GLM 的 B3
（分类法即命运）是同一问题的两面：**分母由人工声明，引擎不越界**。

### 最强反解释

声明文法路线本身是正确的安全设计（可枚举分母、remainder=0、防止无界搜索）；本审计不主张改为
无约束生成。反解释成立的部分是：校准器足以验证候选；不成立的部分是：它不能**发现**候选，
而 Goal 的完成门要求至少一个**新**的贯通候选。因此结论保留，但修订方案把"生成器"限定为
"在冻结文法族 + 冻结任务族上的有界新组合 + 人工/来源供给的新文法"，不要求无界生成。

## 4. A4（P0）：审计证据链与目标契约本身全部 untracked

### 事实（observed）

`git ls-files` 逐目录计数：

```text
GLM独立审计 tracked=0      GLM的建议方案 tracked=0    GLM的回应 tracked=0
GPT的回应 tracked=0        GPT的方案 tracked=0        Astra的审计报告集 tracked=0
DeepSeek的审计报告集 tracked=0  DeepSeek的方案 tracked=0  goal.md tracked=0
```

`git status` = 218 changed（180 untracked + 38 modified），最近 commit `2bbf5c8`（2026-09-13）。

### 结论

DeepSeek 的 04 §3.3 指出"九轮互审文档全部 LOCAL_UNCOMMITTED"，但**未指出 goal.md 本身也未提交**
（本审计 A1）。两者叠加意味着：项目当前的目标契约 + 全部外部审计 + 双方共识方案，**没有任何
一项进入版本控制**。这产生两个后果：

1. 单一副本风险覆盖了"决定下一轮执行条件"的全部输入（goal、方案、审计判词）；
2. FR-001 试图用 Git 考古裁决冲突时，连"actual 版本"都不是可固定的 Git 对象——冲突的**两端**
   都不在版本控制里，只有一端在文件系统里、另一端在 STATE 的一个过期哈希里。

### 影响

VC-001 的紧急度因此高于任何一份既有审计的表述：它不只是"保护 807 文件 Coq 归档"，而是
"让下一轮的执行前提可恢复"。修订见 `Atria的方案/修订片/002`。

## 5. A5（P1）：Astra 审计集自身不完整（元审计）

### 事实（observed）

- Astra 的 `01 - 总结论与决定性发现.md` §2.2 引用 `[专项分析](04 - 证明语义、校验契约与运行复核.md)`

- Astra 的 `00 - 审计方案与验收口径.md` §8 承诺"预计报告集"共九类（含项目边界、原意与往返、
  机器实现与证明完整性、搜索完备性、发现清单与接手验收、Session/KC 回评），并定义了 A01–A12
  共 12 个审计面。实际交付 3 份，覆盖约 A02/A05 的一部分。

### 结论

Astra 是四份审计中唯一实际运行校验器并发现真实证据契约失败的一份（A2 的原始来源），价值最高，
但**它的交付不完整**：最有价值的发现（14 包失配、协调器未集成）只写在总结论里，没有 promised
的"机器实现、证明与证据完整性"报告承载细节、复现步骤与处置建议。这本身就是一个治理事实：
**"已完成审计"不能按其自述清单被假定为完整**，与本项目的其它资产一样需要覆盖对账。

### 影响

本审计的 02/05 部分承担了 Astra 未交付的报告载体（独立复算 + 补充分类）。同时这提示用户：
DeepSeek 与 Astra 的结论存在**分工缺口**——DeepSeek 做方案/契约层（未跑校验器），Astra 做实现
层（未成报告），两者的结论不能互相替代。

## 6. A6（P1）：验收门之争是"两处用户原文之间"的张力

### 事实（observed，用户原文）

- **KC-000005**（LocalGPT，2026-09-09）："我们真正的目的是：找到它其中存在的悖论……但是我们
  找到悖论才是关键，至于悖论作为矛盾，它到底是否定了哪个前提，那是未来的下一个故事。"
- **KC-000010**（WebGPT，2026-09-10）："最优雅的结果，是我们用 Think in HoTT 的方式，
  **构造**出来了一个悖论，这个悖论让人们觉得现实当中根本不存在这种理论推演出的'困难'，
  但是如果人们 Think in HoTT 的话，那么就一出现无法完成的困难……结果就是以'不可计算性/
  不可停机性'为特征。"
- **KC-000011**（WebGPT）："我其实有种预感，要在 HoTT 中发现关于时间、时序的问题，其实就是
  看它什么时候，不想让时间、时序参与到 Think in HoTT 这件事中。"
- 对照 **rulings.md §23**（用户裁定，2026-09-14）：新 goal 要求"至少一个候选贯通精确 HoTT 规则、
  机器证明的不完成/不相容、HoTT 必要性、**自然 consumer**、**现实同任务对应**和方向 A/B"。

### 结论

GLM 的 B1 说"验收门把哲学命题塞进数学定理门"；GPT 反驳"正向门可达"；DeepSeek 提炼为"L1 定理
见证 / L2 哲学交付"需用户裁定。本审计为这场争论补上判别性证据，并把它**重新定性**：

这不是"AI 自设门槛对不对"的问题，而是**用户两处原文之间的真实张力**——KC 的验收语言是
**构造导向**（"构造出来一个悖论"、"找到悖论才是关键"、"归因是下一个故事"），而 ruling §23
的 Goal 链是**贯通导向**（含自然 consumer 与现实同任务）。两种读法都有用户原文支撑，因此
**只有用户能裁决，且裁决的输入现在比 DeepSeek 提出时更充分**。

同时必须指出对 GPT 方案有利的一面：§23 的"自然 consumer + 现实同任务"是 2026-09-14 的、
更晚的、针对新 Goal 的显式裁定，时序上后于 KC；且 Z_LAW §0 的目标表述也要求"提升为已完成对象
时产生可证明的非法构造或非现实性"。因此**默认（无新裁定时）应维持 §23 门**，但把"构造导向的
L2 组装交付"设为**并行可达的独立交付态**，而不是像现在一样只作为 008 §11 的"中间报告"。
详见 06 与 `Atria的方案/修订片/004`。

### 影响

若不裁决，项目会按 DeepSeek 预判的 R1 模式运行（高质量有界负结论无限累积）。若裁决为"并行
交付态"，已有机器结果族（C-71–C-76、C-96–C-99、C-92–C-95、C-106–C-109）可以立即进入组装，
且**不与定理线冲突**。

## 7. A7（P1）：文献截止日是用户裁定级义务，已被语义再解释软化

### 事实（observed）

# 05 - 机器统观引擎能力边界审计

> 问题：作为"机器统观"的执行主体，引擎真实能做什么？它能否生成新候选，还是只能校准已知候选？
> 这是"确保机器统观成功"最直接的能力问题。本审计是唯一独立运行了引擎并给出定性结论的一份。

## 2. 能力定性（本审计的核心判断）

引擎的真实能力是四件事，且都做得干净：

1. **有限声明文法上的完整枚举**（含负控制策略与 reduction guard）；
2. **grammar-preserving 归约**（每次缩小仍留在声明文法内，且 never_drop_kinds 保护 consumer 形状）；
3. **原生核校验与收据化**（RUN.json/stdout/stderr/environment/source-manifest/index-row-manifest）；
4. **确定性可复现**（selftest 含 answer-independence、determinism、replay-without-kernels）。

它**不能**做的三件事，恰是 Goal 完成门要求的：

1. **生成新的理论构造**（新抽象变换、新 HoTT construct 组合）——文法由人工预置；
2. **生成新的 consumer/任务**——task/grammar/case 三者一一对应且人工冻结；
3. **跨声明文法族的自动搜索**——M2 自评"no general dependent/higher-path search"。

**判词**：

```text
MACHINE_OVERVIEW_ENGINE_IS_A_DECLARED_GRAMMAR_CALIBRATOR
/ NOT_AN_OPEN_CANDIDATE_GENERATOR
/ SIX_GENERATOR_FAMILIES_REQUIRED_BY_PLAN_007_ARE_PARTIAL
/ NO_EARLY_ACCEPTANCE_UNIT_COVERS_GENERATOR_CAPABILITY
```

## 3. 与 GLM B3/B4、Astra 3.3 的关系

- GLM B4（基础设施偏好：验证侧扩张、假设生成侧无对应投入）——本审计以 registry 与 grammar 证据
  **确认其机制**，并指出它不只是"偏好"，而是引擎的**设计边界**；
- GLM B3（自指分母：478 项中约 430 是自产工件）——与本发现合流：**分母由人工声明、引擎不越界**，
  两者叠加意味着候选空间在物理上被人工预置的文法/任务集合界定；
- Astra 3.3（把新候选生成提前到第一轮验收）——方向正确但未给出能力定性，也未定级；本审计把它
  精确化为 `GEN-001` 修订（`Atria的方案/修订片/003`）。

## 4. 关键澄清：这不是设计错误

声明文法路线本身是**正确的安全设计**：它给出可枚举分母、remainder=0、防止无界搜索与虚假覆盖。
本审计**不主张**改为无约束生成，也不主张"统观必须能无界发现悖论"。问题在于**方案与实现之间的
落差**：方案 007 片把六类生成器（typed synthesis / rule mutation / consumer synthesis /
self-reference / metamorphic / source-guided）作为已声明的搜索广度义务，而实现只有其中第 1 类的
有限形态与若干个案。若不显式验收，"统观覆盖证书"会继续在人工分母上签发。

## 5. 有界生成器的可行最小形态（修订依据）

`GEN-001` 不要求无界生成，只要求证明引擎能处理**冻结文法族之外的新输入**：

1. 冻结一个**新**任务（来自 TGSQ/ATD 来源或用户 KC 指名的方向），其文法不在现有 15 个之中；
2. 由程序（而非人工预置 benchmark）在**扩展后的声明文法**上枚举候选；
3. 至少一个候选进入原生核 oracle 并产出 receipt；
4. 明确标注哪些内容由人预置、哪些由程序搜索、哪些由原生核检查（Astra 3.3 的要求）；
5. 若新文法族不产生新候选，登记为该族的 scoped negative + successor，不得因此宣称生成能力已具备。

这把"六类生成器"从抽象义务变成**一个可验收的早期单元**，且不破坏现有安全边界。

## 6. 单工作面与集成的真实状态（复算 Astra）

rulings §22 与 goal.md §2 要求 main 为唯一 active write root，外部 worktree 只作只读候选来源。
但执行下一轮所需的最小机器闭包（协调器 + grammar + verify 链）**仍在 `/Volumes/D/HoTT-machine-overview`**，
main 只有 169 份选定实物的 hash-frozen 导入。方案 010 §1 的单工作面原则因此**在 main 侧尚未具备
执行载体**。修订：把"协调器最小可用闭包接入 main"列为 M0.5（在 FR/EC 之后、PSJ 之前），
与 Astra 推荐的下一步一致。

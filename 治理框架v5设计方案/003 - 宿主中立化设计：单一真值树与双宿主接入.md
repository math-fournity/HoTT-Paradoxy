# 宿主中立化设计：单一真值树与双宿主接入

## 一、原问题（机制报告 002/003 的调查结论）

`.codex/` 的命名与叙事（"Codex 数学研究治理框架"）把整套资产绑定在单一宿主上：
ZCode 没有正式入口，若要在 ZCode 侧"也用起来"，直觉方案是复制一份改造成
ZCode 版——这正是你禁止的"维护两套"。深究后发现绑定其实是三层：
(1) **物理绑定**：目录名 `.codex`；(2) **机制绑定**：Codex 原生发现
`.codex/skills/*/SKILL.md`，ZCode 无此机制；(3) **叙事绑定**：文档通篇以
"Codex 会话"为主语，ZCode 会话在证据链里没有一等身份。

关键事实（分片 002）：三层绑定里只有 (2) 是真差异，而 (1)(3) 是命名与措辞；
且 ZCode 官方提供从 Codex 导入 Skill 的 symlink 通道、runtime 本来就是纯
python3、根 AGENTS.md 两宿主都自动注入——**去绑定不需要发明新机制，只需要
把真值树从宿主私有约定里搬出来**。

## 二、调整设计

> **2026-09-18 修订（用户质询"Codex CLI 会默认加载 repo 内 `.codex` 中内容，移动后 Codex 侧会不会彻底失效"）**：
> 联网查证坐实——Codex CLI 默认自动发现项目级 `.codex/skills/`（与用户级 `~/.codex/skills/` 并列；
> 来源见分片 002 补注）。因此原稿"git mv 走树、不留 stub、Codex 损失为零"的断言撤回：
> 搬走会杀死 Codex 的原生 Skill 发现/元数据注入/自动触发/`$` 调用，把三枚 SOP 从一等公民降级为
> 普通文件。修正后的默认方案是**树不动**；宿主中立只在真正发生绑定的三层（叙事/路由/证据）实现。
> 原迁移方案降级为"可选备选"，且必须带 symlink 兼容层与硬验收门（见 §2.2）。

### 2.0 默认方案：`.codex/` 保持原位（修订后推荐）

物理树不动：`.codex/` 继续作为唯一真值树，Codex 的项目级 Skill 发现零损失。
宿主中立通过三层实现（这三层才是绑定的真实位置，机制报告 002 的调查结论）：

1. **叙事层**：根 AGENTS 与 `.codex/AGENTS.md` 明文声明"目录名为历史遗留，不构成宿主绑定；
   任何能读文件 + 跑 python3 的宿主共用本树"；validator R3（禁宿主排他措辞）兜底。
2. **路由层**：根 AGENTS v5 分档路由表直接给出 `.codex/…` 路径——两宿主走同一路径、
   同一命令（`python3 -B .codex/tools/cognition_runtime.py …`）。
3. **证据层**：SESSION.md 元数据加 host/model/tier/load_receipt；ZCode 会话与 Codex
   会话在 STATE/checkpoint 走完全相同的原子事务（见 §2.3，不受本修订影响）。

ZCode 侧接入（2026-09-18 二次修订）：合同层仍是文本路由（宿主最小合同不变）；
**原生触发的推荐通道改为 repo 内 symlink 农场**——`<repo>/.zcode/skills/<name>`
→ 符号链接指向 `.codex/skills/<name>`，**随 git 提交**：ZCode 经其官方 workspace
发现机制（`<repo>/.zcode/skills/`）原生发现三枚 SOP，真值仍在 `.codex/skills/`
单株树，全局 `~/.zcode` 零足迹（跨项目零元数据税、零误触发）。备选的
`~/.zcode/skills` 全局导入维持默认不装。验收注意：ZCode 对 symlink 目录的
发现行为与 Codex 同样未在本 repo 实测——进 P2 双宿主验收门。

### 2.1 备选方案：symlink-shim 迁移（仅在用户坚持去供应商命名时）

真值树 `git mv` 为 `.cognition/`（结构同下表），`.codex/` 保留为**纯兼容层**：
`.codex/skills/<name>` → 指向 `.cognition/sops/<name>` 的**目录符号链接**
（Codex 经原路径照常发现；单真值、零内容复本）；`.codex/AGENTS.md` 留 3 行指针
（若该文件被宿主读取则自动跳转，未被读取亦无害）。**硬验收门**：fresh Codex
会话必须实测三枚 skills 全部可发现、可 `$` 调用、治理链（plan/checkpoint）完好；
validator 增加 symlink 一致性检查（断链即 FAIL）。风险：Codex 对 symlink 目录的
发现行为未在本 repo 实测过——这正是它只作备选、不作默认的原因。

| 目标布局（仅备选方案） | 说明 |
|---|---|
| `.cognition/{AGENTS,LOAD_SET,PROTOCOL,ROLES}` | 合同四件 |
| `.cognition/sops/<name>/SKILL.md` | SOP 正文（canonical） |
| `.codex/skills/<name> → symlink` | Codex 兼容层（零内容） |
| `.cognition/{STATE,archive,checkpoints,runtime,research/…}` | 其余原结构迁移 |

### 2.2 双宿主接入矩阵（不维护两套的合同）

| 层 | Codex 接入 | ZCode 接入 | 真值在哪 |
|---|---|---|---|
| 宪法 | 根 AGENTS.md 自动注入（标准行为） | 根 AGENTS.md 自动注入（3.8.1 组合行为） | 根 AGENTS.md（唯一） |
| SOP | **`.codex/skills/` 即 Codex 项目级发现路径（树不动即原生保留）**；文本路由按档全文读为公共路径 | **`<repo>/.zcode/skills/<name>` → symlink 指向 `.codex/skills/<name>`（随 git 提交，workspace 级原生发现）**；文本路由按档全文读为公共路径 | `.codex/skills/`（唯一） |
| 执行 | `python3 -B .codex/tools/cognition_runtime.py …` | 同一命令（Bash） | runtime（唯一） |
| 证据 | SESSION.md/RUNS.json + 宿主 rollout 补充 | SESSION.md/RUNS.json + 宿主 model-io 补充 | repo 收据（唯一）；宿主原始档各在宿主侧 |
| 宿主私有件 | — | project memory / repo wiki：声明为辅助件，禁入真值链 | — |

单套性由三条硬规则保证：(R1) **宿主专属信息只允许出现在收据的元数据字段**
（host/model/tier），不允许出现在任何治理正文的规则语义里；(R2) 任何文档
不得以宿主名做条件分支（"Codex 会话须 X，ZCode 会话须 Y"不允许——差异全部
收敛到"档位"维度）；(R3) validator 增加一条检查：治理正文 grep 不得出现
"仅 Codex/Codex 专属"类排他措辞（防叙事绑定回归）。

### 2.3 ZCode 会话的一等身份（证据层）

SESSION.md 模板新增必填元数据：`host: codex-cli|zcode-desktop|…`、`model`、
`tier: T0–T3`、`load_receipt`（档内文件 sha256 清单）。runtime 的 session
bundle Gate 与 checkpoint 不区分宿主——ZCode 会话写 STATE/checkpoint 与
Codex 会话走完全相同的原子事务。**这使"谁来干活"从架构问题降为收据字段。**

### 2.4 ZCode workspace overlay（`.zcode/`）作为一等交付物（2026-09-18 三次修订新增）

事实修正（分片 002 二次修正注记）确认 ZCode 有 workspace 作用域后，v5 把
`.zcode/` 从"零 footprint"升级为**repo 内的宿主加速层**，与真值树并立：

```
.zcode/                          # 随 git 提交；只放加速器，不放真值
  skills/
    hott-local-session-governance -> ../.codex/skills/hott-local-session-governance
    hott-paradox-research        -> ../.codex/skills/hott-paradox-research
    hott-paradox-search-sop      -> ../.codex/skills/hott-paradox-search-sop
  commands/
    closure.md                   # /closure：档位声明 + plan/check 组合调用（正文=指示，指向同一 runtime 命令）
    checkpoint-dry.md            # /checkpoint-dry：checkpoint 默认 dry-run 包装
```

设计要点：(a) skills 全部是指向 `.codex/skills/` 的**符号链接**——ZCode 原生发现、
真值单株、全局零足迹；(b) commands 是纯 `.md` 指示文件，包装的是**同一条**
runtime 命令，不是第二套逻辑；(c) `.zcode/config.json` **默认不建**（无 MCP/hooks
需求）——workspace hooks 虽经指南确认存在（需 `hooks.enabled: true`），但
(a) 你的全局宪法"Project Hook 被忽略"条款与之冲突未裁定，(b) v5 强制哲学是
"以必然性强制"（fail-closed 状态机），Hook 只作 P3+ 可选项、待 ROI 遥测显示
需要且宪法冲突解决后再议；(d) 降级路径：若任一宿主对 symlink 目录的发现
不生效，加速层静默失效，回退到文本路由——合同层不受影响（宿主最小合同
本就不依赖加速器）。

## 三、为什么这样调整之后更好

1. **一套成本，两个宿主**：零复本、零翻译层；ZCode 接入不新增任何 repo 内文件
   （可选项都在宿主侧）。对比"两套"方案：同步成本随宿主数线性涨、漂移面
   随文件数平方涨（机制报告 002 的复述定律）——本方案从结构上消灭该类漂移。
2. **顺标准而行**：AGENTS.md 是 Linux Foundation 托管的跨工具标准（60k+ 项目），
   根文件作唯一入口正是标准推荐的"单一真值源"模式；未来任何读 AGENTS.md 的
   宿主（Cursor/Gemini CLI/…）零成本接入。
3. **绑定解除不牺牲 Codex（修订后的准确表述）**：默认方案下 Codex 的两个原生通道
   都完好——指令注入走根 AGENTS.md（不依赖 `.codex/`），**项目级 Skill 发现走
   `.codex/skills/`（树不动即零损失）**。原稿"原生发现只是锦上添花、损失为零"
   是未经验证的断言，已由用户质询与联网查证（Codex CLI 默认发现项目
   `.codex/skills/`）纠正：真搬走会砍掉发现/元数据注入/自动触发/`$` 调用。
   这正是默认方案改为"树不动"的原因——去供应商命名的外观收益，不值得
   用 Codex 侧降级去换；若未来仍要迁移，只能走 §2.1 备选的 symlink 兼容层
   + 硬验收门。
4. **消融实验的教训被吸收**：S170–176 证明状态机不可绕过——本设计让状态机
   （runtime+STATE+checkpoint）保持唯一且宿主无关，把"哪个宿主"完全挡在
   状态机之外。

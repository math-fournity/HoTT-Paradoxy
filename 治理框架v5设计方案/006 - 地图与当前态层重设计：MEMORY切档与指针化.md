# 地图与当前态层重设计：MEMORY 切档与指针化

（对应《机制报告》004：README / MEMORY / feature-list / rulings 的调查结论）

## 1. README 逻辑文档（索引+4 片，≈8,235 tokens）

**原来存在什么问题**：地图嵌身份事实——001 片写死 generation-4/89 消息，
已过时两代（机制报告 004 的实测漂移）；四片里有相当篇幅在复述治理规则
（加载方案、验证入口与 PROTOCOL 重叠）。

**打算如何调整**：压成**索引+2 片**（目标 ≈3,500 tokens）：001=入口与认知流
链路图（保留——这是本 repo 独有的空间地图价值）+ 关键文件表（身份字段全部
改为"见 STATE.current_core"式指针）；002=历史交接包与归档恢复说明（纯历史，
压到最小）。原 003"加载方案与验证入口"整片撤销——加载方案归 LOAD_SET，
验证入口归 validator/PROTOCOL（地图不教流程）。

**为什么调整后更好**：地图回归"只路由、不承载事实/规则"的本位，其漂移面
（gen-4 嵌入）被消灭；启动核再省 ≈4.7K；删除的 003 片内容零损失（owner
文档里有权威版本）。

## 2. MEMORY 逻辑文档（索引+3 片，≈39,716 tokens）

**原来存在什么问题**：003 片（顺序日志，≈27,551 tokens，218 行）在
always_full_boot——append 越勤勉启动越贵（机制报告 004："与勤于记录的初衷
直接对抗"）；时序证据的消费方式是"回溯时查"，不是"每轮全文重读"，
层归属按写入习惯而非消费方式定的典型错配。

**打算如何调整**：三职分家——`MEMORY/001 当前队列`（原位更新，≈1 万，
T0 以上常驻）；`MEMORY/002 证据上限与恢复入口`（原位更新，常驻）；
**003 顺序日志降为 query_first**：改名为 `MEMORY/log/`（按 S 号分文件），
索引片只保留"当前已验证状态"快照节（每轮覆写，≈3–5K，常驻），历史条目
全部移入 log/（追加规则不变，证据零损失）。

**为什么调整后更好**：启动核从 MEMORY 项省 ≈2.3 万（39,716 → ≈1.6 万）；
append-only 的证据性质完好保留（log/ 只增不改，可审计性不变）；队列/上限/
日志三职的层归属与各自消费方式对齐——这是把"核心认知纪律"（正文常驻、
账本按需）应用到当前态层的同构改造。

## 3. feature-list.md（≈3,190 tokens）

**原来存在什么问题**：机制报告 004 判定其机制成功（16 条需求证据链全可点验、
状态词表本身就是 F5 防御）——唯一隐忧是状态词膨胀（最长状态词已达 9 段拼接）。

**打算如何调整**：不动结构；只做两件小事——(a) 状态词改为"主状态 + 修饰
键值对"（`STATUS: MECHANICALLY_VERIFIED; version_closed: true; fresh_model:
NOT_RUN`），机械可解析、不再人肉拼接；(b) 证据列的 SRC/DES/IMP/VER 定位
改用 `owner 文档 §节` 短指针，替代当前的超长内联叙述。

**为什么调整后更好**：可维护性提升（词表不再失控），语义零变化；
体量预计略降（修饰键值化天然去重）。

## 4. rulings.md（≈5,094 tokens）

**原来存在什么问题**：无——机制报告 004 实测它是全 repo 唯一"复述零漂移"
的多处引用源（引用链根位置，人人引用它、它不引用别人）。

**打算如何调整**：**不动**。仅在未来新增裁定时沿用现有格式（编号裁定 +
用户原文逐字块）。v5 全部重大变更（分级原则、宿主中立、STATE v3、收据制）
落地时各产生一条新裁定——立法记录随方案走。

**为什么调整后更好**：好部件不动是最好的调整；且它将成为 v5 各项变更的
合法性锚（本 repo 的惯例：机制变更必须能追溯到 ruling）。

# 用户权威层与投影层重设计：hot/cold 与 baseline 自同步

（对应《机制报告》005 用户权威层 / 006 投影层的调查结论）

## 1. 核心认知.md + generation 机制（≈12,191 tokens）

**原来存在什么问题**：机制报告 005 的结论是它**没有问题**——它是全框架
纪律最好的部件（单文件、生成器写路径、七代退休机制、元数据降层），
保真与容量协作的孤例，单位价值最高的开销。

**打算如何调整**：正文与机制**零改动**。仅一处增量：把它的纪律模板化——
新增 `docs/quality/常驻文档准入与退休合同.md`（从 core 的实践中抽象出
"进 always_full 层的文档必须满足：单写路径/退休通道/元数据降层"三条件），
作为其他常驻文档的准入规则（validator 检查 always_full 清单里每件文档
声明其三条件的落实方式）。ZCode 侧无需任何适配：它是文件，两宿主同样读。

**为什么调整后更好**：不动的理由与调整的理由同源——它已经被证明是对的
（12K 七代零失控）；把它"为什么对"写成合同，让 STATE/投影的 v5 改造有
章可循（分片 008 的退休机制直接引用此合同），防止未来的新常驻文档重蹈
STATE 覆辙。

## 2. 方向追踪 / 全景视野（≈13,786 / ≈41,857 tokens）

**原来存在什么问题**（机制报告 006）：投影机制正确（视图按需重组、revision
锚定），但**行空间随结果数单调增长且全部行都在 always_full 层**——全景视野
成为四件套最大件；"回望全部结果"的消费需求其实分层（当前活跃 vs 冻结/历史）。

**打算如何调整**：**hot/cold 行拆分**（不动投影生成机制）：每张 OUT-*/DIR-*
大表增加 `heat` 列（hot=被 active 记录引用或近 N 个 revision 内更新；
cold=其余）。投影索引+hot 行分片保留在四件套全文里；cold 行移入
`全景视野/archive-rows/`（query_first，同表头格式，行级对账规则不变）。
投影生成器（既有 manager 脚本）自动维护 heat 与迁移，人工只裁决语义。

**为什么调整后更好**：四件套的"全文"覆盖的是**当前决策 relevant** 的方向/
结果全集，冷行仍可显式水合（证据零损失）；估计全景 41,857 → ≈1.5–2 万、
方向 13,786 → ≈1 万，四件套合计 100,646 → ≈6 万；行级对账+revision 锚定
等有效原理原样保留。这是把"latest+active 增量续接"（机制报告 007 认定的
正确模式）推广到投影层。

## 3. 扩展认知（≈32,812 tokens）

**原来存在什么问题**（机制报告 006）：角色声明权威隔离设计精良；但
baseline 字段钉在 generation-4 而实际引用 generation-7——又一根植于
"人工同步 baseline"的漂移点。

**打算如何调整**：**baseline 自同步**——修订片/长文的更新脚本在每次
core generation 变化的 checkpoint 里，机械地把 `baseline:` 字段刷新为
新代并触发"覆盖检查"（长文合同已规定"原文变化时必须按新代重新检查覆盖"，
现在把这个触发从人肉改成脚本强制）。正文结构不动。

**为什么调整后更好**：漂移类缺陷（baseline 过时）从"靠人记得"变为
"事务内机械保证"，与 core generation 的 transition 收据同事务——
该类漂移结构性消灭；长文的展开价值（AI 阐释层防账本不可进入）不受影响。

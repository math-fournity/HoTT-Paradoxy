# 治理框架 v5 设计方案·索引

> ⚠️ 逻辑文档索引：全文 = 本索引 + 下方 10 个分片；缺一片即未完成全文阅读。
> 本方案是**提案（DRAFT_PROPOSAL）**：一切变更需用户逐项裁定后才实施；本方案自身不改任何治理真值源。

- **委托**：用户 2026-09-18 原话——"把你的具体的对未来的 repo 内的治理框架的设计拿出来，注意你的新版本的方案也是分片的，
  而且要逐个论述 `Codex治理框架机制报告/` 中的每项你的调查内容：它原来存在什么问题？你打算如何调整它？
  为什么这样调整了之后才是更好的？另外，你要考虑，`.codex/` 让这套框架只能被 codex cli 中的 AI 使用，
  在 ZCode 这边如何也能用起来，而且肯定不能维护两套。你要联网查查 ZCode 的 repo 的治理方法。"
- **前置**：本方案站在两份姊妹报告上——[`Codex治理框架报告/`](../Codex治理框架报告/000%20-%20索引.md)（成本测量，G1–G7 杠杆）
  与 [`Codex治理框架机制报告/`](../Codex治理框架机制报告/000%20-%20索引.md)（逐文档作用/目的/原理 + 两族原理）。
- **一句话方案**：v5 = **分级治理（T0–T3）× 宿主中立（单一真值树，双宿主共用）× 三处保真义务补上容量配套**
  （STATE 热/冷拆分、压缩收据制、复述改指针）。目标：T0 轻任务 ≈1.5 万 est tokens 启动、T1 ≈4 万、
  T2 研究 ≈12 万；压缩重付从 49.7 万降到 ≈6 千；ZCode 与 Codex 走同一套文件、同一个 runtime、同一份证据链。

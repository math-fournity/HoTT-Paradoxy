# 形式合同、对角化与机器化

## 1. GodelizationCard：开始任何证明前必须冻结的合同

每个候选 interface 必须有一张 GodelizationCard。缺任何 material 字段时，只能作来源调查或规格工作，不能声称正在进行哥德尔式证明。

| 字段 | 必须冻结的内容 | 可接受证据 | 不可偷换 |
|---|---|---|---|
| T | 精确对象理论、语言、公理、规则、版本及有效公理化范围 | 作者形式系统、proof assistant object theory、版本固定来源 | bare ZFC、某个 model、ZFC 加大基数、Lean host 不得混称 |
| M | 证明元定理的元理论、kernel、所有公理、版本 | toolchain、source、run、axiom report | M 的成功不能自动成为 T 的内部证明 |
| Code | 公式、证明、过程或任务的可计算编码域 | 编码／解码实现与往返或限定失败定理 | “可以口头说成集合”不等于可表示 |
| Check | 有限输入上停止的 proof checker 或 acceptance checker | totality / termination theorem 或相称 kernel check | 一次运行或 timeout 不等于全称有限检查 |
| Accept_T | 真实 completion acceptance consumer 的输入、输出、Done 和来源 owner | 版本固定论文、规范、实现或真实使用者 | 研究者自造 Bool fixture 不得冒充实际 interface |
| FormalDone | interface 所输出的形式完成谓词 | source contract 或固定 formal specification | 不得用自然语言 “resolved” 代替 |
| OriginDone | 原过程的完成谓词 | 用户过程卡、版本固定过程／来源、同一任务控制 | 不得为凑对角化临时改写 |
| Bridge | 从 Accept_T 或 FormalDone 到 OriginDone 的支付方式 | 定理、source statement、明确 task switch 或拒绝 | 沉默不等于 bridge |
| ObjectCodeBridge | `Code` 如何作为 T 内可引用、可代入的对象；算术中通常是 numeral/term，集合论中可以是 set/class code | T 内 code/object/substitution correspondence theorem 或 source-defined exact construction | host serialization、macro quotation、M 层 AST 或“都是自然数”不等于 T 内引用 |
| InternalProvabilityAdequacy | 元层 proof relation、T 内 `Prov_T` formula 与二者的明确 payment | representability/adequacy theorem、版本固定语义或 proof-relation construction | 一个外部 checker、`reflect` 名称或 host proof transport 不等于理论在谈自身可证明性 |
| Diag | substitute、quotation、fixed point 或等价自编码构造 | 可执行算法与形式 theorem | 手写“我自己”不是对角化 |
| QObservation | 什么算观察到未支付提升 | 明确谓词、输入域、正反控制 | “有时间维度”不是可判定接口 |
| RealityMap ρ | 原过程到 Code 的保真映射 | 同一输入／操作／观察／Done 的逐字段表 | 编码存在不等于任务保真 |

### 1.1 外部技术校准（2026-10-04）

独立的 Isabelle/AFP 与 Agda 哥德尔化来源表明，`Code` 到 `Diag` 之间仍有一段不能省略的内部化工作：code 必须变成可在 T 中代入的对象，且内部 provability formula 必须对外部 proof relation有明确 adequacy。`NumeralBridge` 是 arithmetic target 的特例；冻结 `set.mm` source 已显示 set theory 可以使用 internal set-code。当前 [技术校准卡](../../audit/20261004-GODEL-Q-REFLECTION-G2-EXTERNAL-TECHNICAL-CALIBRATION.md) 与 [set.mm 重资格化卡](../../audit/20261004-GODEL-Q-REFLECTION-G2-SETMM-INTERNALIZATION-REQUALIFICATION.md) 共同固定证据标准。它们不把外部 formalization 用作本项目 ZFC 或 parent-Q 的 theorem。

## 2. 候选命题的三种强度

### 2.1 句法不完备性命题

若 T 有有效 proof predicate 和对角化，可以尝试证明：

~~~text
T ⊬ G
或
T ⊬ G 且 T ⊬ ¬G
~~~

它是关于 T 的可证明性边界的元定理。它本身不证明 G 对现实过程的解释。

### 2.2 完成反射失败命题

若 Accept_T、OriginDone、Bridge 都被固定，可以尝试证明：

~~~text
不存在统一的 B : ∀ e, Accept_T(e) → OriginDone(e)
~~~

或证明某个指定 d 使：

~~~text
Accept_T(d) ∧ ¬OriginDone(d)
~~~

这个结论只能归于该接口与该过程类别，不得泛化成所有 ZFC。

### 2.3 实际来源归因命题

只有当 source owner 实际将 Accept_T 当作原过程完成的充分理由，才可讨论：

~~~text
ACTUAL_ZFC_FACING_REFLECTION_FAILURE_WITH_SCOPE
~~~

该层仍不是 ZFC 对象语言矛盾；它是基础接受／反射政策的有界归因。

## 3. 候选对角化的最小逻辑骨架

设 T 的接受谓词为 Accept_T，且有一族带代码参数的过程 D。候选固定点结构是：

~~~text
OriginDone(D(e)) ↔ ¬Accept_T(e)
d = D(⌜d⌝)
~~~

若来源或理论承诺了：

~~~text
Accept_T(d) → OriginDone(d)
~~~

则得到：

~~~text
Accept_T(d) → ¬Accept_T(d)
~~~

这一步只排除 Accept_T(d)。它有三种不同的后续含义，必须分开：

| 额外条件 | 合法结论 | 不可声称 |
|---|---|---|
| 无额外条件 | interface 不能接受该特定 d | T 不一致 |
| interface 对该编码类声称 complete | 接受完整性失败或须排除 d | 现实过程已被证明无法完成 |
| T 内证明同一 reflection / completeness | 可研究对象层的反射冲突或不完备性 | 任何元层事实自动回落为 T 内 theorem |

对角化候选必须有 DifferentTask control：改变 ρ、OriginDone 或 Code 使 d 不再属于同一过程类别时，禁止把拒绝归为 Q。

## 4. Lean、Agda 与 ZFC 化的分工

| 工具层 | 可承担的工作 | 必须显式披露 | 不能替代 |
|---|---|---|---|
| ZFC 或其他 T | 其对象语言的公式、证明、编码、可表示性 | exact axioms / effective schema | M 的一致性与现实语义 |
| Lean | 固定逻辑与公理下的 syntax、checker、fixed point、有限模型或相对 metatheorem | Lean version、imports、axioms、kernel run | “Lean 已证明”升级为 bare ZFC 结论 |
| Cubical Agda | 与 exact HoTT / cubical target 相称的 path、HIT、guarded 或 computation theorem | compiler variant、options、library、postulates、native run | 用宿主 equality 假装对象 calculus |
| Meta-meta audit | ρ、实际 consumer、process contract、source payment、SameFullQ | source/version/task matrix | 只凭哲学相似认证同一任务 |

机器化结果必须按如下身份写入 claim matrix：

~~~text
MACHINE_PROVED_METATHEOREM_WITH_EXPLICIT_T_AND_M
SOURCE_CERTIFIED_ACCEPTANCE_PREMISE
PROJECT_DEFINED_DIAGONAL_FIXTURE
ACTUAL_INTERFACE_UNDERDETERMINED_WITH_SCOPE
~~~

不得把四种身份合并。

## 5. 必需正反控制

### 正控制

1. 一个非自编码、明确 bridge-paid 的过程，Accept_T 可接受且 OriginDone 可由 source 或 theorem 支付；
2. 一个有足够 rich process code 的接口，能恢复 OriginDone；
3. 一个理论外但元层可验证的有限 checker，逐 input 终止；
4. 若使用 哥德尔式 proof predicate，至少一个已知可证明句和一个已知无效编码都通过相应控制。

### 反控制

1. DifferentTask：换掉原过程合同时不得把输出差异归给 Q；
2. SourceSwitch：来源明确将 Done 改写时，结果是 task switch，不是未支付 bridge；
3. DecoderControl：富编码可恢复时，不能宣称不可表示；
4. NoDiagonalControl：没有 quote/substitute/fixed-point 时，不能宣称哥德尔式自指；
5. MetaObjectControl：M 中的 theorem 不能被误写成 T 的 theorem；
6. AcceptanceAbstentionControl：T 对 d 的拒绝或要求额外证书可能是合法防御。

## 6. 与现有 C-359 的严格关系

C-359 证明的是：

~~~text
SameFullQ ∧ source-permitted P ∧ HoTT-side B
→ contradiction in an explicit ZFCOneUse policy model
~~~

它仍缺实际 Accept_T、有效编码、对角操作和 ρ 的保真支付。因此本方案开始时不得将 C-359 作为终点；它只是一个待连接的 consequence kernel。未来若形成真实 GodelizationCard，应新建独立 claim，不修改 C-359 的证据身份。

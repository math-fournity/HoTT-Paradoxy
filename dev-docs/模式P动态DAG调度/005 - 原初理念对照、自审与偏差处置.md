# 原初理念对照、自审与偏差处置

## 1. 为什么 P-DAG 必须做系统自审

P-DAG 的任务不是仅把更多节点接到图上。它承载了研究发起人对模式 P 的一组连续要求：从罗素的计算—存在—自指张力提取可迁移模式；让 P 在无泄漏条件下引导 AI 的已有理论知识先定位线索；把 P1、P2、P3 按不同惯性打磨；先在 HoTT 重放中检验，再把同一冻结工具用于 ZFC；并让来源、控制、Battle 和 Master 裁决不替代同一任务与 UR。

因此每个自然锻造单元结束时，Master 不只问“这个节点得到了什么”，还必须问“它是否仍在做原初讨论要求的那件事”。这一步是对公开要求、来源和实际运行的比较，不是要求或保存任何 agent 的隐藏思维。

## 2. 两种审计节奏

### 2.1 每个自然单元的 delta self-audit

在来源卡、盲测、Battle、失败运行或某把刀修订后，Master 写一张 `SelfAuditCard`：

```text
source unit(s) / original requirement / actual action and evidence
alignment verdict / deviation class / why the deviation occurred
repair or stop action / affected P1-P3 fields / regression or falsifier
Git commit eligibility / next trigger
```

只审本单元触及的原初要求；不得为同一未变事实反复全文审计。它至少覆盖：理论靶与明显位置、P 的一遍线索身份、blind/no-cheat 边界、三刀分工、P3 的原始张力、同卡会合、MatchTrace、层级／任务忠实性、运行／来源证据和 Git 谱系。

### 2.2 版本更替或用户要求时的 full origin audit

出现下列任一触发时，重做完整来源清点和逐项对照：用户明确要求；创建／退休一把刀；改变 P 的成功定义；从 HoTT 校准转入 ZFC 定位；改变 agent／隔离／证据架构；或出现足以推翻此前解释的反例。完整审计必须从用户原文、可见对话档案、rulings、现有工具规格和运行收据重建，不以最近 SOP 摘要替代最初讨论。

当前完整审计 owner 是 [`audit/20261002-P-DAG-刀具系统全历史逐段对照审计.md`](../../audit/20261002-P-DAG-刀具系统全历史逐段对照审计.md)。旧的[`起源—实作对照审计`](../../audit/20261002-模式P刀具系统起源—实作对照审计.md)保留为历史输入：它的原分母没有纳入 U19、H010 与较早的工作意识前驱，不能单独冒充全历史审计。

### 2.3 全历史审计的分母与时间分界

当 Master 使用“全部讨论”“原初理念已逐项对照”“刀具系统已与用户要求一致”一类强表达时，必须先在 full audit 中明确：

1. **候选来源宇宙与逐项处置。**列出检索过的 source families、每个 conversation unit、`IN_SCOPE`／`PRECURSOR`／`OUT_OF_SCOPE_WITH_REASON` 身份及理由；关键词命中不自动等于直接设计输入。
2. **原文—实现—运行三段链。**每条直接要求必须有 user locator、当前 owner／代码／NodeCard locator、以及真实 run／source／Git evidence 或明确 `NOT_YET_RUN`。不能以 SOP 自述替代运行证据。
3. **历史与后续严格分界。**审计 `PRE_GOAL_HISTORICAL_CORPUS` 时，不用 Goal 后的修复倒灌为前一阶段的 PASS；Goal 后工作作为 `CONTINUATION_DELTA` 单列。
4. **偏差的可证伪归类。**只能使用本节的分类；若说 `ORIGINAL_IDEA_CHALLENGED`，必须写出被挑战的原句、同一任务的直接反例和为什么规格／运行故障不能解释它。
5. **精确 Git 证据。**有效的工具／SOP／收据修订必须有精确路径 commit；`NO_CHANGE` 仅在 audit 写明实际无变化理由时成立，不能为凑历史重复提交。

这不是要求每次短节点都重新读取全部历史。它是 full-audit 的可复算入口；自然单元仍使用 2.1 的 delta SelfAuditCard。

## 3. 偏差分类：先判断哪一层出了问题

| 类别 | 含义 | 允许的处置 |
|---|---|---|
| `ALIGNED` | 实际行为实现了原初要求，且证据等级与宣称相称。 | 保留、回归、写入过程记录。 |
| `EXPECTED_CALIBRATION_FAILURE` | 原初要求明确把失败当作磨刀输入；节点在既定边界内失败并暴露了具体字段缺口。 | 修订对应字段，保留负控制，不把失败写成理论结论。 |
| `IDEA_SPEC_INCOMPLETE` | 原初理念没有错，但当前工具规格漏掉了它已明确要求的条件。 | 增补/拆分 P1-P3 条件，写控制与回归；不能事后声称旧规格已包含它。 |
| `EXECUTION_DEVIATION` | 实际运行越过、跳过或替换了原初流程，例如泄漏、跨层、过早进入 ZFC 结论、将 site 当 Q。 | 停止受影响路径，标 stale，恢复正确顺序；保留错误和纠正收据。 |
| `RUNNER_OR_EVIDENCE_FAILURE` | 网络、provider、权限、超时、缺收据或来源不足使节点不能回答。 | 与模型／理论判词分开；修 NodeCard、runner health 或 source pack，不从失败推出数学结论。 |
| `ORIGINAL_IDEA_CHALLENGED` | 有直接来源、控制或同一任务反例显示原初要求的某一经验预期不成立。 | 说明具体哪一句被挑战，保持用户原话身份，向用户提出可审裁定；不得由 Master 静默改写。 |

“模型未命中”本身不能直接归类为 `ORIGINAL_IDEA_CHALLENGED`：用户说的是 **P 被写清楚以后**应产生线索。先要判断 P 当时是否已满足完整规格、输入是否真盲、理论是否是同一变体，以及 runner 是否健康。

## 4. 强制对照问题

每张 `SelfAuditCard` 至少回答：

1. 当前节点审的是理论 X 的显眼基础承诺，还是被熟悉叙事带到元语言／局部例子？
2. P1、P2、P3 是否仍是不同职责，还是某一把刀替另一把刀填了字段？
3. P2 的逻辑余式是否被误写为 P3 的“算符先于存在性落定”，或反过来？
4. HoTT 无泄漏重放在本轮成功了吗？若没有，ZFC 工作的身份是否仍是校准／控制，而非对 ZFC Q 的最终定位？
5. P 的“一遍匹配”是否只被用于首轮线索，后续来源／Battle 是否没有被误说成一遍成功的证明？
6. 每个 worker 的模型、effort、可见材料、source pack、**experiment root 与祖先 AGENTS 链**、observation cadence、operator-review rule、终态与 output 是否实际可复核？经过多少秒不得被写成隐含 deadline，当前 runner 也不得接受自动墙钟中止配置。
7. source card 是否把公式／定义名误当成当前理论已经断言的义务；它是否逐项扫描 formation、definition、公理／假定、定理前提与 supplied witness，分清未支付、条件支付与已经直接支付？
8. 出现不对齐时，是什么：原初理念被直接反证、规格遗漏、执行偏差，还是 runner/evidence 故障？
9. 本单元是否需要新刀具？只有当存在独立理论职责、非 P1/P2/P3 的失败模式、最小正负控制和 ZFC 同卡贡献时才创建；运行器、文档或来源收据缺口不自动成为 P4。

## 5. Git 审计链

一项 `IDEA_SPEC_INCOMPLETE`、`EXECUTION_DEVIATION` 修复、`RUNNER_OR_EVIDENCE_FAILURE` 防错，或经过控制的 `ALIGNED` 刀具修订，均按本项目 Git 合同进入精确路径 commit：先 baseline、后 source/contract/evidence 写回，再跑结构、JSON、diff 和受影响验证，最后回读 commit 与 current owner。Git log 证明历史可追溯，不证明 P、ZFC 或 HoTT 的数学结论。

`NO_CHANGE` 也应在本轮 audit 中写明理由；不能为了制造 Git 记录重复提交未改变的规格。

## 6. observation-first 终止纪律

盲态或 source-aware 理论节点的默认政策是可观察的继续运行，而不是短墙钟中止：NodeCard 必须给 `observation cadence` 和 `operator-review rule`；runner 只写私有 `STILL_RUNNING`，不得按经过时间自动 `turn/interrupt`。每一次状态还必须追加到 `run-liveness.jsonl`，保留 `sequence`、elapsed、thread／turn、工具计数和状态；`run-liveness.json`只作最新快照。预算、成本、失联或用户取消是 Master 的复核输入，不是 runner 的秒表触发器。若未来需要人工 interrupt，先单独资格化控制器、权限、race 和 terminal receipt；本 SOP 不把该未验证能力写成已经可用。

历史 NodeCard 保留其当时的 timeout 字段，不能为让文档一致而回写。若没有超过一个观察窗的真实 node，则“liveness 足以支持长期观察”仍是 `NOT_YET_RUNTIME_TESTED`；CLI 参数校验或自然终态只能支持较弱范围。

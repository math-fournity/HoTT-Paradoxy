# 运行引擎、验证与治理影响

## 1. 运行引擎选择

| 引擎 | 适用节点 | 当前资格 | 必须记录 |
|---|---|---|---|
| fresh Codex CLI | 已获允许的非盲态 source/control | `P-DAG-BATTLE-001` 证明一次 Battle smoke；HOTT-DISCOVERY-007 观测到 global-instruction/tool injection，空 `CODEX_HOME` health node则在采样前无认证 `401`，故本家族 `BLIND_CARD` 继续为 `CONTEXT_ISOLATION_AND_AUTH_NOT_QUALIFIED` | model/effort banner、sandbox/approval、scratch root、prompt/output hash、终态、实际可见上下文与 tool-event 边界 |
| Codex App Server facade | 单一受控盲态节点；未来多 worker 生命周期、观察者、取消与同一 Battle DAG 的动态编排 | `governance-v3.26.0` direct wrapper已通过zero-material health与HOTT-DISCOVERY-008的Terra/Max no-tool terminal run；共享Broker的一般 sandbox forwarding、observer ACL与取消路径仍未由此资格化 | thread/start、turn/start、model/effort、sandbox/approval回显、worker/session/turn ID、private wire、prompt-input、auth gate、cancel/terminal receipt |

本机 `codex-cli 0.157.0` 的 App Server schema 有 `thread/start`、`turn/start`、`sandbox`、`approvalPolicy`、`model` 与 `effort` 字段。共享 `agent_session_broker.py` 已把 Codex 标为 `app-server` 的 ACP-compatible facade。当前阅读到的 broker adapter 尚未在 `new_session` 转发 schema 的 `sandbox` 字段，因此 App Server lane 在获得“read-only sandbox + approval=never 的实际回显”之前标为：

```text
APP_SERVER_PERMISSION_FORWARDING_NOT_QUALIFIED
```

这不是 App Server 不可用的断言；它限制的是共享 Broker adapter 尚未实证的 sandbox forwarding。HOTT-DISCOVERY-007 还证明 fresh CLI 的 `--ignore-user-config --ignore-rules` 和 `/tmp` cwd 不足以证明盲态：global instructions仍可注入并诱导 tool call。随后空 `CODEX_HOME` + keyring health node在模型采样前认证失败。`governance-v3.26.0`的 direct wrapper改用run-scoped home/state、text-only workspace、pre/post deny gates和受控临时0600 auth；health-005与HOTT-DISCOVERY-008实际回显 Terra/Max/cwd/approval/permission，prompt-input合格且无tool event。此资格只属于该 exact profile/NodeCard，不能以 prompt、CLI flag或 credential copy泛化为任意环境权限／上下文隔离。

## 2. 验证计划

1. **结构：** 分片、Skill 路由、AGENTS、README、任务路由与链接都可解析；
2. **NodeCard：** 一张盲态 P1 card、同卡 P2/P3、一个 source-tracer card 和一个 Battle pack 被分别检查为不泄漏；
3. **实际行为：** `P-DAG-BATTLE-001` 已使用已有 consumer conflict 完成两个 source-isolated 立场节点和一个仅消费 sealed pack 的 CLI arbiter；`P-DAG-SOURCE-001` 已用两个 `PRIMARY_WEB_SOURCE` 节点与同卡 P2/P3 并行 mapper 验证 source→freeze→differential-map 路径；`P-DAG-SOURCE-002` 进一步以 Metamath proof-layer card、Isabelle/ZF formula-semantics card 与 P3 negative control 验证同卡差分；`BATTLE-002` 将 proof-system C 与对象／语义／runtime C 分开，驱动 L2c/layer-integrity 门；判词见相应 audit；
4. **App Server：** health-005与HOTT-DISCOVERY-008已证明 exact Terra/Max、approval/permission/cwd/effort echo、private wire、prompt-input/auth gate和normal terminal；observer ACL、共享Broker sandbox forwarding、explicit cancel/late race仍未验证，不能借本节点升级；
5. **超时路径：** `P-DAG-SOURCE-003` 的三个 `PRIMARY_WEB_SOURCE` CLI 节点在 4 分钟观察窗无 terminal output 后由 Master `SIGINT` 停止；无 final artifact、无 source fact。它验证 timeout 必须有 prelaunch NodeCard、deadline 和 partial-output fail-closed 规则，不能被解释成来源负结论；
6. **连接失败路径：** `P-DAG-SOURCE-004` 已有预封存 source pack；foreground runner 回显 exact profile 后，在模型输出前因 `workspace routing discovery failed` 退出。它验证 `RUNNER_CONNECTION_FAILURE` 必须和 timeout、模型失配、source-negative verdict 分开记录；
7. **盲态隔离：** HOTT-DISCOVERY-007使H-005/H-006降为`CONTEXT_ISOLATION_NOT_QUALIFIED`，空-home HOTT-RUNNER-ISOLATION-002保留`401`控制。HOTT-DISCOVERY-008在R-035受控App Server lane上完成 sealed D-L6b Prompt的无工具终态；其 Π/h-level candidate被Book `hlevel-prod`支付，成为 discovery→source-validation control，不是HoTT release。新的blind node只可复用同一exact lane或先重做其隔离资格；
8. **数学边界：** 上述验证只证明编排与证据路径，不证明 ZFC Q、HoTT 悖论或任何数学命题。

## 4. 完成和退役

本 SOP 成功的标准是未来 Master 能据 TaskCard 选择必要节点、隔离不该见的材料、让分歧触发有界 Battle，并把最终判断回到来源和同一任务；不是每次都启动多个代理。若未来共享 App Server adapter 得到权限资格化，更新本片的运行状态；若 P 的共同锻造停止或被用户替代，保留本片为历史证据，并让当前 README/AGENTS 路由指向替代方法。

### 1.1 同一隔离 lane 的两种输入 profile

`scripts/pattern_p_appserver_blind_discovery.py` 现有两个彼此不替代的 profile。它们复用 run-scoped home、text-only workspace、prompt-input、pre/post auth deny gate、exact echo、private direct wire 与 observation-first 终态纪律；它们的**可见输入**和**输出 oracle**不同。

| Profile | NodeCard access | 可见输入 | prompt-input 禁止项 | 输出 oracle | 能支持什么 |
|---|---|---|---|---|---|
| `blind-discovery` | `BLIND_CARD` | 仅脱敏理论画像和 P-DISCOVERY 指令 | 项目根、既有答案、指定 source、ZFC标记、工具系统名 | D0/D1/D3–D5 + D2标题或独立精确终态行，且唯一 candidate，或与理由一致的`DIRECT_PAYMENT_ONLY`／`FORMATION_ORIGIN_NOT_SUPPLIED`无候选终态 | 一遍匹配的 bounded 线索。 |
| `source-match` | `PINNED_LOCAL_SOURCE` | 唯一 frozen source card 加 P1、P2 或 P3 方法卡 | 项目根、旧 P1/P2/P3 report、旧 discovery output、工具系统名 | E0–E7 MatchTrace | 该 source 对 P1/P2/P3 字段的 source-aware 判词。 |

`source-match` **不是盲态重放**：它明确允许 source card，绝不允许用旧结论填字段。其 preflight 既确认 `BEGIN FROZEN SOURCE CARD` 与 source-profile，也拒绝项目路径和已知 P1/P2/P3/H010 输出标签。每张source-match prompt必须包含完整的精确 marker `You are a P-VALIDATION source mapper.`；P1/P2/P3的专门身份另起句。H031缺此marker而在模型采样前拒绝，故这个格式是runner输入合同，不是可选文风。新 profile 的空 workspace 仍不存 theory source；卡片只作为精确 turn input 提供。若它承担 P1 parent validation，prompt还必须封存父 discovery 的 T/u/F/Q?；source worker只能补、拒绝或收窄这些字段，不能重新挑一个对象冒充继承。若它核 P1 的 Q，NodeCard 还须明写 Q 在 T 中的 status（definition／assertion／goal／conditional theorem／supplied witness），并要求 L5b/L6/L7/L7b payment matrix以及固定顺序的`L2c/L5b/L6/L7/L7b` Gate Ledger；标签错置即`MATCHTRACE_GATE_LABEL_DRIFT`，不能以终稿语义近似替代字段验证。只有 NodeCard、prompt hash、source hash、thread/turn echo、terminal wire 和 trajectory receipt 全部存在时，才可把 E0–E7 读为该 source card 的外部 worker行为。

H063–H066补出一个更早的输入合同：上述 marker 必须位于 runner 实际抽取的**唯一**标注为 `text` 的 fenced block 内。H063缺 payload，H064虽有 payload却缺冻结 source-card boundary，二者均在模型采样前拒绝；H065通过 profile 但把 `PS0–PS6`写成任意 source-fact 序列，故其 ledger 不能接受。后继 H066 只补精确 ledger 问题标签并通过。故所有新的 source-match 节点启动前都要调用 runner 的 `read_frozen_turn`，再在抽取 payload 中核 marker、source-card boundary、所要求的 E3继承字段和 E6/Gate Ledger 字段。该 preflight 不替代 prompt-input deny gate、模型／权限回显、terminal或TrajectoryReceipt；它只把本可在采样前发现的格式错误停在采样前。

对于`blind-discovery`，无候选终态也必须如实说明**为何**没有候选：既有`NO_MODEL_RECALL_CANDIDATE / DIRECT_PAYMENT_ONLY`保留给 F 已直接回答所问 Q? 的情形；`NO_MODEL_RECALL_CANDIDATE / FORMATION_ORIGIN_NOT_SUPPLIED`只用于已尝试 D-L10F 却未从明确 formation 中得到不等于存在重述的完成性／自指追问。runner 接受这两个互斥的精确 no-candidate terminal；不能把后者伪写成 direct payment，也不能让一个prompt出现两个终态。

每个 App Server node 同时写两份私有 liveness 证据：`run-liveness.json`是最新快照，`run-liveness.jsonl`是按单调序号追加的完整状态序列（`RUNNING`、每个`STILL_RUNNING`与`TERMINAL`）。当前 schema 为 `p-dag-<profile>-liveness/v2`，显式写入`automatic_wall_clock_interrupt=false`；历史 v1 收据保持原样。前者便于实时观察，后者使“超过观察窗仍继续运行”成为可回放的证据；只有最终快照、没有历史序列时，不能把长期观察说成已留存。

### 1.1.1 实验根与祖先指令链

`CODEX_HOME` 隔离只约束 home、config、auth 和 sqlite；它不会自动切断 `cwd` 向父目录寻找 `AGENTS.md` 的行为。因此 run-scoped home 与 text-only workspace 必须放在业务项目根以外的独立 experiment root。若把 `private-root` 放进业务项目的`private-audit/`，预检会在 project `AGENTS.md` 的祖先链上失败或污染可见上下文，即使 prompt 本身没有泄漏答案。当前 runner 在认证和模型采样前拒绝这种布局；失败状态是`RUNNER_OR_EVIDENCE_FAILURE / NO_AGENT_OUTPUT`，新外部根必须使用新的 run ID。这个约束不禁止项目保留 private trajectory；它只规定运行时 experiment root 不能是该项目的后代。

profile 选择不得改变 P1/P2/P3 的数学职责：P2 仍要有合法 Bind/Form/Bridge/Reenter；P3 仍要有 source-backed Draft/Admitted/OperatorUse 边。`source-match` 只是补足 H010 之后的验证接力，不能因能读 source 就回写盲发现的结果。

本机 `codex-cli 0.157.0` 的 App Server schema 有 `thread/start`、`turn/start`、`sandbox`、`approvalPolicy`、`model` 与 `effort` 字段。共享 `agent_session_broker.py` 已把 Codex 标为 `app-server` 的 ACP-compatible facade。当前阅读到的 broker adapter 尚未在 `new_session` 转发 schema 的 `sandbox` 字段，因此 App Server lane 在获得“read-only sandbox + approval=never 的实际回显”之前标为：

```text
APP_SERVER_PERMISSION_FORWARDING_NOT_QUALIFIED
```

这不是 App Server 不可用的断言；它限制的是共享 Broker adapter 尚未实证的 sandbox forwarding。HOTT-DISCOVERY-007 还证明 fresh CLI 的 `--ignore-user-config --ignore-rules` 和 `/tmp` cwd 不足以证明盲态：global instructions仍可注入并诱导 tool call。随后空 `CODEX_HOME` + keyring health node在模型采样前认证失败。`governance-v3.26.0`的 direct wrapper改用run-scoped home/state、text-only workspace、pre/post deny gates和受控临时0600 auth；health-005与HOTT-DISCOVERY-008实际回显 Terra/Max/cwd/approval/permission，prompt-input合格且无tool event。`governance-v3.26.1`后来只补齐 direct-wire trajectory reader。此资格只属于该 exact profile/NodeCard，不能以 prompt、CLI flag或 credential copy泛化为任意环境权限／上下文隔离。

### 1.2 App Server 终态后的 trajectory 双证据

从 H008 起，App Server `thread/start`／`turn/start`回显和 `TrajectoryReceipt` 是不同证据面：前者证明本次请求与
Host回显的配置；后者从私有双向`{timestamp,direction,message}` wire重建实际 thread、turn、item、tool/approval、
visible message和terminal。当前 shared reader（`governance-v3.26.1`）能够解析该 direct wire；它不把 wire伪装成
`rollout-*.jsonl`，也不把 `item/reasoning/summary*`写成完整 reasoning。

| 层 | H008 的可支持状态 | 不可补造的部分 |
|---|---|---|
| L1 context injection | `NOT_TESTED` | `instructionSources`与prompt-input gate只证明路径／禁止标记，不给完整 injected system body |
| L2 selected-read coverage | `NOT_OBSERVED` | wire中的0 tool call/result不等于证明任何文件被完整读取或没有未导出工具 |
| L3 model recall | `NOT_TESTED` | public discovery trace不是独立 recall 实验 |
| L4 cognition execution | `REQUIRES_SEMANTIC_REVIEW` | terminal与事件序列不自动证明P被正确消费 |
| L5 behavior verdict | `REQUIRES_ACCEPTANCE_EVIDENCE` | NodeCard output-contract和source tracer只证明各自范围 |

H008 的 direct wire 有496条record（4 outbound／492 inbound），tree显示一条terminal turn、0个tool call/result/approval、
455个assistant message delta、3个reasoning summary item和6个summary delta。完整 prompt、assistant text和context extract
均保持0600私有。没有 persisted rollout 时必须报告`PERSISTED_ROLLOUT_UNAVAILABLE /
BIDIRECTIONAL_APP_SERVER_WIRE_AVAILABLE`；不允许把 activity-block的zero block或reader的旧`unknown`当成零行为。

## 2. 验证计划

1. **结构：** 分片、Skill 路由、AGENTS、README、任务路由与链接都可解析；
2. **NodeCard：** 一张盲态 P1 card、同卡 P2/P3、一个 source-tracer card 和一个 Battle pack 被分别检查为不泄漏；
3. **实际行为：** `P-DAG-BATTLE-001` 已使用已有 consumer conflict 完成两个 source-isolated 立场节点和一个仅消费 sealed pack 的 CLI arbiter；`P-DAG-SOURCE-001` 已用两个 `PRIMARY_WEB_SOURCE` 节点与同卡 P2/P3 并行 mapper 验证 source→freeze→differential-map 路径；`P-DAG-SOURCE-002` 进一步以 Metamath proof-layer card、Isabelle/ZF formula-semantics card 与 P3 negative control 验证同卡差分；`BATTLE-002` 将 proof-system C 与对象／语义／runtime C 分开，驱动 L2c/layer-integrity 门；判词见相应 audit；
4. **App Server：** health-005与HOTT-DISCOVERY-008已证明 exact Terra/Max、approval/permission/cwd/effort echo、private wire、prompt-input/auth gate和normal terminal；H008又以 direct-wire `TrajectoryReceipt`证明该次wire能重建thread/turn、tool/approval=0、summary-only reasoning和terminal。`source-match` 随后在 H011/P2 与 H012/P3 取得 actual terminal、E0–E7、0 tool/result/approval 与 direct-wire receipt；H015–H017将这种差分推进到具体 universe card：blind P1定位`U + process-wide completion`，同卡 P2/P3分别得`P2_NOT_APPLICABLE`、`COMPLETION_PROCESS_NOT_ADMISSION_CYCLE`。H025/H026 的预认证失败进一步分离出安全-home读取与项目祖先AGENTS两个运行条件；H027从项目外 experiment root 完成同字节 source-match，取得prompt-input PASS、exact Terra/Max/permission echo、0 tool/file/approval及正常terminal。H028在同一 qualified 外部根上首先停在`SOURCE_CONSUMER_GAP`，但作为字段控制核出了公式—断言—支付区别：实际 Isabelle/ZF source只定义AC0，故没有活跃Q；假设将AC0作为公理断言时，Q虽为正义务却被该公理直接支付，促成L5b/L7b。H029随后以实际`AC` axiomatization证明payment内容可以source-match，却暴露Gate标签漂移；H030在同source上以强制五行Ledger回归通过，维持`QUALIFYING_PROOF_SYSTEM_CARD / SOURCE_PACKET_DIRECT_PAYMENT`而不越级为ZFC Q。H031的P3 node在采样前因profile marker失败，H032只修marker后在同source卡获得`CONSTRUCTION_SEMANTICS_NOT_SUPPLIED`，不把proof local witness升级为B向对象构造。H033/H034在更丰富的Zorn/TFin object-language card上分别确认static closure和source-consumer gap；二者仍无Q。H035–H042完成D-L10 discovery行为链：开放画像重识别全子对象，closed-menu selector被父source拒绝，RepFun直接支付函数像，最终平衡画像fresh返回valid no-candidate；H040/H041的D2 false negative由runner v2 oracle在H042 fresh回归修复。它限定性通过该外部根的运行链与这些source cards，不证明B-direction admission loop、HoTT不一致或ZFC Q。H013/H015/H017/H027/H028/H030/H033/H034/H036/H038/H042 已在真实长节点中证明追加式 liveness JSONL 保留每个观察窗；observer ACL、共享Broker sandbox forwarding、explicit cancel/late race、完整 injected context和L4/L5仍未验证，不能借本节点升级；
5. **历史中断控制：** `P-DAG-SOURCE-003` 的三个 `PRIMARY_WEB_SOURCE` CLI 节点在预封存的4分钟 source观察窗无 terminal output 后由 Master `SIGINT` 停止；无 final artifact、无 source fact。它只验证该历史 CLI source-node 的预注册、partial-output fail-closed 与失败分类，不能被解释成来源负结论，也不能成为 App Server 理论节点的时间上限。当前 App Server runner 刻意不提供对应的自动中断路径；人工取消控制器仍是未资格化的独立能力；
6. **连接失败路径：** `P-DAG-SOURCE-004` 已有预封存 source pack；foreground runner 回显 exact profile 后，在模型输出前因 `workspace routing discovery failed` 退出。它验证 `RUNNER_CONNECTION_FAILURE` 必须和 timeout、模型失配、source-negative verdict 分开记录；
7. **盲态隔离：** HOTT-DISCOVERY-007使H-005/H-006降为`CONTEXT_ISOLATION_NOT_QUALIFIED`，空-home HOTT-RUNNER-ISOLATION-002保留`401`控制。HOTT-DISCOVERY-008在R-035受控App Server lane上完成 sealed D-L6b Prompt的无工具终态；其 Π/h-level candidate被Book `hlevel-prod`支付，成为 discovery→source-validation control，不是HoTT release。新的blind node只可复用同一exact lane或先重做其隔离资格；
8. **数学边界：** 上述验证只证明编排与证据路径，不证明 ZFC Q、HoTT 悖论或任何数学命题。

### 2.1 H043–H047：历史 AI 来源的并行 P2/P3 差分与长观察

历史 Gemini proof-search 草稿先以 H043 在单一 P1 source-match 节点中运行 152.829 秒；私有liveness记录了`RUNNING → STILL_RUNNING@61.539s → STILL_RUNNING@121.548s → terminal`，全程无自动interrupt、command、file change或approval。它给出 external proof-search / source-consumer gap。随后 P2/P3 作为独立分支启动：H044/H045 都在模型采样前暴露 exact source-profile marker缺失，保留为输入合同失败；H046/H047 只修 marker 后在独立 private roots 中并行终态，分别得到 external algorithm time 不等 theory admission、representation 不等 same-object re-entry。它验证动态 DAG 能把同一文本的层次、编码与构造语义拆给不同刀具，而不是让一个worker用“有循环”同时填完三门。其 wire仍只证明本次行为、输入gate、0工具和terminal；不证明完整context、L4/L5、ZFC Q或数学结论。

## 4. 完成和退役

本 SOP 成功的标准是未来 Master 能据 TaskCard 选择必要节点、隔离不该见的材料、让分歧触发有界 Battle，并把最终判断回到来源和同一任务；不是每次都启动多个代理。若未来共享 App Server adapter 得到权限资格化，更新本片的运行状态；若 P 的共同锻造停止或被用户替代，保留本片为历史证据，并让当前 README/AGENTS 路由指向替代方法。

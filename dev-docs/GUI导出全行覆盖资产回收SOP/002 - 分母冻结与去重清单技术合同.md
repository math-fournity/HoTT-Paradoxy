# 分母冻结与去重清单技术合同

## 1. 行与字节的精确定义

- 行定义：文件内容按 `b'\n'` 切分；若末元素为空字符串则不计入行数。第 N 行（1 基）＝切分结果的第 N-1 个元素（不含换行符）。总行数 L(f)。
- 行的字节切片：从该行首字节的文件偏移到该行末字节（不含 `\n`）；块的哈希对"首行偏移到末行换行符（若原文件该处有换行）"的连续字节切片计算。脚本用累计偏移表实现，禁止逐行拼接近似。
- 每文件另记整体 SHA-256 与字节数。

## 2. Phase 0：身份冻结

脚本 `scripts/audit/gui_export_freeze_manifest.py`（执行期创建）：

1. 读八份导出，计算每文件 SHA-256、字节数、L(f)、首行内容（标题行）；
2. 记录冻结锚：执行时的 `git rev-parse HEAD`、八文件在 Git 中的 blob OID；
3. 生成抽样种子：`seed = sha256("GUI-ASSET-RECOVERY-v1" + sha256(八文件按 tag 排序拼接的个体哈希))`；
4. 输出 `audit/GUI-ASSET-RECOVERY/manifest.json`（schema 见 §5）。

**失效条件**：任一文件 SHA-256 改变 → manifest 作废，义务分母与账本中的 SHARED_POINTER 需重算（READ 收据按块哈希重验，仍一致的保留）。

## 3. Phase 1：diff 式区间对齐（不是公共前缀）

### 3.1 为什么不能用公共前缀（2026-10-07 探针冻结事实）

当日探针（python 逐行比较，首行起）确认的**首分歧行**：

| 子线 | 与 dev-08 首分歧于 | 与逻辑父首分歧于 |
|---|---|---|
| dev-01 | 15,556 | —（父=dev-08） |
| dev-02 | 13,132 | 与 dev-01：13,132 |
| dev-03 | 10,850 | —（父=dev-08） |
| dev-04 | 10,850 | 与 dev-03：12,278 |
| dev-06 | 14,596 | 与 dev-01：14,596 |
| dev-07 | 14,596 | 与 dev-06：14,702 |
| dev-09 | 15,891 | 与 dev-01：15,556 |

同时冻结的反例：dev-03 与 dev-08 首分歧于 10,850，但 dev-03 第 11,367 行仍含共享内容（与 dev-04 对齐），而 dev-08 的同内容在 11,450——**局部插入/缺失后内容会重新对齐**。因此首分歧点≠分叉点，公共前缀法必然漏读；必须用能找出**全部极大相同区间**的 diff 式对齐。

### 3.2 对齐算法合同

1. **阅读顺序**（逻辑分叉树，根优先）：`dev-08 → dev-03 → dev-04 → dev-02 → dev-06 → dev-07 → dev-01 → dev-09`。
2. 维护"已覆盖行集"（此前文件的行区间及其内容指纹）。对当前文件按顺序处理：
   - 用行序列 diff（`difflib.SequenceMatcher` 或解析 `git diff --no-index --unified=0`；二者择一，manifest 记录所用方法）将当前文件对**已覆盖内容库**对齐；
   - 极大逐字节相同行运行（identical run）长度 ≥ **3 行**者判 `SHARED`，记录来源文件与来源行区间（指针）；< 3 行的短运行**不判共享**（防 `## Codex` 这类高频短模板造成假去重），按义务行处理；
   - 其余行为 `UNIQUE`，计入义务分母 D；
   - 本文件自身的 UNIQUE 与本文件新贡献给内容库的行，读完后进入"已覆盖行集"。
3. 保守方向：任何不确定（如对齐算法差异、编码歧义）一律归入 UNIQUE（多读不漏读）。八份文件的首行（各自标题）天然 UNIQUE。
4. 输出去重清单：每文件一组不重叠、全覆盖的区间标注 `{range, UNIQUE|SHARED→(src_file, src_range)}`；`Σ 各文件行数 = SHARED 行数 + UNIQUE 行数`（脚本断言）。

### 3.3 义务分母

`D = Σ UNIQUE 行数`。按 3.1 探针估算 D ≈ 3.1 万行（上限估计 ≤ 4 万；以脚本输出为准）。执行中允许的对齐变更：仅当发现脚本缺陷时，重新运行 Phase 1 并在账本追加 `REALIGN` 条目记录差异；已 READ 且块哈希仍验过的收据不变。

## 4. 验证脚本合同

`scripts/audit/verify_gui_line_coverage.py`（执行期创建，D1 的机器裁判）：

1. 重算八文件身份 → 与 manifest 比对；
2. 重放 Phase 1 对齐 → 与 manifest 去重清单比对（SHARED 指针区间逐字节重验相等）；
3. 对账本每条 READ/RELOAD 收据：按其行区间重算字节切片哈希 → 比对；
4. 按账本与 manifest 合并计算全行归类，输出 remainder（= 全行数 − 已归类行数）；
5. 按种子重抽样，与 D1 引文逐条比对（§004 规则）；
6. 输出 `coverage.json` 与人类可读 `PASS/FAIL` 明细；退出码非 0 即 FAIL；
7. **echo 复核（裁决 #2）**：重算 `echo/` 存档各行 SHA-256，与 `echo-log.jsonl` 记录及 `PROTOCOL-ANCHORS.json` 锚表逐条一致；
8. **token-log 复核（裁决 #1/#2）**：每条 READ/RELOAD 收据区间在 `token-log.jsonl` 有记录，缺失清单与笔记/账本的豁免记录一致；
9. **互锁复核（裁决 #2）**：负例抽查——构造缺前置条件（无笔记节/无 token 记录/无账目且无 NO_ASSET 行/seq 跳号）的收据请求，验证 `--receipt` 确实 REFUSE。

## 5. manifest.json schema（要点）

```json
{
  "schema": "gui-asset-recovery/manifest/v1",
  "frozen_at": "<ISO>", "head": "<OID>",
  "seed": "<hex>",
  "files": [{"tag": "dev-08", "path": "...", "sha256": "...", "bytes": N, "lines": N, "title_line": "...", "blob": "<OID>"}],
  "alignment": {"method": "difflib|git-diff", "order": ["dev-08", ...],
    "per_file": [{"tag": "dev-03", "ranges": [{"start": 2, "end": 9850, "status": "SHARED", "src": ["dev-08", 2, 9850]}, {"start": 9851, "end": 13603, "status": "UNIQUE"}]}]},
  "obligation_lines": D, "total_lines_all_files": T,
  "sample": {"k_per_file": 20}
}
```

（区间数值为示意，以脚本输出为准；manifest 不进入本 SOP 正文。）

# 执行者工作集、压缩边界与审计清单

> 本片存在的原因（研究发起人 2026-10-07 裁定 R-4）：执行将在**全新会话**进行，**可能由非建案模型**承担，可假设约 **100 万 token** 上下文；执行结果将来由**另一个 AI 审计**。因此本 SOP 不得依赖任何先前会话记忆，必须把"跨压缩边界后什么需要完全重载"写成显式协议，并把全部流程清单化。

## 1. 执行者中立性合同

1. 本 SOP 可在任何具备文件分段读取、文件写入、Python 执行能力的 AI 宿主上执行；不依赖特定厂商、模型、Skill 菜单或本仓库以外的任何记忆；
2. **唯一状态载体是仓库文件**：SOP 五片、闭包、`manifest.json`、`ledger.jsonl`、`notes/`、两个脚本。执行者的对话记忆、自我印象、"我记得读过"**都不是证据**；
3. 中途更换模型天然被支持：新模型从 CL-A（会话启动清单）进入即与原执行者等价；
4. 执行者对语料的任何内容断言，只能来自**当前上下文中实际出现的原文**；出上下文的内容按 §4 重载后再用；
5. 执行者发现 SOP/闭包与现场事实冲突时：停下，在账本追加 `{"kind":"PROTOCOL_NOTE",...}` 登记冲突，按闭包§7失效条款处理；不得静默绕过；
6. **摘要非权威（裁决 #2，2026-10-07）**：对话内摘要——包括系统压缩摘要、历史转述、以及执行者自己的回忆——都不是本 SOP 的权威文本；与盘上五片＋闭包冲突时一律以盘上为准，并登记 `PROTOCOL_NOTE`。跨压缩边界后唯一合法的"我记得方案"证据是 protocol-echo 通过记录（003 片 §9.10）。

## 2. 常驻工作集（任何时刻，以下内容必须在当前上下文中；缺任一项→执行 CL-BR）

| # | 内容 | 来源 | 体积估计 |
|---|---|---|---|
| W1 | 任务合同＋三项裁定＋完成门 | SOP 001 | ~2k token |
| W2 | 阅读与收据协议要点 | SOP 003 | ~2k |
| W3 | 本片清单（CL-A…CL-E） | SOP 005 | ~3k |
| W4 | manifest 摘要：八文件身份＋**当前文件**义务区间表＋全局进度（covered/D） | `manifest.json`＋账本末条 | ~1k |
| W5 | 账本尾部最近 ≥10 条收据＋assets-ledger 尾部（最近 ≥10 行） | `ledger.jsonl`、`assets-ledger.md` | ~3k |

合计 ~13k token 量级——远小于任何现代上下文；问题从来不是放不下，而是**压缩后要意识到它们没了并重载**。

## 3. 压缩边界协议

**触发判定（满足任一即按压缩边界处理）**：① 新会话开始；② 被系统或用户告知发生了压缩；③ 自检发现 §2 工作集任一项不在当前上下文；④ 对某块是否已读/读过什么没有把握。

**CL-BR 压缩后恢复清单（按序执行，全部完成前禁止一切产出性写作）**：

- [ ] 1. 停止一切写入（包括"顺手补一条笔记"）；
- [ ] 2. 重载 `认知闭包/GUI-ASSET-RECOVERY-001.md`（全文，含 §8 裁决记录）；
- [ ] 3. 重载 SOP 001、003、005 三片（002/004 在涉及 Phase 0/1 与终期时再载；各片"修订记录"节必读）；
- [ ] 4. **protocol-echo（裁决 #2）**：从重读的正文中逐字节摘出 `PROTOCOL-ANCHORS.json` 全部锚句（一行一句）写入临时文件，运行 helper `--echo-file … --echo-kind CL_BR`，全匹配（exit 0）才准继续——未通过不得进入第 5 步；
- [ ] 5. 重载 `manifest.json` 摘要并核验八文件 SHA-256 未变（改变→002 片§2失效流程，中止并登记）；
- [ ] 6. 重载 `ledger.jsonl` 尾部 ≥10 条＋当前文件 `notes/` 尾部 ≥3 节＋assets-ledger 尾部；
- [ ] 7. 以账本计算第一个未覆盖义务行（**以文件为准，不凭记忆**）；
- [ ] 8. 恢复后第一块：先完整重读该块原文进入上下文，然后才允许为其写收据/笔记。

**铁律：不凭记忆续写。**压缩后"我记得这块讲了什么"不构成覆盖证据；只有该块原文此刻在上下文中，才能为它写或补笔记。

## 4. 完全重载对照表（什么场景必须重载什么）

| 场景 | 必须完全重载 | 说明 |
|---|---|---|
| 会话启动／压缩后 | §2 全部（按 CL-BR） | 见 §3 |
| 从文件 A 切到文件 B | B 的义务区间表；A 的 `FILE_DONE` 账本条目 | 切换时在账本记 CHECKPOINT |
| 写 D2 某线章节 | 该线笔记全部节标题；本章将逐字引用的**每个**原文区间 | 每个区间一条 RELOAD 收据 |
| 写 D3 某资产条目 | 该资产首现行所在块 | 同上 |
| 写 D1 抽样引文 | 每条抽样行所在块 | 引文只能来自当前上下文中的原文 |
| 审计质询（若仍在运行） | 被质询块 | 见 §6 |

## 5. 执行清单（执行者在 CHECKPOINT 条目中记录完成情况；2026-10-07 按裁决 #1 升级）

**CL-A 会话启动**（新会话或接手时）：
- [ ] 读闭包全文（**含 §8 设计者裁决记录**）；- [ ] 读 SOP 索引＋001/002/003/004/005 全片（**含各片"修订记录"节**）；- [ ] 若 `manifest.json` 不存在：按 002§5/004§4 合同写 `gui_export_freeze_manifest.py` 与 `verify_gui_line_coverage.py`，跑 Phase 0/1；- [ ] 若存在：跑身份核验；- [ ] 读账本尾部≥10条＋当前文件笔记尾部≥3节＋assets-ledger 尾部；- [ ] **protocol-echo（裁决 #2）通过**（helper `--echo-kind SESSION_START`，锚句全匹配）；- [ ] 定位第一个未覆盖义务行；- [ ] 在账本追加 `{"kind":"SESSION_START",...}`。

**CL-R 同会话恢复**（用户暂停后继续原会话、或设计者发出新裁决后；2026-10-07 新增）：
- [ ] 1. 核对自上次 CHECKPOINT 后，闭包 §8 与各片"修订记录"是否有新裁决/修订——有则**完整重读受影响节**，不得凭记忆；- [ ] 2. **protocol-echo（裁决 #2）通过**：从重读正文摘出全部锚句，helper `--echo-kind RESUME` 全匹配；- [ ] 3. 核验八文件 SHA-256 与 manifest 一致（脚本 REFUSE 即停并登记）；- [ ] 4. 采纳性登记：新裁决以 `PROTOCOL_NOTE` 入账；- [ ] 5. 若裁决要求回填（如裁决 #1 对 R0001–R0010）：按其 Q5 规则执行——块原文仍在上下文→注明"自上下文"直写；已不在→先记 RELOAD 收据再写；- [ ] 6. 回填后运行 token 覆盖检查（003§9.7），缺失全部补记或显式豁免；- [ ] 7. 账本追加 `{"kind":"RESUME",...}`，从 `next_gap` 继续。

**CL-B 每块循环（裁决 #1 后为五拍）**：
- [ ] 1. 确认工作集在位（否则走 CL-BR）；- [ ] 2. **CL-C 每文件完成**：- [ ] 义务行全覆盖；- [ ] `FILE_DONE` 条目（含收据数、行数、**assets-ledger 条目数、token 覆盖结果**）；- [ ] 笔记尾部写该文件 3–6 句小结（供 D2）。

**CL-D 终期**（对应 G1–G8）：- [ ] G1 身份与对齐重算；- [ ] G2 全部收据哈希重验；- [ ] G3 笔记完备＋笔记↔assets-ledger 1:1；- [ ] G4 抽样引文（先重载所在块）；- [ ] **G4b 每文件全区间 token 覆盖复跑**（全补记或全豁免）；- [ ] G5 D2 八线叙事；- [ ] G6 D3（以 assets-ledger 为原料）＋D4＋v1 标注；- [ ] G7 交叉一致抽查；- [ ] G8 remainder=0 总账＋闭包改 `TOTAL_CLOSED`。

## 6. 审计者清单（授权审计本次执行结果的 AI；研究发起人 2026-10-07 要求预留）

前提：审计者**不重读全部语料**也能完成核验。方法与执行者自检共用一套证据结构：

1. **脚本可信性先行**：两个脚本是执行者写的——审计者必须先读脚本源码，确认其实施了 002/004 合同（身份重算、对齐重放、逐收据哈希重验、抽样重验），或以独立实现抽查若干项；
2. **账本完整性**：append-only（若已入 Git，查提交历史）；收据区间对义务行不重不漏；
3. **笔记锚定抽查**：审计者用**自己的新鲜种子**随机选 ≥20 个收据，核对笔记中的行号锚定摘录与文件实际内容逐字一致；并以自己的参数独立复跑 `gui_asset_token_check.py`（003§9.7）核对每文件 token 覆盖与豁免记录；
4. **反向质询（"读过"的核心检验）**：审计者按新鲜种子抽 ≥10 块，用脚本从文件生成可机械验证的问题（该块 FileChange 胶囊的全部路径清单、用户轮首句、出现的资产名/判词字符串），与该块笔记比对；系统性缺失＝覆盖存疑，登记为审计发现；
5. **越权检查**：八文件与 `git-worktree对话录/README.md` 哈希未变；无数学结论措辞；账本无改写痕迹；
6. **产出审计报告**：逐项 PASS/FAIL＋证据定位，交研究发起人；
7. **执行力度复核（裁决 #2）**：`echo-log.jsonl` 与 `echo/` 存档重算哈希核对锚表（跨压缩边界的每次恢复都有 OK 记录）；`token-log.jsonl` 对每条 READ/RELOAD 收据区间覆盖核对；负例互锁抽查——构造缺前置条件的收据请求，验证 `--receipt` 确实 REFUSE。

## 7. 100 万 token 假设下的定量结论

- 去重后义务语料 ≈ 2.8–3.5 MB（探针外推；Phase 1 冻结后为准），按中文 UTF-8 ≈ 0.3–0.4 token/字节 ≈ **0.9–1.4M token**，另有笔记、收据、SOP、脚本开销；
- 结论：即使 1M 上下文，也无法全程常驻"全部原文＋全部笔记"；预计跨越 **1–3 次压缩边界**；本 SOP 不假设零压缩，也不因上下文大而放宽任何证据要求；
- 1M 上下文的真正收益：块上限可放宽至 600 行、单会话可完成更多块、CL-BR 重载次数更少——仅此而已。

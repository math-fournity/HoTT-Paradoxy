# 压缩边界、完全重载与执行清单

> 本片存在的原因：研究发起人要求，跨越压缩边界后，执行者的上下文必须"该有的都有，不该被压缩的，要重新完整加载"。执行者可能是新会话，甚至是另一个模型，因此本片不依赖任何先前会话的记忆，把压缩边界写成可检查的协议，把整个执行写成清单。

## 1. 基本原则

1. **磁盘即记忆**：所有决定、收据、笔记与游标，都必须先落盘，再被使用。
2. **摘要非权威**：压缩摘要、会话恢复摘要、他人的转述，以及执行者自己的回忆，都不是证据。与盘上内容冲突时，以盘上为准。
3. **不凭记忆续写**：压缩后，"我记得读过、写过"不构成任何证据。
4. **先重载，后写入**：任何写入之前，都必须完成本片要求的重载，使对应原文处于工作集之中。
5. **失败即停**：任何检查失败，停在当前位置，写 PARTIAL 或 NOTE，不得绕过。
6. **完整重载**的含义：用整读方式（分段读到 EOF）把全文读入上下文。不是 grep，不是摘要，也不是只看头部。

## 2. 工作集三分

- **不可压缩集**（压缩后必须整装重载，以盘上版本为准）：
  - (a) 本次闭包全文；
  - (b) 本 SOP 全部五片（含各片的修订记录）；
  - (c) `SESSION-REAUDIT.md` 全文；
  - (d) `seal-log.jsonl`（全文；若超过 1 MB，则读其全部 STAGE 与 UNSEAL 事件，以及最后 200 行）；
  - (e) `STATUS.md`（由 `cursor.py --refresh` 刷新后读取）；
  - (f) `ledger2.jsonl` 的最后 50 行，以及全部 RS、RC、NOTE 条目；
  - (g) 当前文件的 `notes2/<tag>.md` 全文、`classes2/<tag>.tsv` 全文，以及 `assets2.md`（若超过约 300 KB，则读当前文件相关条目与 ID 索引）；
  - (h) 当前块的原文（若该块尚未提交，须整读）；
  - (i) `PROTOCOL-ANCHORS2.json`（锚表，只含哈希与提示）。
- **可重建集**（需要时按范围重载）：语料中非当前块的原文；前一文件的笔记（仅在对照时）；第一战役产物（仅阶段 C）。
- **可丢弃集**（压缩后不需要）：推理过程、中间计算、已提交块的原文、临时输出（其结论已入盘的部分）。

## 3. 完全重载清单（按场景）

| 场景 | 必须完全重载 |
|---|---|
| 新会话启动 | CL-A2 的全部步骤 |
| 文件边界（tag 切换，预防性） | CL-F2 |
| 压缩或重启之后 | CL-BR2（§4） |
| 阶段切换（A 到 B、B 到 C、C 到 D） | 不可压缩集，加上该阶段的产物清单 |
| 写 R1 至 R5 任一交付物之前 | 该交付物的规格（004 §6）、其引用的全部数据文件，以及被引用的块原文（RR 收据） |
| 怀疑上下文失真（见 §7） | CL-BR2 |

## 4. CL-BR2：压缩边界恢复

全部步骤通过之前，禁止任何写入。

1. 停止写入。
2. 整读不可压缩集 (a) 至 (d)：闭包、SOP 五片、SESSION、seal-log。
3. 运行 `cursor.py --refresh`，整读 `STATUS.md`。
4. **protocol-echo**：从第 2 步读入的正文中，逐字摘出 `PROTOCOL-ANCHORS2.json` 的全部锚句，按锚表顺序、一行一句，写入 `echo/<时间戳>.txt`。运行 `echo_check.py`，全部匹配才继续（§5）。
5. **封印核验**：读取 seal-log 的最后一条 STAGE 或 UNSEAL 事件，它必须与 `STATUS.md` 的阶段一致。不一致则 PARTIAL。
6. **账本核验**：运行 `check_all.py --chain-only`，核对 prev 链，并随机重算三个 RA 的 chunk_sha256。失败则 PARTIAL。
7. 整读不可压缩集 (f) 至 (h)：账本尾部、当前文件的 notes2、classes2、assets2，以及当前块原文（若未提交）。
8. 写 RS 收据：`boundary_id`、`reload_list`（每个路径的字节数、行数、EOF 行号与 SHA-256）、echo 结果、游标（下一块 ID）、封印状态。只有 RS 收据写入之后，才允许继续。
9. 若恢复后的第一块尚未提交：该块的草稿节须追加 `[作废·块未提交]` 标注，然后从拍 1 重新开始。不得沿用压缩前的草稿。

## 5. protocol-echo

- **锚表**：`audit/GUI-ASSET-REAUDIT/PROTOCOL-ANCHORS2.json`，由设计者放置，只含 SHA-256 与提示，不含明文。每个锚点对应规范文件中的一整行，哈希值为该行 UTF-8 字节（不含行尾换行）的 SHA-256。
- **执行**：从重载的正文中逐字复制锚句，按锚表顺序写入 `echo/<时间戳>.txt`。运行 `echo_check.py`，它重算每行哈希，与锚表逐条比对，输出 OK 或 FAIL，并记入 `echo-log2.jsonl`。
- **失败策略**：FAIL 则不得继续。重新整读相应规范文件，再试一次；连续两次 FAIL，则 PARTIAL。
- **边界**：echo 只证明这些字节在本次上下文中被复制出来，不证明模型的内部状态。最终的兜底是审计者的独立核验（§9）。

## 6. 执行清单

### CL-A2 会话启动（新会话）

- [ ] 1. 写身份声明（SESSION §1）：宿主、模型家族，以及与第一战役的模型家族是否相同。相同则停止，报告研究发起人。
- [ ] 2. 写复述（SESSION §2）：原问（001 §1.1）、取舍（001 §1.3 与 §3）、过程（本 SOP 的阶段结构）、验收（001 §7），以及尚未知道的事。
- [ ] 3. 整读本闭包与 SOP 五片，在 SESSION 中记录每片的 EOF 行号与字节数。
- [ ] 4. 运行 P0 身份冻结（002 §2）。BLOCKED 则停止。
- [ ] 5. 建立 `tools/`，编写工具，并通过 `selftest/`。
- [ ] 6. 运行 P1 对齐（002 §3 至 §5），通过自检。
- [ ] 7. 写 seal-log：`STAGE_START A`；写 `SESSION_START2` 收据。
- [ ] 8. 进入阶段 A 的第一块。若 `ledger2.jsonl` 已存在，则不是 CL-A2，而是 CL-R2。

### CL-F2 文件边界（预防性）

- [ ] 1. 完成上一文件的全部块提交，并写 `FILE_DONE2`。
- [ ] 2. 执行 CL-BR2 的第 2、3、4 步，以及第 7 步。
- [ ] 3. 写 RS 收据，`boundary_id` 为 FILE_BOUNDARY。
- [ ] 4. 进入下一文件。

### CL-B2 每块五拍

- [ ] 拍 1：整读本块（003 §2）。
- [ ] 拍 2：写 notes2 节（003 §4）。
- [ ] 拍 3：写 classes2 与 assets2（003 §5、§6）。
- [ ] 拍 4：第二遍整读，按 003 §10 的检查表复读自检；补记（只追加）；运行 `reread.py`。
- [ ] 拍 5：运行 `commit_block.py --precheck`，再运行 `--commit`，写入 RA 收据；运行 `cursor.py` 刷新。
- 任一拍失败：不得跳过，保留草稿并标注，从失败的拍重做。

### CL-R2 恢复（同会话或新会话）

执行 CL-BR2 的全部步骤。然后读取 SESSION 中的"上次结束点"，并与 `STATUS.md` 的游标核对。

### CL-C2 阶段 C 启动

- [ ] 1. 确认 seal-log 中有 `STAGE_DONE A` 与 `STAGE_DONE B`。
- [ ] 2. 写 `UNSEAL` 事件（附理由）。
- [ ] 3. 每次打开第一战役路径，写一条 `ACCESS` 事件（路径与目的）。
- [ ] 4. 按 004 §3 的 C-01 至 C-08 执行。每项产出写入 R2、R3、R4、R5 的草稿，或以 ledger2 的 NOTE 记录。
- [ ] 5. 阶段 C 中的任何补正：只能以 RC 追加，依据必须是本次重读的原文（RR 收据）。

### CL-D2 终审

- [ ] 1. 重载不可压缩集与 R1 至 R5 的草稿。
- [ ] 2. 逐门核对 G'1 至 G'11（001 §7），每门写明证据路径。
- [ ] 3. 生成最终的 R1 至 R5。
- [ ] 4. 运行一致性检查（G'8）。
- [ ] 5. 写 R3 的总判词，以及 004 §5 的独立性自评。
- [ ] 6. 在闭包 §4 写两行判词，并把状态改为 TOTAL_CLOSED；若未通过，则改为 PARTIAL。

### CL-E2 中止与移交

- [ ] 1. 在 `ledger2.jsonl` 追加 `CHECKPOINT2`：`next_gap`（块 ID）、原因、未通过的门、未比对清单。
- [ ] 2. 更新闭包 §4：状态为 PARTIAL，并写移交指针。
- [ ] 3. 核对状态载体一致：闭包、SESSION、manifest2、ledger2、seal-log、STATUS、notes2、classes2、assets2。
- [ ] 4. 不宣称完成。
- [ ] 5. 接手者按 CL-R2 恢复。

## 7. 漂移自检

出现下列任一症状，立即执行 CL-BR2，不待确认：

- 没有重新看原文，就写出引文或行号；
- 想跳过某一拍，或认为"这块读过了"；
- 不确定封印状态或当前游标；
- 复读时发现笔记里有自己不记得写过的内容；
- 收据或笔记中出现"差不多""应该是""大概"之类的措辞。

## 8. 预算与检查点

- 不设消耗上限。检查点是块的提交（RA 收据）与文件边界（RS 收据）。
- 粗估（执行时以 P1 结果校正）：一遍读取独有行，约需 1M token 量级（按中文 UTF-8 每 2.5 字节约 1 个 token 估）。阶段 A 的第二遍读取与阶段 C 的重读是主要成本。整个执行可能累计数百万 token，跨越多次压缩边界。至少两次；规划时按十次以上计。
- 预算耗尽时，执行 CL-E2。不删减拍，不压缩已写内容。

## 9. 审计者清单（供后续审计者使用，不由执行者自检）

1. **封印**：seal-log 的 STAGE 事件单调；阶段 A 中没有第一战役路径的 ACCESS。若有，必须有 SEAL_BREACH 与 TAINT 记录。
2. **账本**：审计者用自己的脚本重算 prev 链与 RA 的 chunk_sha256。
3. **笔记**：审计者用自己的种子（不同于 B-12），抽取不少于 20 个块，从语料机械生成问题（该块的角色标记行、commit 候选、标题行清单、反引号标识清单），与 notes2 比对。
4. **压缩边界**：每个 RS 收据都有对应的 OK echo 记录；每个压缩边界都有 RS。
5. **反向质询**：抽取不少于 10 个资产条目，要求在语料指明行中找到其名称与引文；缺失则登记。
6. **重算判词**：审计者从 ledger2 与 notes2 独立重算 R2 的判词计数。
7. **越权**：八份语料与 README 的哈希未变；第一战役产物未被修改（若有前后快照则比对）；没有 commit、没有 push；没有数学结论措辞。

8. **补录**：按 004 §3 C-06 的互锁补录项，抽取不少于 3 次补录，独立核对补录内容与原文一致，且补录没有改写既有收据或笔记。

## 10. 修订规则

- 本 SOP 只能由研究发起人授权的设计会话修订，并在闭包 §8 写明日期、原因与影响范围。
- 执行者不得修改 SOP。发现冲突时，在 `ledger2.jsonl` 追加 `NOTE`（SOP_CONFLICT），并停止相应步骤。
- 修订后，旧版本保留（由 Git 历史保存）。已完成的阶段不因修订而重算，除非修订明确要求。

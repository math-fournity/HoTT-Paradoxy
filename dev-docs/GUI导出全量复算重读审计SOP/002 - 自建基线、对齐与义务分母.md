# 自建基线、对齐与义务分母

> 本片只规定阶段 A 之前的自建部分：身份、对齐、分块与自检。与第一战役的对账在 004 §3 的 C-02 执行，不在这里。

## 1. 行、字节切片与块哈希的定义

- **行**：语料字节按 LF（0x0A）切分。若文件以 LF 结尾，末段空串不计为行；否则非空的末段计为最后一行。第 k 行（1 基）的起始偏移记为 off(k)，off(1) = 0，off(N+1) = 文件字节数。
- **字节切片**：第 s 行至第 e 行的切片是 `bytes[off(s) : off(e+1)]`，包含每行的 LF。若文件中有 CR，按原字节保留，不做任何规范化。
- **块哈希**：`chunk_sha256(s, e) = SHA-256(切片)`。
- **行的相等**：按字节比较，不去除空白，不转码。行指纹 `fp(k) = SHA-256(第 k 行的字节，不含 LF)`。
- **编码**：按字节处理；需要显示或引文时按 UTF-8 解码。遇到非法序列不得静默替换，记为 ENCODING_ANOMALY（写入 ledger2 的 NOTE）。
- **长行**：字节数超过 2000 的行称为长行，按 003 §9 的窗口方法读取。

## 2. P0 身份冻结

1. `git rev-parse HEAD`，记入 SESSION。
2. `git -c core.quotepath=off ls-files -- git-worktree对话录`，取出语料文件。tag 为文件名中第一个 ` - ` 之前的部分。应得八个 tag；数量不对，BLOCKED。
3. 对每个语料文件：
   - `git rev-parse HEAD:<路径>` 得到 blob OID；
   - `git hash-object <路径>` 得到工作树 OID。二者必须相同，否则 BLOCKED；
   - 记录 `shasum -a 256 <路径>`、字节数与行数（按 §1 计算）。
4. `git status --porcelain -- git-worktree对话录` 必须无输出，否则 BLOCKED。
5. 写入 `manifest2.json`：

```json
{"schema": "gui-asset-reaudit/manifest/v1", "frozen_at": "<ISO>", "head": "<OID>",
 "files": [{"tag": "dev-01", "path": "<路径>", "blob": "<OID>", "sha256": "<hex>", "bytes": 0, "lines": 0}],
 "order": ["dev-01", "..."], "T": 0, "fingerprint": "<按 tag:sha256 的字典序拼接后的 SHA-256>"}
```

- `order` 为 tag 的字典序。这是本次独立选择的阅读顺序（§3.2），不得参照任何既有顺序。
- `T` 是本次自算的总行数，不预设。

## 3. P1 对齐

### 3.1 定义

- **相同运行（run）**：当前文件 f 与一个更早的文件 g 之间，连续 K 行逐行字节相等，且两侧同步连续。K = 5。
- **最大相同运行**：不能再向两端延伸的 run。
- **COVER(f)**：f 中落在某个长度不小于 K 的最大相同运行之内的行号集合（对所有更早的 g 取并）。
- **SHARED(f)** = COVER_A(f) ∩ COVER_B(f)，即两种方法（§3.3、§3.4）都判为共享的行。
- **UNIQUE(f)**：f 的其余行。
- **指针**：对 SHARED 行 p，取更早文件中与之匹配的行 (g, q)，其中"阅读顺序最早、行号最小"者。若 (g, q) 本身也是 SHARED，则沿指针解析到其规范位置。
- **规范出现（canonical occurrence）**：每个 UNIQUE 行是其内容的规范出现；SHARED 行的规范出现，是其解析后的 UNIQUE 位置。

### 3.2 阅读顺序

按 tag 字典序处理（dev-01 到 dev-09，缺号不补）。

### 3.3 方法 A：K-gram 哈希法

1. 对全部语料行计算指纹 fp。
2. 对已处理的文件建立 K-gram 索引：键为 K 个连续指纹组成的元组，值为（文件，起始行号）的列表。
3. 对当前文件的每个 K-gram 查索引，对每个命中向两侧延伸，得到最大相同运行，并入 COVER_A(f)。
4. 输出 run 列表：（当前文件与起止行，更早文件与起止行，长度）。

### 3.4 方法 B：git diff 法

1. 对每一对（更早的 g，当前的 f），执行 `git diff --no-index --unified=0 --diff-algorithm=patience -- <g 的路径> <f 的路径>`。注意：有差异时退出码为 1，这不是错误。
2. 从 hunk 头 `@@ -a,b +c,d @@` 推出未改动行的一一配对：两个 hunk 之间的行，按顺序配对。
3. 对每一对配对行做字节比较。不相等则记 ALIGN_ERROR，并停止该对。
4. 把连续配对合并为 run，丢弃长度小于 K 的 run，并入 COVER_B(f)。

### 3.5 取舍与指针校验

- COVER_A 与 COVER_B 不一致的部分，一律归入 UNIQUE（I8）。每处不一致写入 `align-disagree.jsonl`：文件、行号、哪一方判为共享、长度。
- 对每个 SHARED 行的指针：目标行必须字节相等，且所在 run 长度不小于 K。任一条件不满足，该行改为 UNIQUE。

### 3.6 结构断言

- 对每个文件：SHARED(f) 与 UNIQUE(f) 不重叠，且全覆盖 {1..N_f}。
- Σ N_f = T；Σ|SHARED| + Σ|UNIQUE| = T。这些断言由脚本执行，结果写入 `align2.json`。
- 不预设 UNIQUE 的数量。若某文件的 UNIQUE 为零，或数量异常，写明原因。不得为了"对得上"而改算法。

## 4. 块划分与指针表

- **块**（写入 `blocks.json`）：对每个文件，把 UNIQUE(f) 的连续段切分成块。
  - 上限：200 行，或 40 KB（按字节），先到者为准；
  - 块不跨文件；
  - 允许合并：相邻两段 UNIQUE 之间若只隔着不超过 5 行的 SHARED 小缝，可并入同一块。小缝内的行作为上下文一并读入，不计入义务，不分类；
  - 块 ID：`B-<tag>-<NNNN>`，NNNN 为该文件内的 1 基序号；
  - 每块记录：start、end（连续的行范围）、obligation 行号列表（可用区间表示）、上下文缝、字节数、整块的 chunk_sha256、最大行字节数。
- **指针表**（`pointers.json`）：每个 SHARED 行 → 规范位置（文件、行号、所在块 ID）。
- **冻结**：块划分在 P1 结束时冻结。阶段 A 中不得重切块（见 §6）。

## 5. P1 自检（进入阶段 A 前必须全部通过）

- 每个文件的行数与 §2 一致；
- §3.6 的结构断言全部通过；
- §3.5 的指针校验全部通过；
- 块覆盖：各块 obligation 之和等于各文件 UNIQUE 之和；块之间的 obligation 不重叠（上下文缝可以互相重叠，但不得覆盖他块的 obligation）；
- `blocks.json`、`pointers.json`、`align2.json` 写盘后，用重新加载的方式核对计数一致；
- 写入 `seal-log.jsonl`：`{"event": "STAGE_START", "stage": "A"}`。

## 6. 重算与失效

- 允许重算 P1 的情形：（1）发现对齐工具的缺陷，例如 K-gram 漏匹配、git diff 解析错误；（2）语料 HEAD 改变。第二种情形全部重做，并判为 BLOCKED，由研究发起人决定。
- 重算时：旧的 `align2.json` 改名保留，不删除；在 `ledger2.jsonl` 追加 REALIGN 记录（原因与差异统计）。已提交块的收据，若其块 ID、起止行与 chunk_sha256 不变，则保留；否则该块作废（RC），重做。
- 阶段 A 结束后不得重算 P1。阶段 B 的 B-04 会重验指针。

## 7. 自建工具合同

工具放在 `audit/GUI-ASSET-REAUDIT/tools/`，用 Python 标准库编写，运行一律使用 `python3 -B -I`。**不得复用或读取第一战役的脚本**（I0）。至少包括：

1. `freeze.py`：P0 身份冻结，写 `manifest2.json`；
2. `align.py`：方法 A、方法 B、取交集、指针、分块，写 `align2.json`、`align-disagree.jsonl`、`pointers.json`、`blocks.json`；
3. `slice_hash.py`：按 §1 对任意 (tag, s, e) 计算 chunk_sha256，供各工具复用；
4. `commit_block.py`：`--precheck` 与 `--commit` 两种模式（003 拍 5）；
5. `reread.py`：记录拍 4 的复读结果（PASS 或 FAIL，以及补记条数）；
6. `cursor.py`：从 `ledger2.jsonl` 与 `blocks.json` 算出下一个未提交块，刷新 `STATUS.md`；
7. `check_all.py`：阶段 B 的总校验（004 §1），以及 `--chain-only` 模式（005 §4 第 6 步）；
8. `echo_check.py`：protocol-echo 校验（005 §5）；
9. `token_scan.py`：自建 token 扫描（004 B-10）；
10. `selftest/`：合成小样本的自测（自造数个小文件，内含已知的共享、分歧与引文）。**所有工具必须先通过自测，才能用于正式语料。**

每个工具的输出都要落盘（写入文件），不得只打印到终端。

## 8. 格式侦察（阶段 A 第一块之后写入 SESSION）

下列事实必须由执行者在阅读中自行确认，不得直接假定：

- **角色标记**：设计者的侦察显示，`## User` 与 `## Codex` 这两种精确行出现频繁；同时，以 `## ` 开头的其他行也很多（例如 `## 已落盘`、`## 为什么`，多为 Codex 回复中的正文标题）。执行者须验证：角色边界是否只由精确的 `## User`、`## Codex` 行构成。若不成立，登记 FORMAT_ANOMALY。
- **胶囊形态**：导出中记录"本轮改动文件"之类摘要的行，其标记字样不得先验假定。执行者须在阅读中归纳其精确的字面模式（前缀或正则），记入 SESSION，供 004 B-08 的机械枚举使用。
- **最长行**：设计者的侦察显示，八文件中单行字节数的最大值约为 1.5 KB，未超过长行阈值。执行者仍须在每块记录最大行字节数；若出现超过 2000 字节的行，按 003 §9 处理。
- **行尾**：设计者的侦察显示，八文件均以 LF 结尾，未见 CR。执行者须自行核实并记录。

## 9. 失效条件

- 任一文件的 HEAD blob 与工作树不一致：BLOCKED，不得继续。
- 工具自测失败：修复后重新自测。自测通过之前产生的任何结果，一律不得沿用。
- 对齐结构断言失败：回到 §6 的重算流程。

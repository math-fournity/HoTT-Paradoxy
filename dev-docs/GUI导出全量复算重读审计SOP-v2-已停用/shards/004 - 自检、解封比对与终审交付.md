# 自检、解封比对与终审交付

## 1. 阶段 B：自建自检（不接触第一战役产物）

- **B-01 身份**：HEAD 与 `manifest2.json` 一致；`git status` 对语料为空。
- **B-02 收据重算**：每个 RA 的 chunk_sha256 由 `slice_hash.py` 重算一致；`ledger2.jsonl` 的 prev 链完整。
- **B-03 覆盖**：每个 UNIQUE 行恰属于一个已提交块的义务集合；remainder' = 0；块之间的义务无重叠。
- **B-04 指针**：`pointers.json` 中每个 SHARED 行的目标字节相等，且所在 run 长度不小于 K（重算）。
- **B-05 分类**：classes2 各块的覆盖与无重叠检查通过；类别码合法。
- **B-06 引文**：notes2 与 assets2 中的全部引文，都能在指明的行中以字节子串形式找到。
- **B-07 资产 1:1**：[A] 与 assets2 行一一对应；ID 唯一；"又见"指向存在的首现条目。
- **B-08 胶囊枚举**：用 SESSION 中记录的字面模式，对全部 UNIQUE 行做机械枚举，与 [F] 条目的集合（行号、字面内容）比对，差异逐条列出。
- **B-09 commit 枚举**：对全部 UNIQUE 行枚举十六进制候选（7 至 40 位，词边界）；每个候选用 `git cat-file -e <候选>^{commit}` 判断存在与否；与 [G] 条目比对。不存在的候选记为 UNVERIFIABLE，不推断为错误。
- **B-10 token 扫描**：`token_scan.py` 对全部 UNIQUE 行做两类扫描：（a）反引号包裹的标识，逐个去重；（b）标识形态，包括大写下划线标识、带编号的标识（如 `X-123` 形态）、版本号形态。每个出现过的 token 类型，都必须在 notes2 或 assets2 中有字符串匹配，或在豁免表中有理由。不允许静默缺失。结果记入 `token2-log.jsonl`。
- **B-11 复读完整性**：每个块的 `reread` 为 PASS；统计补记条数，写入 R1。
- **B-12 自建抽样复核**：种子 = SHA-256("GUI-ASSET-REAUDIT-v1" + manifest2.fingerprint)。每个文件从 UNIQUE 行中，按 SHA-256(种子 + ":" + tag + ":" + 行号) 排序，取前 20 行。对每个抽样行，用 RR 收据重读其所在块的原文（不依赖 notes2），重新摘出一条逐字引文，再与 notes2 中该行的相关条目比对，记录一致与否。
- **B-13 证明生成**：`check_all.py` 生成 `coverage2.json`，并把输出原文写入 R1。
- **B-14 阶段 B 出口**：B-01 至 B-13 全部 PASS，或为 UNVERIFIABLE 且附理由。写入 `seal-log.jsonl`：`STAGE_DONE B`。

## 2. 阶段 C：解封

- **前提**：`seal-log.jsonl` 中有 `STAGE_DONE A` 与 `STAGE_DONE B`。
- **动作**：追加 `UNSEAL` 事件（附理由）。此后每次打开第一战役路径，都追加一条 `ACCESS`（路径、目的、时间）。
- **禁止**：不得回头修改阶段 A 的条目。若阶段 C 发现自建错误，走 §3 的 C-补正规则。

## 3. 阶段 C：比对

### C-01 读取第一战役规范与结构

- 整读第一战役 SOP 的分片（只读规范条款），以及其闭包 §8 的裁决记录；
- 读取第一战役 manifest 的字段结构，用于 C-02。只读结构，不据此改变本次任何自建结果。

### C-02 内容并集对账（G'2）

1. 从第一战役的收据与 manifest 取得其 UNIQUE 区间表。
2. 对第一战役的每个 UNIQUE 行，计算其字节指纹，在本次的规范出现中查找相同指纹，记录命中与否。
3. 反过来，对本次的每个规范出现，检查第一战役是否有收据覆盖它（UNIQUE、RELOAD 或 SHARED 指针），记录缺口。
4. 对每条差异判定类别：顺序依赖（同一内容在另一位置）、对齐差异、第一战役漏读、本次漏读。

出现"本次漏读"时，走 C-补正规则。

### C-03 收据级比对（G'5、G'6）

对第一战役的每一笔收据 r（READ 与 RELOAD，包括被 void 的）：

1. 把 r 的行区间映射到本次的规范出现（经指针），得到本次的块集合。
2. 对每个块做 RR 重读（阶段 C 允许，写 RR，purpose 为 C-03）。
3. 在第一战役的笔记中定位 r 对应的节（按其 rid）。
4. 逐条比对第一战役笔记中的条目：
   - 用户轮与 Codex 的引文：是否逐字存在于指明的行（工具与人工双检）；
   - 资产条目：名称是否在指明的行中存在，定义是否与原文相符，类别与状态是否正确；
   - 机械与胶囊条目：是否真实存在于该行。
5. 与本次记录对照：
   - 第一战役有、本次无：核对原文。原文确有，记为本次漏记（走 C-补正规则）；原文没有，记为第一战役误记；
   - 第一战役无、本次有：记为第一战役漏记。
6. 按 §4 给出收据级判词。

### C-04 资产级比对（G'11 与 R5）

- 第一战役资产账本的每一条，与本次 assets2 对照，分为三类：匹配；第一独有（核对原文）；本次独有（核对原文）。逐条计数。
- 本次的 R5（重做版叙事与资产总表）与第一战役的 D2、D3 对照：八线叙事逐线比较，资产总表按 ID 与名称对照。

### C-05 机械主张复核

- 第一战役的 token-log、class_counts 与 CORRECTION 条目：逐条核对其正确性。
- 第一战役所称的"FileChange 胶囊"：设计者侦察到，导出中字面量 `FileChange` 出现 0 次。执行者须核实第一战役是如何识别胶囊的，核实其实际文本形态，并与 B-08 的枚举比对。
- 第一战役的 echo 存档：按其锚表（阶段 C 才读取）重算哈希。
- D3 中的计数声明（资产总数、各类数目、线索数）：与本次自建计数比较。
- D4 的每一条修订建议：逐条核对其事实前提（读取 README 与语料）。
- D2 的轮数表：只核对是否标注了口径，以及 GUI 块数是否被当作轮数。不复算权威轮数（权威口径来自原始轨迹，超出本次范围，登记为 UNVERIFIABLE）。

- **第一战役的已知待核项**：第一战役的机械主张（哈希、覆盖、计数、校验输出，以及覆盖文件与存档输出的一致性）全部独立复算。已知需要核实的具体项记在第一战役设计者审计报告的第六节（更正）中；该报告属于第一战役产物，阶段 C 才读取（SOP 001 §4）。核实结果写入 R2；涉及覆盖文件的影响在 R1 中注明。

### C-06 裁决合规

第一战役闭包 §8 的裁决 #1 至 #3，逐条核对其要求是否被实施（资产即时入账、收据互锁、轮次口径标注等）。

**互锁补录**：第一战役的收据互锁（规则见第一战役 SOP 003 的修订记录）在执行中可能出现拒发、补齐前置后重发的情形。复算在第一战役账本的 CORRECTION 与 PROTOCOL_NOTE 中查找此类记录，并逐项核对：（a）补齐的 token-log 记录与 notes 清单，是否与该区间内真实存在的内容一致（以 RR 重读后比对），而不只是能通过门槛；（b）补齐的时间是否晚于同一区间的阅读（若账本或 echo 的时间戳可查）；（c）补录是否改写了既有收据或既有笔记（不允许，只能追加）。找不到对应记录本身即为发现。互锁的拒发与账本零污染只证明门槛存在，不证明覆盖真实。

### C-07 F1 至 F6 复核

读取设计者审计报告。这是阶段 C 中读取它的唯一时机。对 F1 至 F6 逐项给出 CONFIRM、REFUTE 或 PARTIAL，附证据位置。另外登记新发现，编号自 F7 起。

### C-08 第一战役校验脚本作为外部对照

- 仅作对照（oracle），不替代本次判定。
- 第一战役的脚本会改写其目录下的 `coverage.json`，因此只能在一份副本上运行。副本放在 `audit/GUI-ASSET-REAUDIT/oracle-copy/`，并保持脚本所需的相对路径结构。
- 若无法在副本中运行（例如依赖 git 上下文），则不运行，在 R3 中登记为 UNVERIFIABLE。**不得修改第一战役目录。**
- 运行后，把每一项输出与本次 R1 对照，差异逐条解释。

### C-09 阶段 C 出口

- C-01 至 C-08 全部完成（C-00 即 §2）；每一笔收据都有判词；每一个资产都有对照结论；R2、R3、R4、R5 的草稿完成；
- 写入 `seal-log.jsonl`：`STAGE_DONE C`。

### C-补正规则

阶段 C 中发现本次阶段 A 的错误（漏记、误记、引文偏差）时：

- 只能以 RC 追加更正，并在 notes2 中追加 `[补正·阶段C]` 条目；
- 补正的依据必须是本次重读的原文（RR 收据），不得是第一战役的文字；
- R2 中须把该处标注为"阶段 C 补正"，并说明它是本次的错误。

## 4. 判词体系

**收据级判词**：

- **CONFIRMED**：第一战役笔记与原文、本次记录一致，覆盖正确；
- **DIVERGENT**：存在分歧，列出分歧类型与位置；
- **UNVERIFIABLE**：原文或证据不足以判定，列出原因；
- **TAINTED**：本次该块的阶段 A 记录因封印破坏而作废。正常情况下不应出现；若出现，须在 R3 首部披露。

**分歧分类**：

- **D-a 漏记**：原文有应记录的内容，第一战役未记；
- **D-b 误记**：第一战役记录的内容在原文中不存在，或与原文不符；
- **D-c 定位错**：内容存在，但行号错误；
- **D-d 引文偏差**：引文非逐字，且不属于 003 §4 允许的截断；
- **D-e 解读差**：定义、状态（首现或又见）或含义与原文不符；
- **D-f 分类差**：类别码或资产类别错误；
- **D-g 口径差**：轮次、计数、标注口径不一致；
- **D-h 收据差**：区间、哈希或链的问题；
- **D-i 机械差**：计数或索引与本次自建计算不一致。

**实质与非实质**：实质指影响资产存在与否、定义、覆盖结论或判词；非实质指格式、截断规则、标点（需明示）。

**主张级判词**（R3）：CONFIRM、REFUTE、PARTIAL、UNVERIFIABLE 四选一。

**总判词**（R3 首部，五选一）：

- REAUDIT_CONFIRMS：全部主张确认；
- REAUDIT_CONFIRMS_WITH_FINDINGS：主张确认，但有发现；
- REAUDIT_REFUTES_PART：部分主张被推翻（列出）；
- REAUDIT_REFUTES：主要主张被推翻；
- INCONCLUSIVE：阶段未完成，或关键门为 UNVERIFIABLE。

## 5. 独立性自评（R3 末尾）

写明：模型家族是否与第一战役相异（SESSION §1）；封印是否破坏（seal-log）；工具自测结果；UNVERIFIABLE 的比例与原因；已知的弱点。

## 6. 交付物规格

- **R1**：身份（P0 输出）；对齐方法、分歧清单与结构断言；remainder'；RA 哈希重验结果；token 覆盖（B-10）；胶囊与 commit 枚举（B-08、B-09）；抽样引文（B-12）；`check_all.py` 的输出原文。
- **R2**：G'2 对账结果；逐收据判词表（rid、判词、分歧类型、位置）；判词汇总；分歧分类计数；重大差异清单；阶段 C 补正列表。
- **R3**：主张表（编号、主张原文、判词、证据位置）；总判词；独立性自评。
- **R4**：F1 至 F6 复核表（每项判词与证据）；F7 起的新发现（严重度、证据、处置建议）。
- **R5**：八线叙事（每线按阅读顺序，每段附行号锚定）；资产总表（ID、名称、类别、位置、定义），与 assets2 的 1:1 对照。

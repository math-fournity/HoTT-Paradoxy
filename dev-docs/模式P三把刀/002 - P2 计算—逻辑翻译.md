# P2 计算—逻辑翻译

## 它的刀刃

P2 从脱敏的计算结构出发，把一段 formation／substitution／judgment 过程翻译成逻辑语言中可检验的模式。它不是问“理论的哪个对象最中心”，而是问：该理论是否允许条件被绑定、对象被形成、形成规则提供 bridge、输出对象被合法代回、回代后的判断以何种极性反馈，以及哪些 guard 改变这条链。

## P2/v0 中间表示

```text
Bind(φ) → Form(φ)=u → Bridge R(x,u)↔κφ(x) → Reenter x:=u
→ normalize φ(u) to H(q), q:=R(u,u) → Polarity / Guard / Trace
```

每一项都要有理论 X 的语法、规则或语义定位。`↔κ` 不能被含混地翻译成普通逻辑等价；它可能是对象语言、语义条件、单向规则或不完整描述。

## 当前方法与惯性

P2 的自然惯性是“把动态过程压缩为可归约的逻辑余式”。它因此能很好地识别 `q↔H(q)`，并分析负极性、正极性、bridge 方向和 guard；但也容易把 `Form` 视为已完成的原子交付，漏掉构造中的 pending／admission 时序。那一缺口由 P3 承担。

P2 的硬门是：

1. 条件确实在相应语言层可绑定；
2. formation 真产生 `u`；
3. bridge 的域与方向足够明确；
4. `u` 可合法进入回代位；
5. `φ(u)` 有可审计的 normalization witness，确实回到同一 `q`；
6. 理论专属 `ConflictOracle_X` 才能判局部反馈是冲突、允许固定点、语义依赖或未知。

## 强制 MatchTrace

P2 输出必须逐字段说明：source rule 如何填 `Bind`、`Form`、`Bridge`、`Reenter`；bridge 的域／方向如何限制推断；`φ(u)` 通过什么明确 rewrite 得到或未能得到 `H(q)`；正负／混合极性从何而来；哪一个 guard 阻断了链。它还必须说明为什么相邻的、更短的 rewrite 或另一个 bridge 不能替代这条链。若只给 `MATCHED`、`BLOCKED` 或公式而无这些来源—归约—淘汰链，状态为 `UNEXPLAINED_P2_MATCH`，不计作锻刀收据；共用输出格式由 [010](<010 - 代理匹配自我说明合同.md>) 固定。

## 进一步迭代的方法

- 建立 typed IR，而不是关键词清单；
- 用无限制形成＋负极性作正控制；用有界／分层／类型／证书 guard 作负控制；用正极性 `q↔q` 作 sanity control；
- 做 bridge-direction、reentry-domain 和 polarity 的消融；
- 将 `FINITE_SPECIFICATION_CONFLICT_CANDIDATE`、`ADMISSION_UPWARD_PROCESS_CANDIDATE`、`GUARD_BLOCKED`、`NONCONFLICTING_OR_UNDECIDED_FEEDBACK` 和 `INSUFFICIENT_ALIGNMENT` 保持不同身份；
- 当 P2 需要解释“为什么对象还未可用却已被使用”时，停止扩写逻辑余式，转交 P3。

## 停止条件

找不到对象语言 binder、双向 bridge 或合法 reentry 时，P2 必须停在 `PARTIAL/BLOCKED/UNKNOWN`。任何固定点、任意否定、任何递归定义都不自动构成 P2 命中。

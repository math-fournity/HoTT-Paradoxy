# 分母、范围与原子身份

## 1. 审计的对象不是“报告数”

这次审计问的是：一次已经发生的锻打、来源核对、控制、Battle、失败的预检或 Master 决策，在它发生的当时，怎样改变了
P 的字段、候选 Q 的状态、误报风险或下一次可检验的选择。它不问当前有多少 Markdown 文件，也不问后来有多少总结。

以下对象必须严格分开报告：

| 名称 | 定义 | 能否作为全量分母成员 |
|---|---|---|
| `AUDIT_CARD` | 一张历史审计写作卡，例如 R00--R15。它可以覆盖多个实际单位。 | 否 |
| `COARSE_NATURAL_UNIT` | 为理解锻造史划出的粗粒度自然阶段，例如 R01--R13。 | 否 |
| `H_NUMBERED_NODE` | 已统一成 `H001`--`H075` 的 P-DAG 编号节点。一个编号是一项原子审计义务。 | 是 |
| `NON_H_SESSION_RUN` | 非 H 报告中由精确 session/thread/turn 或等价运行身份区分的实际运行。 | 是 |
| `NON_H_DOCUMENTED_EXECUTION` | 有执行事实、但没有统一运行 ID 的早期探针或隔离执行。 | 在去重理由足够后是 |
| `NON_H_MASTER_DECISION` | 改变 P/Q 准入、来源边界或审计路线的 Master 直接来源判读／运行资格动作。 | 在排除与其他单位重合后是 |
| `BRANCH_CANDIDATE_EXECUTION` | 可达但未合入 current branch 的 P-DAG 实际运行；必须带分支、commit 与独立身份。 | 是；不得改变 current truth |
| `NODECARD_ONLY` | 只封存计划，未发现实际执行或决策收据。 | 否；登记排除理由 |
| `MATERIAL_REPORT` | 一个可能包含多次运行的来源报告或总结。 | 否；它是证据容器 |

预采样失败、认证失败、输入合同失败和零理论健康运行不是自动排除项。它们若实际改变可运行性、可见性、输入合同或后继
节点的资格，就仍是一个已发生单位；字段 `sampling_state` 说明它是否真的采样了模型，不能以“未采样”抹掉执行事实。

## 2. 唯一原子分母与四种计数

在本审计中，原子分母是经去重后的集合，而不是加总的报告数：

```text
D_atomic = H_NUMBERED_NODE
         ∪ NON_H_SESSION_RUN
         ∪ NON_H_DOCUMENTED_EXECUTION
         ∪ NON_H_MASTER_DECISION
         ∪ BRANCH_CANDIDATE_EXECUTION
```

每个成员必须只有一个稳定 `atomic_id`。`H001--H075` 保留既有编号；non-H 单位沿用原子账本中的 `Nxx` 家族或在
该账本中新增可回溯 ID。不能为了叙述方便把相同 session 重复算作 H 与 non-H，也不能把一个多终端 Battle 写成一个
不可拆的单位。

每次报告状态时都同时给出下列四个数，并禁止互相替代：

```text
C_cards       = 已写 AtomicAuditCard 数
C_coarse      = 已完成粗粒度自然单元数
C_canonical   = current branch 已注册、身份去重的 D_atomic 成员数
C_branch      = 未合入但在声明分支宇宙内的实际单位数
C_atomic      = C_canonical + C_branch，且跨集合去重后的总成员数
C_identity_remainder = 尚未分类、去重或排除的候选执行族数
C_audit_remainder    = 已冻结但尚无完成 AtomicAuditCard 的 D_atomic 成员数
```

在 A0 完成前，`C_atomic` 可以只报告已确认下界，`C_identity_remainder` 必须写 `UNRESOLVED`；这时禁止使用
“所有轮次”或“完整审计”字样。A0 只允许将 `C_identity_remainder` 归零，绝不能把它误写成
`C_audit_remainder=0`。A0 的 current 计数、source universe 和 branch disposition只由原子账本的最新顺序分片拥有，
不得从旧下界或审计卡数倒推。

## 3. 去重、拆分与排除的证据规则

每个候选执行族必须落入且只能落入下列一项：

| 判词 | 必需证据 | 对分母的效果 |
|---|---|---|
| `UNIQUE_ATOMIC_UNIT` | exact ID，或足以证明独立发生的来源、时间、输入与终态组合 | 纳入一个成员 |
| `DUPLICATE_OF(<id>)` | 与既有成员相同的运行／决策身份，以及为何不是重跑 | 不新增成员 |
| `SPLIT_INTO(<ids>)` | 一个报告含多个独立终端、角色或实际动作的可核证证据 | 分别纳入成员 |
| `NODECARD_ONLY_NOT_COUNTED` | 只找到计划卡，未找到执行／决策事实 | 不纳入，保留 locator |
| `OUT_OF_SCOPE_WITH_REASON` | 已证明与模式 P 锻造、P/Q 准入或其运行资格无关 | 不纳入，给出范围理由 |
| `IDENTITY_UNRESOLVED` | 证据不足以独立、重复或排除 | A0 不通过 |

“名称相似”“同一报告”“同一日期”都不足以去重。相反，缺少 runtime ID 也不自动表示独立；对于
`NON_H_DOCUMENTED_EXECUTION`，必须记录它与可能重复单位之间的输入、来源、时间、作者、模型或结果差异。

一个报告也不能因为只列出一个成功 session 就被当成一个执行。A0 必须枚举报告叙述中的**每一次实际启动尝试**：
若某次命令、认证、prompt-input 或 runner 调用在模型采样前退出，并且它改变了后继可运行条件、冻结输入或证据边界，
则它是独立的 `NON_H_DOCUMENTED_EXECUTION`。只有来源明确表明没有 console、final artifact 或实际 agent turn 的
后台／计划性尝试，才可按 `OUT_OF_SCOPE_WITH_REASON` 排除；一次成功重跑不能覆盖前一次可观察失败。

### 跨分支实际执行

`git` 分支的 `CANDIDATE_NOT_CURRENT` 身份不让它成为 current requirement、current Q 或 current tool 的证据，
但也不抹掉已经发生的 P-DAG 运行。A0 必须查看附着 worktree、reachable non-current ref 和它们的 P-DAG 路径：

1. 若其中有独立 NodeCard 之后的真实启动、输入失败、terminal run 或 Master 执行，将其作为
   `BRANCH_CANDIDATE_EXECUTION` 登记，使用 `branch-qualified atomic_id`、exact commit 与 raw/session identity；
2. branch 内复述、relay、source-recovery 或审计文件若没有一个独立 P-DAG 动作，保持为 `MATERIAL_REPORT` 或
   `OUT_OF_SCOPE_WITH_REASON`；
3. 不得把 branch 内的 `H060` 之类本地标签与 current branch 同名 H 编号合并。只有 raw identity、冻结输入和
   branch/commit 同时相同才允许 `DUPLICATE_OF`；
4. 每个 branch unit 的 AtomicAuditCard 要把 `current_truth_effect = NONE_UNTIL_INTEGRATED` 写明，仍可审其对
   P/Q 共同锻造方法的实际贡献或漂移。

## 4. 进入 A0 前的认知闭包

原子审计不是只对账运行 ID。它必须先恢复“为什么这些运行被称为锻刀、为什么锻刀服务于 Q”的原初工作意识。
进入 A0 前完整激活以下 owner，随后才接触每个原子单位的底层证据：

1. 本 SOP、[`P-FORGE-SOP`](<../模式P刀具持续锻造SOP.md>)、[刀具系统理念](<../刀具系统理念.md>) 与 [P-DAG 原初理念对照、自审与偏差处置](<../模式P动态DAG调度/005 - 原初理念对照、自审与偏差处置.md>)；
2. [模式 P 刀具系统全历史逐段对照审计](<../../audit/20261002-P-DAG-刀具系统全历史逐段对照审计.md>) 的全体分片，区分原初用户要求、旧规格和历史修复；
3. [P/Q 逐轮兵棋审计](<../../audit/20261003-P-FORGE-PQ-WARGAME.md>) 的 R00--R15，作为粗自然单元地图，而不是原子覆盖证据；
4. [P-FORGE 原子锻打账本](<../../audit/20261003-P-FORGE-ATOMIC-LEDGER.md>) 的所有分片，作为当前分母 owner；
5. 对当前候选实际发生的 NodeCard、报告、source pack、Git commit、session/trajectory 或运行收据。

这一加载顺序要求每张卡同时面对两种错误：把后来锻出的 P 当作旧运行已经拥有的规则，和把某次工具／运行事实错说成
与 Q 无关的元层杂务。它不要求重新运行理论 worker，也不将历史读入本身变成 Q 的证据。

## 5. A0：分母冻结门

在书写第一张新的 AtomicAuditCard 之前，执行 `A0_DENOMINATOR_FREEZE`：

1. 完整读取原子账本及其每个分片，复核 H 编号规范化、non-H 执行族和已有下界；
2. 用来源报告、session/trajectory 元数据、Git 历史、附着 worktree/reachable branch 与可见运行收据枚举剩余候选；
3. 对每一候选应用第 3 节的唯一判词，填写 raw identity、证据 locator 和去重理由；
4. 更新原子账本，使 `IDENTITY_UNRESOLVED=0`、`C_identity_remainder=0`，并给出 `C_atomic` 与
   `C_audit_remainder` 的精确数；
5. 冻结账本的 Git commit、哈希和审计顺序。后续若发现漏项，标记分母为 `STALE`，只重开受影响卡，不偷偷改总数。

`A0` 的成功不意味着找到了 Q。它只保证之后的逐卡审计知道自己在审什么；`Q-0 UNFORMED`、`ZFC_Q_NOT_LOCATED`
仍可完全保持。

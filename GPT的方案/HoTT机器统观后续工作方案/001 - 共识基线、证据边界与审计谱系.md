# 共识基线、证据边界与审计谱系

## 1. 本方案解决什么

本方案把此前分散的机器统观、计算合法性、时间／时序、Gödel、自反、自然 consumer、现实同任务和开放世界完备性工作，组织成一个可以逐项执行、失败、转向和审计的研究程序。

它不把“完整方案”写成“已经完成研究”。当前状态仍是：

```text
CURRENT_HOTT_REALITY_RELATIVE_WITNESS_COUNT_ZERO
/ ROOT_GOAL_ACTIVE_IN_CURRENT_PROJECT_OWNERS
/ ACTIVE_GOAL_AND_R4_RECORD_SOURCE_HASH_REVIEW_REQUIRED
/ GPT_PLAN_UPDATED_BY_USER_REQUEST
/ CURRENT_PROJECT_QUEUE_NOT_CHANGED_IN_THIS_PLAN_EDIT
/ NO_NEW_MATH_CLAIM
/ LOCAL_UNCOMMITTED_NOT_VERSION_CLOSED
```

## 2. 决定性问题

过去工作已经能高质量证明许多局部边界，但完整见证仍缺三个必须汇合的部分：

1. **提升来源**：谁把较弱的理论对象、相等、存在或部分分类当成完整过程身份、当前归约或有效交付？
2. **时间／现实任务来源**：理论侧与现实／应用侧是否具有相同 input、observation、completion？时间结构与时序关系是否被准确区分？
3. **exact HoTT 计算／自反**：一般停机和一般不完备性已有基础，精确 HoTT syntax/proof relation/representability/fixed point 与 HoTT essentiality 尚未闭合。

因此不能只继续 R4，也不能只把既有非因子化结果写成哲学结论。后续必须让三条线在一个候选上汇合。

## 3. 权威与证据顺序

1. 用户当前指令与 `rulings.md` 决定已接受目标和修正；
2. `核心认知.md` 决定研究问题意识；
3. Goal、Feature、MEMORY、方向、全景和 STATE 决定项目 current 状态；
4. proof source、kernel run、claim matrix、源码、来源快照、TaskSpec 和 Git 决定实现与证据；
5. GLM/GPT 审计与本方案说明为什么这样安排，但不单独改变 current truth。

用户本轮明确要求更新并拆分“GPT 的方案”，因此本逻辑文档成为 GPT 当前方案；这项授权没有自动扩展成 current owner、checkpoint 或 Git mutation。

## 5. 最终稳定共识

1. 当前合格见证为 0，且未被虚报；
2. 正向 Goal 门可由异质证据链闭合；开放世界无命中没有全局负向门；
3. P0/P1/A1 必须分层；
4. PromotionSource 必须有来源；
5. synthetic consumer 只能校准；
6. source-first 搜索必须有冻结分母、holdout、三终局和退出；
7. 时间与时序分别建模；
8. R4 先做一般性消融，不建第三套同型编码；
9. community implementation 与 formal calculus 分层；
10. canonicity 使用五组对照；
11. commit 只版本化证据身份，不证明事件或数学；
12. 后续应产生 TaskSpec/source/run/反模型，不继续无新证据的文本往返。

## 7. 为什么此前没有闭合完整见证

1. **局部数学强、提升来源弱。** C-71–C-148 的许多结果准确证明商化、截断、外延化或统一化后某观察量不可恢复，却没有说明谁承诺该观察量仍属于完整身份。
2. **consumer 分母偏向数学库。** 库审计善于证明资格防线怎样工作，却不能代替在线交付、资源、物理运动和应用合同的来源；自行合成 consumer 又不能取得自然性。
3. **R0–R3 越成功，越容易得到 generic 结论。** 固定发散、编码、公平枚举、半判定和一般不完备性是必要底座，但若 arithmetic-only 已承载机制，继续增加 HoTT 构造不会自动产生 HoTT essentiality。
4. **时间结构长期被时序工具遮蔽。** step/tick/deadline 的时序证明不能回答稠密性、连续性、运动和圆环复原的来源解释；直接把 Path 当物理运动同样不成立。

所以后续先做 PSJ 与 TGSQ，再回 R4。它们分别补最关键的两座桥，并让 R4 在早期消融中判断自己是 generic 继承还是 HoTT-specific 候选。

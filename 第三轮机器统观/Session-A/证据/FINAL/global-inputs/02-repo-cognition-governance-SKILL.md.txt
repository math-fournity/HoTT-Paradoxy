# Repo Cognition Governance

## Governance Acceptance

Governance artifacts are means, not the outcome. A governance change is successful only when it improves the
discoverability, correctness, evidence traceability, freshness, or efficiency of current and future cognitive closure, or
prevents Codex from bypassing or degrading continuous closure behavior. More files, rules, or Skills are not evidence
of improvement. Before write-back, the current task must already have a valid cognitive closure.

## Purpose

This is the persistent cognition-update core router. It can run after user correction, material evidence change,
a natural work unit, before compaction/handoff, or at task completion. It decides which persistent facts were
added, changed, invalidated, or retired; loads matching domain Skills; updates one authority per responsibility;
and requires the active closure to refresh from the updated owner. It does not require every file to change and
does not authorize unrelated writes.

## Authority, Scope, And Triggers

Follow the user's current instruction and the most specific active project instructions. This Skill governs
persistent knowledge only within the authorized task; it does not authorize unrelated code changes, external
systems, publication, push, or destructive actions.

Use it when work changes or may change requirements, parameters, design, interfaces, schema/data, configuration,
operations, verification status, current direction, asset routing, system lifecycle, history, or cross-session
handoff. Also use it when creating/repairing a formal repo's governance skeleton or resolving conflicting truth.

Do not use it merely because code was touched. A local implementation/test edit with no semantic, state, routing,
or durable-knowledge effect may need no governance write. The impact scan still decides; it does not force files.

## Continuous Closure Write-Back Loop

`COGNITIVE_CLOSURE_CONTINUITY_V1`. This Skill is not only an end-of-task documentation checklist. Trigger it when
a user correction, accepted requirement, decisive evidence, lifecycle state, owner/index, invalidation, or
cross-session handoff state persistently changes. First compute:

```text
new facts / changed facts / invalidated facts / no-longer-relevant facts
conflicts / unknowns / decisions / evidence / next action / reopen-or-stop triggers
```

Then apply cognition CRUD:

- **create/add** reliable durable cognition in the one owning source and add only necessary routes;
- **delete/retire** erroneous, superseded, or ineligible cognition from the active/current lane while normally
  preserving closed/superseded/replacement/Git history; physical deletion requires separate authorization;
- **update** the current owner in place, preserve old state in history, and propagate stale status to dependent
  conclusions, plans, indexes, and evidence claims;
- **read/query** the owner and decisive evidence after write-back, refreshing the direct active and indexed deferred
  sets before dependent work continues.

Use existing MEMORY/Feature/rulings/design/Topic/Goal/Git owners for natural-work-unit, compaction, session-end,
and handoff checkpoints. Do not require a new closure file, database, semantic Hook, or standing auditor. If no
persistent fact changed, record `NO_CHANGE(reason)` in the current task context and leave owners untouched.

## Task Closure Persistence Routing

`TASK_CLOSURE_ADMISSION_V1`. Before durable write-back, confirm the task's source verdict and make a separate
persistence projection. Reusing an existing Capsule does not prevent owner updates; building a new logical closure
does not require a new file.

- `CONTEXT_ONLY`: no durable fact changed; create no file or index entry.
- `OWNER_UPDATE`: route user intent to rulings, requirements to Feature, stable contracts to design/ADR,
  implementation to code/config/schema, verification/runtime to test/quality/run, and current state/next action
  to MEMORY. Add only necessary thin pointers.
- `SEED`: for a future/not-READY cross-session Topic, persist only purpose, depends_on, entry_points, unknowns,
  and reopen_if in the existing Topic/Program owner. Do not prewrite answers.
- `CAPSULE`: materialize only for high fan-out/risk/frequency, repeated multi-session closure cost, complex

  invalidation, and owner pointers; never duplicate current truths.
- `AUDIT_CLOSURE`: use the existing explicit auditable-closure route only when the user requests it or a high-risk
  decision needs an independent claim/evidence/conflict/unknown artifact.

Update README/docs indexes only for a new discoverable route. MEMORY remains the current queue/recovery/next
owner, not an archive of every closure. If one result changes a requirement, evidence, and next action, write each

## Normalize Intent Before Write-Back

Classify each new statement before persisting it:

- Explicit user requirement/correction: accepted requirement or constraint, with a source anchor.
- User exploration without decision: candidate or dev-doc, not accepted truth.
- AI-inferred improvement: proposal only; never silently promoted to user intent.
- Settled implementation choice: design/ADR, unless it has independent user-visible requirement semantics.
- Temporary parameter/experiment setting: current experiment/config fact, not permanent product requirement.
- Bug: actual implementation deviates from an existing requirement; normally fix code/tests without rewriting the requirement.
- Runtime finding: MEMORY/incident/evidence first; only stable reusable conclusions become docs.

For Feature records, keep decision state and delivery state separate. “Documented”, “implemented”, “verified”,
and “observed in one run” are distinct states and require distinct evidence.

## Load The Affected Cognition Bundle

Before editing durable assets, load only the affected component/system bundle:

1. user intent and current required behavior;
2. current stable system/detailed/interface/data/operations contract;
3. actual implementation/configuration/schema/dependencies;
4. tests and direct runtime/data evidence;
5. MEMORY current direction/open decisions;
6. history/incident/migration evidence when provenance or conflict requires it.

An index, map, old handoff, or Feature row is not a substitute for the source that decides the update.

## Parent Outcome And Return To Integration

BREADTH_FIRST_EXECUTION_V1. At each natural work-unit boundary, distinguish newly usable behavior or parent integration evidence, resolved material uncertainty/risk, and preparation alone. Research and DEFER can be valuable; their counts do not add up to a completed parent capability.

Once local work meets the current need, return to the incomplete integrated path. Further refinement needs a current consumer, direct necessity, a smaller-alternative check and a bounded return point. Existing investment, elegance or hypothetical reuse alone is insufficient. This is engineering judgment within existing authorization, not another user approval gate.

Update current outcomes, remaining scope and next action in the existing owner/plan/MEMORY; preserve history separately. Parent completion still requires integrated acceptance for all accepted scope, not checked child tasks or complete-looking reports.

## One Truth Per Responsibility

- `AGENTS.md`: constitution, invariants, hard safety, cognition and Skill routing.
- `README.md`: hierarchical project/system/component/asset map.
- `feature-list.md`: current accepted/candidate/retired requirements with decision and delivery state separated.
- `MEMORY.md`: current direction, verified findings, open decisions, next handoff, concise work history.
- `rulings.md`: original user decision and context.
- `docs/`: settled product/domain/design/interface/data/quality/security/operations/release/AI/history knowledge.
- `dev-docs/`: investigations, proposals, POCs, and unsettled work.
- Code/config/schema/tests/data/runtime/Git: actual implementation, verification, observation, and history evidence.

Reference current facts elsewhere; never maintain two full current specifications.

## Stable Docs And Dev-Docs

Create or expand a stable doc when future work depends on a cross-component or exact contract, the risk is high,
the same fact has been repeatedly rediscovered/misunderstood, the user requests a stable specification, or
runtime/experiment evidence has settled a reusable conclusion.

Do not create a stable doc for terminal transcripts, session plans, obvious local code details, unsettled options,
or template parity. The complete topic README skeleton may state “not applicable yet”, but it must not invent facts.

When sedimenting dev-docs:

1. extract only conclusions that still hold;
2. update Feature/source/evidence anchors and README routing;
3. mark the old document historical/superseded or let Git preserve it;
4. do not keep two full current specifications;
5. retain failed experiments and incident evidence when they change future judgment.

Long-lived docs should expose type, current/draft/historical/superseded identity, scope, truth boundary, freshness
when dynamic, and replacement relation. These are cognition labels, not a document workflow state machine.

## Indexed Long-Document Write-Back

Before drafting the first version of an important governance document, predict its topic topology, growth,
maintenance pattern, and common read path. If multiple stable topics, many sections, or a long sequential record
are already foreseeable, start with a canonical index and semantic shards instead of first creating a giant
monolith. A short heading plan is enough; do not create another approval ledger or document state machine.

A governance document judged too long, repeatedly appended, growing, or difficult to navigate should become a
canonical index plus semantic shards. Approximately 300 lines is only a soft prompt to consider the next natural
boundary. It is never a cap, read cutoff, error, release gate, cleanup quota, or reason to compress, delete,
densify, rewrite, or split a coherent semantic unit. When content is too large, create another shard at a natural,
named semantic boundary; a unit that must remain coherent may exceed the target. Line count alone is not a
mechanical failure, but an active document already judged too long does not receive a permanent legacy exemption.
Migrate it in a bounded unit with a recoverable baseline, consumer/link scan, content reconciliation, and rollback.

If a canonical path contains `governance-shard-index:v1` or `governance-shard-index:v2`, read the full index before
mutation. New logical documents use v2: the shard directory has the same name as the index stem
(`MEMORY.md` -> `MEMORY/`), shard files are `NNN - topic.md`, and the filename topic, index link title, and shard
H1 align; the topic normally reuses the original section heading. Published v1 paths remain read-compatible, but
that compatibility does not authorize new v1 documents. Update the owner shard for `topical` documents and the
indexed `append_target` for `sequential` documents. Creating a shard requires the shard file, ordered table row,
`last_shard`, and sequential `append_target` to change in the same commit. Do not write an unindexed shard or
treat only the final shard as the logical truth.

Current-truth owners are not append-only. When a Feature row, current design section, or topical owner becomes
stale, edit that owner in place and preserve the old state in Git, MEMORY/history, rulings, or a sequential log.
Never append a later "status correction", "latest", or "this supersedes above" block merely because the current
row is long; leaving both claims visible creates two current truths. Route historical detail to its authority or
shard at a natural semantic boundary without compressing content to meet the soft line target.

Before migrating an existing monolith, establish a recoverable commit and annotated boundary tag; retain the
canonical path as the index and reconcile headings/content plus links. Structural validation may fail broken
paths, duplicates, or stale last/append pointers, but line-target excess must remain a non-blocking notice. Do not
build automatic semantic splitters, shard databases, approval states, or bulk migrations by default.

## Feature Cognition Anchors And Evidence Bundles

When a Feature is created or its requirement, decision, delivery, implementation, or verification semantics
change, update the owning row in place with a compact five-part route:

- `SRC` requirement source;
- `DES` current stable design/decision;
- `IMP` implementation paths/symbols;
- `VER` test/run/receipt and scope;
- `EVD` implementation evidence bundle.

The Feature row still owns only current requirement and delivery state. A quality/release report, explicitly
authorized auditable closure, or equivalent bundle owns the per-Feature claim-to-asset-to-evidence mapping and
must list each Feature ID it covers. Related Features may share one bundle; do not create one file per Feature by
default. A verified state requires resolvable implementation, verification, and evidence anchors aligned with the
current snapshot. Missing evidence remains a gap.

Treat pre-contract free-text anchors as `LEGACY_PARTIAL` and upgrade current-queue, high-risk, and touched
Features incrementally. Do not fabricate historical closure from filenames, commit co-change, similarity, or AI
inference. When assets move or retire, update owners, consumers, replacement pointers, anchors, and the evidence
bundle together.

An optional parser/indexer Trace is a rebuildable derived index. Do not hand-edit generated rows or make it a
second truth. A pilot requires concrete discovery failures, an owner, bounded asset universe, provenance/coverage,
atomic generations, incremental-vs-fresh-full parity, benefit measures, and a retirement condition.

## System Design And Detailed Design

Do not force Feature rows to carry design knowledge.

- System design: component boundaries, topology, data/state lifecycle, external dependencies, failure domains,
  nonfunctional constraints, current/target separation, major tradeoffs, and legacy borrowing boundaries.
- Detailed design: API/CLI/events/schema, algorithms, state machines, error taxonomy, concurrency, idempotency,
  leases, recovery, migration, compatibility, and test contracts.

Separate frozen semantic invariants from versioned engineering contracts. A required capability must not degrade
into vocabulary; a field/CLI/schema v1 must not become an eternal product requirement. Route exact changes to
the matching domain Skills and verify real consumers/adapters/runtime before raising delivery status.

## System Islands, Lifecycle, And History

For a multi-system/multi-generation repo, the root README is a system registry, not a giant Feature/document list.
Each active island must make requirements, design, implementation/config, verification/runtime, and current state
reachable. Root truth covers only cross-system constraints and routing.

Frozen/historical/deprecated islands retain identity, lineage, final status, replacement/migration pointer,
critical incidents/lessons, evidence, and historical file/Git range. Do not bulk-migrate every old document.
Do not let historical islands participate in current routing without explicit reason.

Retirement requires Feature status, README lifecycle, replacement, consumer/data migration, retained evidence,
and misleading entry-point cleanup. Git preserves complete history; current docs preserve usable truth.

## Legacy Reconstruction And Structure Migration Write-Back

- A legacy commit ledger and entity registries own investigation coverage/lineage, not duplicate current truth.
- Keep metadata/stat candidates in dev-docs. Sediment only conclusions closed by exact diff plus tip/verification

- System islands/generations, experiments, implementations and research lines keep stable identities and lineage.

## Closed Knowledge Write-Back And Current Queue

- Keep the authoritative current execution queue, open questions/blockers, and open incidents near the top of
  MEMORY. Long logs and closed history must not outrank that queue.
- When an incident closes, remove it from current/open lanes and retain `CLOSED_INCIDENT`, closed_at, closure
  evidence, still-valid lesson, reopen_if, and the current route. Never delete history to prevent revival.
- Superseded facts retain replacement pointers; drafts/proposals never silently enter the current queue.
- Reopening preserves the prior closure record and adds new evidence, time, and scope. Do not silently overwrite
  CLOSED as OPEN.
- README routes to the queue/registry; Feature owns current requirements; rulings own original intent. Do not copy
  a complete current queue into several assets.
- Before finishing, check whether recent or repeated closed history still pollutes the current queue.

If a local repair exists only in a dirty/untracked worktree, label it `implemented locally, not version-closed`.
Do not claim cross-worktree or cross-machine recovery until the relevant assets have a recoverable commit.

## Parallel Worktree Write-Back And Canonical Integration

`PARALLEL_WORKTREE_COGNITION_V1`. Worktrees isolate working files and indexes; they do not serialize Feature,
MEMORY, current design, STATE, checkpoint, revision, or projection-generation semantics. Before write-back with
multiple writers, classify the current role as the single `CANONICAL_INTEGRATOR`, a `CONTRIBUTOR`, or an
`AUDITOR`, then freeze the canonical target, expected target HEAD, common base, candidate source OID, owned paths,
and current-owner set.

A contributor commits only exclusive implementation/proof/test/evidence paths plus a relay when cross-session
delivery needs one. The relay is `CANDIDATE_NOT_CURRENT` and records base/source/observed-target OIDs, scope,
changed paths, verification, failures, conflicts/unknowns, proposed owner updates, and integration state. It does
not modify the canonical queue, allocate a project revision/checkpoint, or become a second Feature/MEMORY/STATE.
Short work may carry the same information in existing task and commit records; do not require a new handoff file.

The integrator must:

1. verify the exact candidate OID, base, worktree/path ownership, dirty/index state, and expected target HEAD;
2. inspect the diff, requirements, evidence, failures, and target changes since the candidate base;
3. integrate only accepted exclusive artifacts using merge, cherry-pick, or reviewed extraction as appropriate;
4. update current owners in place on the canonical target and allocate each accepted logical revision/checkpoint
   exactly once;
5. rerun affected and integration verification, commit precisely, and report integrated commit plus accepted,
   deferred, and rejected parts.

If a contributor changed a current owner, preserve the candidate commit, extract exclusive artifacts, and have
the integrator re-express accepted semantics on the target. Do not blindly merge the whole commit, retroactively
renumber receipts, or delete branch history. Two branch-local passes, a clean text merge, or identical revision
numbers do not establish canonical integration. A target/owner/dependency/requirement change invalidates the old
review. Shared refs, tags, and config remain coordinated by the integrator. The stable contract is available with
`git -C /Users/aurolafly/codex show governance-v3.25.0:docs/design/detailed/Git多Worktree并行认知与Current-Truth集成合同.md`.

## Anti-Overdesign Boundary

Completeness is not a license to create:

- one file/checkpoint per requirement or ordinary task;
- manually synchronized global function/section trace databases or repo replicas;
- work-package platforms, document approval state machines, semantic gates, or standing audit agents;
- a complete handoff document for every session;
- Hooks that decide product semantics;
- copied current state in README, Feature, MEMORY, docs, and dashboards simultaneously.

Additional governance machinery requires at least two concrete recurring failures, or one high-impact incident
with a direct prevention mechanism; a maintainer, smallest pilot, validation method, and retirement condition.
Prefer repairing routing, requirements, contracts, tests, or runtime evidence first.

A bounded parser/indexer-derived Trace is not prohibited by name, but it must satisfy the pilot, coverage,
generation, parity, source-fallback, and retirement conditions above. It never becomes a hand-maintained authority.

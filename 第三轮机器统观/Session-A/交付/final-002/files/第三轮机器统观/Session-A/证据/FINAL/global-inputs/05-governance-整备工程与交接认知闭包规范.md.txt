# 整备工程与交接认知闭包规范

> 资产：HUMAN_EDITED；唯一owner：本文件；合同：PREPARATION_CLOSURE_V1。
> 来源：R-090与FLT R-028；状态：current normative；由现有closure/governance执行，不新建Skill或平台。

## 一、整备的对象与完成含义

整备是重要且可能巨大的认知闭包构建工程：让具体接管角色能在目标环境中正确、安全、可恢复地完成已接受任务。
其规模来自系统知识、真实连接、运行责任与失败面的交集；不是写完文档或把开发工作转交运行AI。
先恢复父级用户结果、当前可用链路、接管角色、权限和下一项最小真实验收。完整用户范围与当前工程动作相称，
不预造全部未来设施，也不把未来可能发生的每个问题设为当前阻塞。

## 二、持续清单

用户明确要求checklist或交接范围复杂时，在已有operations/plan owner维护一份持续清单；普通小任务不机械建新文件。
清单围绕用户旅程和真实连接展开，每项包含责任owner、所需输入、已作设计选择、可调用入口/consumer、实现状态、
正负/恢复验收、证据与失效触发。文档、实现、验证、当前运行分别标识，不能用单个勾代替四者。
接管者和未来复核者都进入范围：开发维护、运行值守、独立审计、人类授权、外部服务和数据责任必须有明确接缝。

至少扫描：

| 面 | 必须回答 |
|---|---|
| 目的/规格/来源 | 做什么、为何、成功和非目标；输入是否完整且可追溯；关键人类批准在哪里 |
| 角色/知识/治理 | 谁开发、谁运行、谁审核；global/project/role规则实际怎样加载；压缩与新Session怎样恢复 |
| 工具/真实连接 | 接管者实际能调用什么；身份/权限/参数/错误；无开发协助时能否跑完主要流程 |
| 代码/依赖/环境 | exact source/build/config/模型/部署版本、安装与升级/回退入口；声明与实物一致 |
| 数据/证据/状态 | durable authority、schema/血缘、锁/幂等、备份/恢复、查询重建与保留边界 |
| 运维/故障/容量 | start/preflight/stop/drain/retry/recovery、预算/限流/backpressure、错误分类与升级到人/开发者 |
| 观测/审计 | logs/metrics/traces/trajectory的范围、时效、水位/gap、权限和直接证据；监控离线时仍持续留证 |
| 交付/维护 | 安装/运行/审计说明、责任交接、Git/变更/发布、验收和接管后维护机制 |

每个自然单元、角色/版本/依赖变化、失败/修订及压缩前复核清单。旧PASS在相关输入变化时重新判断适用域；
历史失败不删，失效项原位更新，不能在后面追加“全部完成”盖过缺口。

## 三、文档与决策闭合

明确要求文档整备完整时，逐条回到用户原意和当前owners，消除矛盾、断链、占位和“以后让运行者决定”的工程选择。
对当前已接受范围，写定默认方案、选择理由、替代、参数边界、输入输出、错误/恢复、验收及何时复审；实现者无需猜。
“某输入未来才会产生”可以是完整合同，前提是其来源、owner、验证和缺失处置已经确定。

不能消灭事实未知，只能消除未处置的认知缺口。未提供credential、人类尚未批准语义、上游能力不存在或实测未执行，
必须保留明确状态、实际影响、责任人和下一动作；不能捏造PASS或把等待当同意。设计定型不等于这些前置已经满足。
用户“不能留待定问题”要求主动研究并裁定授权内的工程选择，不扩大为替用户签署授权、伪造数据或保证未知数学事实。

外部研究先明确待回答问题、权威来源与版本；技术事实用官方docs/schema/同版本源码，领域事实用原始论文/标准/实物。
研究保留证据支持范围、反例、冲突及对当前选择的影响，不靠资料数量证明充分。已有证据足够支持当前行动时进入实做。

## 四、实际接管与按需审计

在接管者真实入口、配置、权限和数据上跑最小完整链，再覆盖已接受范围的关键失败/恢复与容量。
观察input→action→durable outcome→query→audit；mock、文档和工具catalog仅证明各自局部，不能冒充接管能力。
运行者应消费准备好的工具和runbook；遇到软件缺口使用maintenance finding交开发者，不能临场修改控制面自授权限。
新工具/脚本只因明确当前consumer与重复机械工作而创建，复用已有manager/reader/controller，避免再造平台。

监督者不必常驻：系统自身必须持续保存可审计事实。审计入口能由冻结scope重算required集合，显示as-of、水位、
缺失、截断、权限和延迟；model自述不能代替采集。未暴露reasoning如实unavailable，secret不进入普通日志/报告。
审计finding和确定性业务状态分开。审计者提出修复不等于运行者可跳验证/改代码；修订后旧相关审计失效，按合同复核。

## 五、完成与返回父目标

整备完成要求：所有范围项都有唯一owner、已定运行合同、实际入口、相称正负/恢复证据和可用交接路径；必要前置没有
未满足项；future维护/审计者可从持久资产恢复，关键无人工开发协助的接管场景通过。否则报告精确partial，不宣称READY。
最终科研/业务产物可能是在接管后的运行阶段产生：需证明产物生成/验证/归档机制就绪，不能把最终成果本身偷加为所有
交接的前置，也不能反过来用交接READY宣布整个父目标完成。后续实际运行按原成功合同验收。

## 六、外部参照与本地选择

[Google SRE生产接管模型](https://sre.google/sre-book/evolving-sre-engagement-model/)把架构依赖、观测、事故响应、
容量、变更及培训纳入接管，并要求先补齐缺口。它支持本规范的运维覆盖视角，不证明AI可自主接管，也不要求照搬
Google组织/人员数量。这里的认知闭包、四层状态、exact角色隔离与按需AI审计是本地工程选择，需要独立运行证据。

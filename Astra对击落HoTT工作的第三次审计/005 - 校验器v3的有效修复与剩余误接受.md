# 校验器v3的有效修复与剩余误接受

## 1. 原问题已有实质修复

v3先按深度剥离嵌套块注释，保留pragma文本，跳过行注释，再用正则取OPTIONS token。本次用真实Agda检查与当前verifier的 `validate(..., rerun=True)` 验证了GLM所列的五类输入，结果全部符合预期：

| 控制 | Agda执行 | 当前verifier |
|---|---|---|
| 真实safe＋普通数据定义 | exit0 | PASS |
| 无safe＋公设 | exit0 | 正确拒绝safe资格 |
| 块注释内假safe pragma | exit0 | 正确拒绝 |
| 行注释内假pragma | exit0 | 正确拒绝 |
| 嵌套块注释内假pragma | exit0 | 正确拒绝 |

因此前次“块注释内假pragma”这个具体反例已经关闭。不能继续把旧误接受状态说成v3当前行为。

## 2. 字符串字面量是仍未正确处理的实际输入

GLM第002片§4主动说明没有处理字符串/字符字面量，这是诚实边界；但其理由“本检查只消费pragma区，所以足够”不成立为当前实现保证：它先扫描整文件，再从扫描结果提取pragma，必须先知道一段文本是否位于字符串内。

本次加入一个明确的holdout：

```agda
{-# OPTIONS --cubical #-}
module StringLiteral where
open import Agda.Builtin.String using (String)
text : String
text = "{-# OPTIONS --safe --cubical #-}"
postulate witness : Set
```

实际文件：[StringLiteral.agda](../audit/astra-hott-third-20260919/synthetic-option-controls/StringLiteral/StringLiteral.agda)。此处字符串只是普通数据，真实OPTIONS没有safe。

## 3. 真实观察与影响范围

- 原命令Agda exit0，正常接受非safe公设模块。
- 当前正式verifier返回 **PASS_WITH_SCOPE / EXACT_EXIT_STDOUT_STDERR_MATCH**，误把字符串中的选项当作safe资格。
- 对同一文件实际追加CLI `--safe`，Agda exit42并明确报告 **SafeFlagPostulate**。

证据：[OPTION-CONTROLS.json](../audit/astra-hott-third-20260919/OPTION-CONTROLS.json)；[强制safe原始输出](../audit/astra-hott-third-20260919/checks/control-StringLiteral-forced-safe/stdout.txt)；[控制脚本](../audit/astra-hott-third-20260919/option_controls.py)。所有合成源、RUN、index均在本审计独占目录，并标注SYNTHETIC；不进入正式主张矩阵，不是数学反例。

这是**外层验证器对输入资格的误判断**。Agda safe机制工作正常；当前真实safe证明没有因为该控制就失效。本次只证明这个具体实现和输入的行为，不做完整Agda词法认证。

GLM披露了未处理的语言结构，值得肯定；但第005片把“verifier有效选项识别”整体划为完成、第006片说A09已全部修复，超出了五控制范围。准确状态应是“已修指定注释样例，字符串等未覆盖结构仍可能误接受”。

## 4. 避免继续只修一个字符串模式

最小可靠方向是让Agda在正式运行合同中实际启用规定的safe选项，并保存新argv和新收据；文本扫描用于解释配置与发现冲突，不独自承担safe资格的最终依据。这样无需把审计工具升级为另一个完整语言实现才能验证该关键性质。

若仍保留源码词法分析，就应处理字符串、转义和字符语境，或明确拒绝其不支持输入，而不是一面遍历全文件、一面声称只需局部pragma语义。有效语言子集也须被实际校验，不能只写在说明中。

本轮按审计授权交付控制与修复建议，不修改GLM的canonical verifier。五个已修控制与一个剩余误接受同时记录，不用“全部失败”抹去实际进步，也不用“五例成功”认证所有输入。

```text
  → 才生成／评价 HoTT 候选
```

自行构造的 consumer 只能标 `SYNTHETIC_CALIBRATION_CONSUMER`。只有已存在的社区用法、论文任务、应用合同或独立来源能提供 `NATURAL_OR_SOURCE_GROUNDED_CONSUMER` 资格。

方案中的 RL 规格还有若干必须先修正的形式问题：

1. 文档标题和正文称“五个任务族”，实际列出 T1–T6 六族；分母必须一致。
2. 它把 `Complete(P,spec)` 写成“存在有限界 n，使有限前缀满足验收谓词”，同时直接标成 `Π₂⁺`。展示的量词形状不足以支持该分类；必须删除等级标签，或为每种 spec 给出严格的量词正规形和证明。
3. `t`、`e` 与因果标签是人工定义的模型坐标。它们可以表达逻辑时钟、抽象成本和输入可见性，却不能自动承担物理时间、物理能耗或物理因果的证据。
4. `I : TaskSpec → HoTT类型` 的示例主动删除 deadline、因果序与模数。若该翻译由研究者任意选择，Th-1 几乎只是预设信息损失的展开。必须证明 `I` 来自一个真实 HoTT 构造或实际使用，而不是为了得到反例而设计。
5. `d : HoTT对象 → RL过程` 过强且通常没有天然定义。更稳妥的是关系式交付语义：某个实现／解释关系何时把理论见证关联到操作过程，并明确它需要的额外输入。
6. “canonical”必须逐任务定义自然性、等变性或表示不变性；不能把二元素 swap 的判据直接复制到 deadline、在线或测量任务。
7. Th-3 的“π 不在 α 的像中”尚未定义类型。首轮只能逐候选证明某项具体附加数据充分／必要，不能先宣称统一支付下界。
8. ERCF-3 不能由一个专为需要证明谓词而设计的任务自动“解锁”。只有独立来源任务确实需要那种对象层表示与自反接口，才形成门 B 消费者。

任务族的优先级也需调整：

- T1 限时、T2 在线、T4 资源与 T5 有效逼近适合做首轮来源选择；
- T3 竞态需要固定具体并发语义与公平性，不能把一个 `race` 函数当成整个现实并发任务；
- T6 几何连续性风险最高。HoTT 的 Path、interval、`S¹` 与 HIT 不自动表示物理时间轨迹、稠密时空或现实运动。T6 必须先区分“同伦路径的几何／身份角色”与“物理运动的时间参数”，再证明二者之间采用了什么解释。否则会把用户要求保留的“时间”问题再次简化成一个并无现实来源的形式类比。

### 4.4 03 号阶段 C：计算合法性的 HoTT 特有位置

R4 一般性消融与“停止重复编码”的原则应当接受。`stuck-transport` 现有规格则不能进入 F-011。

GLM 给出的项是：

```agda
stuck = transport (λ _ → Bool) (UA notEquiv) true
```

这里的 family `λ _ → Bool` 是常值 family；展示式没有让被 transport 的元素随类型 `X` 变化，因此没有表达 `notEquiv` 对 Bool 元素的预期作用。若研究目的是比较 univalence 路径对元素的 transport，至少需要首先审查 `λ X → X` 这一类依赖 family，并固定 universe、相等类型、`--without-K` 等演算条件。

即使修正 family，仍必须区分：

1. 证明助手把 `postulate UA` 视为不透明常量的求值现象；
2. 扩展理论中的判断计算规则；
3. 可命题证明的 transport 行为；
4. canonicity／normalization 的元定理；
5. Cubical 实现中的计算规则；
6. 编译后端是否支持该实现版本。

用编辑器归约命令观察一个不透明公理项停在某种形状，只能支持该工具／该项的求值记录；它不能单独证明一般不规范化，也不能证明 HoTT 把“公理资格”承诺成了“可执行能力”。任何不透明公理都可能产生相似现象，因此还需要 HoTT 必要性消融。

S052/N10 的后端结果同样只属于固定 Agda 版本与后端组合。它不能被写成“cubical 理论最终不可交付”。阶段 C 可以保留为一个重新设计的 canonicity／conversion 对照包，但不得以当前 GLM 示例作为决定性证据。

### 4.5 支付—债务目录

建立统一目录有价值，但目录必须先使用中性分类：

| 类别 | 含义 |
|---|---|
| `DATA_RETENTION` | 为任务保留标签、模数、代表、trace 或其它数据 |
| `ASSUMPTION_STRENGTHENING` | 加入 UIP、choice、Trans 等额外前提 |
| `MODAL_OR_CONTEXT_RESTRICTION` | crisp/global、pointwise-fibrant、empty-context 等适用域限制 |
| `THEORY_EXTENSION` | 增加 interval、cofibration、clock、directed／quantitative 结构 |
| `IMPLEMENTATION_LIMITATION` | 某证明器版本、编译后端或运行接口的能力边界 |
| `POSITIVE_CONTROL` | 显示在更丰富表示中任务可完成，但不自动说明该丰富是唯一或必需 |

只有一行同时满足以下条件时，才可进一步标 `ABSTRACTION_DEBT_CANDIDATE`：

1. 附加项对应抽象前同一任务已经具有的前提或区分；
2. 该项在抽象中确实被删除或失去可恢复性；
3. 当前 consumer 对该项具有本质依赖；
4. 恢复它没有改变任务、输入、观察量或完成标准；
5. 结论不是某个更强、原任务并未要求的统一化义务。

因此，`DEFENSE_WORKS_WITH_EXPLICIT_PAYMENT` 不能整体翻译为 Z 铁律已证。它首先说明理论把条件写清楚了；这可能是债务显性化，也可能只是诚实的适用域声明。

### 4.7 05 号 Goal 与治理修订

#### Goal 双轨

我赞成另行交付“当前最强哲学与机器证据综合”，不赞成现在直接改变根 Goal 的状态机。

更简单的做法是：

- 根 Goal 保持 `ACTIVE` 与原完成门；
- 综合报告在自己的文档头标 `INTERIM_SYNTHESIS_COMPLETE_WITH_OPEN_BRIDGES`；
- STATE 只有在用户明确采纳后才登记该里程碑；
- 不新增 `DELIVERED_ASSEMBLED` 这种容易被误读为 Goal 部分完成的全局状态。

#### Git 版本闭合

GLM 建议一次 stage 整个 `HoTT/formal/` 和一段日期后的全部 runs，范围过宽。正确顺序是：

1. 枚举每个未提交 proof package 的 source/run/index/依赖闭包；
2. 区分当前 AI、用户、历史来源与其它 AI 的 dirty 所有权；
3. 运行 closure verifier；
4. 按一致的 proof package 或逻辑批次精确提交；
5. 提交后再更新 version-closed 状态并重验。

本方案审计不包含 commit 授权，也不执行 Git 提交。

#### 治理预算

05 号的四项硬数值不应采纳：

- `STATE.json ≤1MB` 没有功能依据；若要拆 machine-managed JSON，必须先设计 schema、manager、原子写入、查询、迁移、兼容和回滚，不能套用 Markdown 分片合同。
- 合并 `NOT_TOUCHED` KC 行与项目当前“逐 KC 回评”明确冲突。
- 每日 corrective 次数上限可能阻止必要纠正。
- “治理时间不超过数学时间一半”不可稳定测量，也不反映高风险任务所需证据成本。

应采用结果型指标：一次工作单元是否减少关键未知、是否出现重复重绑、是否有无消费者的重复基础设施、加载是否出现 query-first 误提升、同一事实是否被多 owner 维护。若这些现象重复发生，再做专门治理修订。

#### 文献日期

删除“逾期处置”建议。2026-09-14 是纳入截止日期，不需要顺延。新来源若发表于截止日以后，应进入新 revision 或 UI-01；若只是继续审读截止日前来源，仍属于同一分母。

### 阶段 R2：来源先行的现实／应用任务分母

先从外部学术与工程来源选择最多两个任务族，不一次建设六族。建议顺序：

- 任务在本项目以外已经存在；
- 输入、观察量和完成标准可被引用；
- consumer 在看到本项目候选以前已经存在；
- 任务不依赖有争议的物理本体判断即可成立；
- 能与一个具体 HoTT 构造或社区接口建立候选联系。

同时建立现实侧计算文献分支，至少覆盖可计算分析、Weihrauch、Pour-El–Richards、物理 Church–Turing 论题的边界、实时／并发操作语义、Blum／资源复杂度以及资源敏感／定量类型理论。每项继续服从现有 LIT 的来源、版本、前提与 TaskSpec 映射纪律。

### 阶段 R3：操作任务模型，而非“现实本身”

只为 R2 选中的任务建立 `OperationalTaskModel`。模型至少包含：

- 原始 task source 与版本；
- 输入到达／可用条件；
- 观察 trace；
- 完成谓词；
- 资源或截止条件；
- 正例与反例；
- 模型没有覆盖的现实因素。

模型的第一目标是忠实重述来源任务；第二目标才是生成候选。形式化结果只能写“在该任务规格语义下”，不能写成物理现实的全称定理。

### 阶段 R4：从真实 HoTT 用法导出解释桥

解释桥不得任意删除 deadline、时序、模数或成本。它必须来自：

- 标准 HoTT／Cubical 构造的精确规则；
- 论文或库的实际接口；
- 已预注册应用对该接口的使用；
- 或显式标为 `SYNTHETIC_TRANSLATION` 的校准映射。

对每座桥机器或来源核查：形成、消去、相等／Path、计算规则、观察保持和任务保持。若桥只在研究者主动删去字段后出现，候选保留为合成校准，不升级。

### 阶段 R5：证明与最强反解释

1. 同任务下的具体非因子化；

3. 某项具体附加数据的必要性与充分性；
4. HoTT 特有构造消融；
5. 富表示、模态限制或显式时序的最强正控制。

如果富表示在不改变任务的情况下完成要求，结论是有范围的表示边界；如果只有改变任务才能恢复，才继续审查现实相对不相容。

## 六、Goal、停止条件与治理的最终建议

### 6.1 根 Goal 暂不改写

GLM 的双轨思想可作为交付组织方式，但当前不应修改根 Goal。原因是：

- 用户尚未裁定降低或改变最终完成门；
- 中间综合可以有自己的完成状态，不需要扩大 Goal 状态机；
- 现有严格门正好阻止表示边界被误报为 HoTT 悖论。

以后若用户希望加入负向终止条件，应单独裁定“在何种已声明分母闭合后，可以结束当前研究计划但不声称全局不存在”。这与正向 witness 完成门是两件事。

### 6.2 每个有界单元使用证据停止条件

接受：

- 分母闭合；
- 关键前提被反证；
- HoTT-essentiality 消融失败；
- 同任务正控制完成；
- 来源 consumer 不存在于已声明范围；
- 继续只会复制已知机制。

不接受：

- 固定周数自动改变数学判词；
- 每日纠错次数上限；
- 为满足进度强迫每个 Session 产生新构造；
